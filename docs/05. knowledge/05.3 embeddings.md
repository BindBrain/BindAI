# Embeddings

Embeddings are numerical representations of text that are commonly used for semantic search and Retrieval-Augmented Generation (RAG).

However, embeddings are **not currently exposed as a verified BindAI core API** in the project version being documented.

This document therefore explains the concept and its relationship to BindAI without presenting embedding generation, vector search, or embedding providers as implemented framework features.

---

# What Is an Embedding?

An embedding converts content such as text into a numerical vector.

Conceptually:

```text
"The server is offline."

↓

Embedding Model

↓

[0.12, -0.48, 0.73, ...]
```

The resulting vector represents characteristics of the input text in a mathematical space.

Texts with similar meanings can produce vectors that are close to one another according to a chosen similarity measure.

---

# Why Embeddings Are Useful

Traditional keyword search primarily looks for matching words.

For example:

```text
Document:
The application crashed unexpectedly.
```

A user might ask:

```text
Why did the program fail?
```

The two texts use different words while expressing related concepts.

Semantic retrieval can use embeddings to identify that relationship.

---

# Semantic Search

A typical embedding-based search architecture looks like:

```text
User Question

↓

Generate Query Embedding

↓

Vector Search

↓

Relevant Documents

↓

Language Model
```

The document collection is usually embedded ahead of time:

```text
Documents

↓

Chunking

↓

Embedding Model

↓

Vector Storage
```

This is a general RAG architecture, not the current BindAI execution pipeline.

---

# Embeddings and BindAI

BindAI currently provides tools that allow applications to expose Python functions to agents.

An application could therefore integrate an external embedding or vector-search system through a tool.

For example:

```python
from bindai import tool


@tool
def search_documents(query: str) -> str:
    """
    Search an external semantic document index.
    """
    # Application-specific embedding and vector-search logic.
    ...
```

The external system could perform:

```text
Query

↓

Embedding Service

↓

Vector Database

↓

Relevant Documents

↓

Tool Result

↓

Agent
```

BindAI does not need to own the embedding implementation for this integration pattern.

---

# Embeddings Are Not Tools

An embedding model and a BindAI tool are different concepts.

An embedding model transforms information:

```text
Text → Vector
```

A BindAI tool is an executable Python function that an agent can invoke:

```text
Model → Tool Call → Python Function → Tool Result
```

An application can combine the two by implementing embedding operations inside a tool or by calling an external retrieval service.

---

# Document Embeddings

In a typical semantic-search system, documents are embedded during indexing.

```text
Documents

↓

Split into Chunks

↓

Generate Embeddings

↓

Store Vectors
```

The stored vectors can later be compared with a query vector.

BindAI currently does not expose a verified built-in document-indexing or embedding pipeline that performs these operations automatically.

---

# Query Embeddings

At query time, the user's question can also be converted into a vector.

```text
User Question

↓

Embedding Model

↓

Query Vector

↓

Vector Search

↓

Relevant Chunks
```

The resulting chunks can then be supplied to the model.

Again, this describes a standard application architecture rather than a currently implemented BindAI API.

---

# Vector Search

Vector search compares a query vector against stored document vectors.

Conceptually:

```text
Query Vector

↓

Similarity Search

├── Document A
├── Document B
├── Document C
└── ...

↓

Top Matches
```

Common similarity approaches include:

* cosine similarity
* dot product
* Euclidean distance

The appropriate method depends on the embedding model and vector-search system.

---

# Vector Databases

Applications implementing semantic retrieval may use systems such as:

* Qdrant
* Chroma
* Weaviate
* Milvus
* Pinecone
* pgvector
* Redis Vector Search

These are possible external integrations.

They should not be documented as BindAI-supported providers unless BindAI adds explicit integrations for them.

---

# Embeddings vs Keyword Search

| Keyword Search                      | Embedding Search                      |
| ----------------------------------- | ------------------------------------- |
| Matches words                       | Compares semantic representations     |
| Primarily lexical                   | Meaning-oriented                      |
| Simple to implement                 | Requires embedding generation         |
| Often easier to debug               | Requires vector-search infrastructure |
| Does not require an embedding model | Requires an embedding model           |

Both approaches can be useful.

An application can also combine them in a hybrid retrieval system.

---

# Embedding Models

Embedding models can be provided by:

* hosted AI providers
* cloud AI services
* open-source models
* locally deployed models

The choice depends on:

* retrieval quality
* language support
* vector dimensions
* inference performance
* cost
* privacy requirements
* deployment environment

BindAI currently does not define a verified core embedding-model abstraction.

---

# Embeddings and Memory

Embeddings and Memory should not be treated as the same feature.

BindAI currently exposes a memory system containing:

* `Memory`
* `MemoryRecord`
* `MemoryProvider`
* `InMemoryProvider`
* `SQLiteMemoryProvider`
* `VectorMemoryProvider`
* `MemoryManager`
* `MemoryRegistry`

`MemoryRecord` can also contain an optional embedding field:

```python
MemoryRecord(
    key="example",
    value="Some information",
    embedding=[0.1, 0.2, 0.3],
)
```

This does **not** by itself mean that BindAI provides a complete embedding-generation system.

The application still needs to provide the vector values unless an embedding provider is explicitly implemented elsewhere in the project.

---

# Embeddings and Memory Search

The current memory API exposes:

```python
memory.search(
    query,
    namespace="default",
    limit=10,
)
```

The exact search behavior depends on the configured memory provider.

Because BindAI currently includes a `VectorMemoryProvider`, vector-oriented memory behavior is part of the implemented memory subsystem.

That should be documented separately from claiming that BindAI provides a general-purpose document embedding or RAG framework.

---

# RAG Architecture

A complete RAG application commonly combines several independent components:

```text
Documents

↓

Chunking

↓

Embedding Model

↓

Vector Store

↓

Retriever

↓

User Question

↓

Query Embedding

↓

Relevant Chunks

↓

BindAI Agent

↓

Language Model

↓

Response
```

BindAI can serve as the agent layer in such an architecture.

The document ingestion, embedding, vector storage, and retrieval components may be implemented by the application or external services.

---

# Current Project Status

The following should **not** currently be documented as built-in BindAI embedding features unless corresponding public APIs are added and verified:

* `Embedding`
* `EmbeddingModel`
* automatic embedding generation
* document embedding pipelines
* built-in embedding providers
* automatic vector indexing
* automatic vector retrieval
* automatic RAG execution
* built-in document chunking
* built-in vector database integrations

The existence of `embedding` data on `MemoryRecord` and the presence of `VectorMemoryProvider` should not be expanded into claims about a general embedding subsystem.

---

# Best Practices

When integrating embeddings into an application:

* Use the same embedding model for indexing and querying.
* Keep document chunks meaningful.
* Store useful metadata alongside vectors.
* Re-embed documents when their content changes.
* Avoid mixing vectors generated by incompatible models.
* Choose a similarity method appropriate for the embedding model.
* Keep retrieval logic separate from agent behavior.
* Treat vector databases as external integrations unless explicitly supported by BindAI.
* Document verified framework APIs separately from application-specific RAG infrastructure.

---

# Summary

Embeddings are a common technology for semantic retrieval and RAG systems.

BindAI can participate in an embedding-based architecture through its existing agent and tool abstractions, and its memory subsystem also contains vector-oriented functionality.

However, the current project should **not** be documented as providing a standalone embedding-generation or automatic RAG subsystem unless those APIs are actually implemented.

This keeps the documentation aligned with the real project instead of documenting roadmap functionality as if it were already available.

# Retrievers

Retrievers are responsible for finding relevant information from a knowledge source.

In a Retrieval-Augmented Generation (RAG) system, a retriever typically receives a query and returns relevant documents or document fragments that can then be provided to a language model.

However, **Retriever functionality is not currently part of the implemented BindAI API documented in this version of the project**.

---

# Current Status

The current BindAI implementation does not expose a verified public `Retriever` abstraction or an `Agent.use_retriever()` API.

Therefore, retriever-based workflows should **not** be treated as currently supported BindAI functionality.

The following API should not be used:

```python
agent.use_retriever(
    retriever,
)
```

No such public API has been established in the current implementation.

---

# What a Retriever Is

A retriever is a component that searches a knowledge source and returns information relevant to a query.

A typical RAG architecture looks like:

```text
User Question

↓

Retriever

↓

Relevant Documents

↓

Language Model

↓

Final Response
```

The retriever is responsible for the search step. It does not generate the final response itself.

---

# Typical Retrieval Strategies

A future retriever implementation could support different retrieval strategies.

### Keyword Retrieval

Searches for matching words or phrases.

```text
User Query

↓

Keyword Search

↓

Matching Documents
```

This approach is simple and can work well when users use terminology that closely matches the source material.

### Semantic Retrieval

Uses embeddings to compare the meaning of a query with stored content.

```text
User Query

↓

Embedding Model

↓

Vector Search

↓

Relevant Documents
```

Semantic retrieval can find relevant information even when the query and source document use different wording.

### Hybrid Retrieval

Combines keyword and semantic search.

```text
Keyword Search
       +
Semantic Search
       ↓
Combined Ranking
       ↓
Relevant Results
```

Hybrid retrieval can combine the strengths of both approaches.

> These strategies describe possible retrieval architectures. They are not currently documented as implemented BindAI retriever features.

---

# Top-K Retrieval

A retriever commonly limits its results to the top `K` matches.

For example:

```text
Search Results

↓

1. Result A
2. Result B
3. Result C
4. Result D
5. Result E

↓

Top 3

↓

Result A
Result B
Result C
```

A smaller result set can reduce the amount of context sent to the language model.

The appropriate value of `K` depends on the retrieval system and application requirements.

---

# Metadata Filtering

Retrieval systems can also use metadata to narrow the search space.

For example:

```text
Category = Documentation

Version = 2.0

Language = English
```

Filtering before ranking can reduce irrelevant results.

Again, this describes a common retrieval design rather than a currently exposed BindAI Retriever API.

---

# Retriever and Knowledge

A retriever and a knowledge source have different responsibilities.

| Knowledge Source       | Retriever             |
| ---------------------- | --------------------- |
| Contains information   | Searches information  |
| Stores or exposes data | Selects relevant data |
| Source of context      | Retrieval mechanism   |

Conceptually:

```text
Knowledge Source

↓

Retriever

↓

Relevant Information

↓

Language Model
```

The current BindAI documentation does not establish a public Retriever implementation connecting these components.

# Custom Retrievers

A future Retriever abstraction could allow applications to integrate external search systems such as:

* SQL databases
* Elasticsearch
* OpenSearch
* REST APIs
* graph databases
* enterprise search systems
* vector databases
* cloud search services

A custom retriever would typically provide a query operation and return relevant results.

For example, conceptually:

```python
results = retriever.search(
    query,
)
```

This is an architectural example only. It is **not a current BindAI API**.

# Retriever in a RAG Pipeline

A complete RAG system commonly follows this pattern:

```text
User Question

↓

Query Processing

↓

Retriever

↓

Relevant Documents

↓

Prompt Construction

↓

Language Model

↓

Final Response
```

The retriever is therefore an important component of a RAG architecture.

However, this pipeline should not be interpreted as the current BindAI execution pipeline unless the corresponding functionality is implemented and exposed by the project.

# Knowledge Overview

Knowledge is intended to provide agents with access to information outside of the model's built-in knowledge.

At the current stage of BindAI, knowledge functionality should only be documented here when it is implemented and exposed by the installed package.

This distinction is important because planned retrieval, document, embedding, and RAG functionality should not be presented as available framework behavior until it exists in the project.

---

# Knowledge and BindAI

Knowledge is conceptually different from the information already contained in a language model.

A knowledge system may eventually allow an application to provide external information such as:

* application documentation
* business data
* reference material
* files
* databases
* other external sources

However, the specific knowledge sources, retrieval mechanisms, and APIs should be documented only when they are implemented by BindAI.

---

# Knowledge vs Memory

Knowledge and Memory represent different concepts.

| Knowledge                                    | Memory                                      |
| -------------------------------------------- | ------------------------------------------- |
| External or reference information            | Runtime/application memory                  |
| Intended for information retrieval           | Stores `MemoryRecord` objects               |
| May contain documents or datasets            | Uses keys, values, namespaces, and metadata |
| Retrieval behavior depends on implementation | Current memory API is implemented           |

BindAI currently exposes a concrete memory system through `Memory`, `MemoryRecord`, and memory providers.

Knowledge should not be described as an automatically available conversation-memory mechanism.

---

# Knowledge vs Workflow Variables

Workflow variables and knowledge would also serve different purposes.

| Workflow Variables           | Knowledge                                      |
| ---------------------------- | ---------------------------------------------- |
| Runtime execution data       | External/reference information                 |
| Created during execution     | Exists independently of a particular execution |
| Used to coordinate execution | Intended for information retrieval             |
| Temporary application state  | Depends on the implemented knowledge system    |

Do not use workflow variables as a substitute for a knowledge system unless the application explicitly requires that behavior.

---

# Retrieval-Augmented Generation

Retrieval-Augmented Generation (RAG) is a common architecture for connecting external information to a language model.

A typical RAG system looks like:

```text
User Question

↓

Retrieve Relevant Information

↓

Build Model Context

↓

Language Model

↓

Response
```

This is a useful architectural pattern, but it should not be presented as BindAI's current execution pipeline unless the corresponding retrieval implementation exists in the project.

---

# Knowledge Sources

Potential knowledge sources in an agentic application include:

* Markdown files
* PDFs
* databases
* APIs
* websites
* internal documentation
* object storage
* vector databases

These are examples of possible integrations, not a list of currently supported BindAI knowledge providers.

The documentation should be updated as each source becomes an actual supported feature.

---

# Retrieval

A retrieval system generally selects relevant information rather than sending an entire data collection to the language model.

For example:

```text
Question

↓

Retriever

↓

Relevant Records

↓

Language Model
```

The exact retrieval strategy depends on the implementation.

Possible approaches include:

* keyword search
* metadata filtering
* full-text search
* vector similarity
* hybrid retrieval

Only implemented retrieval mechanisms should be documented as BindAI features.

---

# Semantic Search

Semantic search commonly uses embeddings to find information based on meaning rather than exact wording.

For example:

```text
Question:
How do I recover my account?

Document:
Credential recovery procedure
```

An embedding-based retrieval system may identify these as related even though the wording differs.

This describes a general retrieval technique and should not be interpreted as confirmation that BindAI currently provides an embedding or semantic-search API.

---

# Knowledge in the Execution Pipeline

Knowledge retrieval should only be shown as part of the BindAI execution pipeline once the framework actually performs that retrieval.

A generic architecture is:

```text
User Input

↓

Knowledge Retrieval

↓

Model Request

↓

Model Response
```

If BindAI does not currently perform those retrieval steps automatically, documentation should not claim that it does.

---

# Knowledge and Memory

The distinction is especially important when documenting the current project.

Memory is currently represented by concrete APIs such as:

```python
from bindai import Memory
from bindai import MemoryRecord
```

Memory records can be stored, retrieved, searched, deleted, and cleared.

For example:

```python
memory.set(
    MemoryRecord(
        key="company",
        value="Acme",
        namespace="user-123",
    )
)
```

Knowledge should remain a separate concept unless and until a concrete knowledge abstraction is implemented.

---

# Knowledge in Applications

Applications can implement their own external-information workflow today using the framework's existing primitives where appropriate.

For example, an application could:

```text
External Data Source

↓

Application Logic

↓

Tool

↓

Agent

↓

Model
```

A tool can retrieve information from an external system and return the result to the agent.

This is different from claiming that BindAI already provides a dedicated Knowledge or RAG subsystem.

---

# Tools vs Knowledge

Tools and knowledge should also be distinguished.

A tool is an executable Python function that BindAI can invoke.

For example:

```python
from bindai import tool


@tool
def get_document(document_id: str) -> str:
    ...
```

The tool can retrieve information from an external system.

A dedicated knowledge system would provide a higher-level abstraction around storing, indexing, retrieving, or searching external information.

Unless that abstraction exists in the current implementation, external retrieval should be documented as a tool/application integration rather than as a built-in Knowledge feature.

---

# Current Documentation Rule

When documenting Knowledge, follow the same rule used throughout the BindAI documentation:

> Document implemented APIs and behavior, not planned architecture.

In particular, do not describe the following as currently supported unless they exist in the source code:

* `Knowledge`
* `use_knowledge()`
* automatic knowledge retrieval
* document loaders
* RAG pipelines
* embedding generation
* vector indexes
* semantic retrieval
* knowledge providers
* automatic document ingestion

These can be documented later when they become actual project features.

---

# Best Practices

When adding Knowledge documentation:

* Verify the public API in the installed package.
* Verify classes and functions against the source code.
* Document actual providers rather than planned providers.
* Separate implemented functionality from roadmap items.
* Avoid describing generic RAG architecture as framework behavior.
* Document retrieval behavior only when it is implemented.
* Prefer executable examples that work against the current package.
* Update this documentation as new knowledge features are implemented.

---

# Summary

Knowledge is the architectural concept used to connect agents with external information.

However, BindAI documentation should distinguish this concept from implemented framework functionality.

The current documentation should therefore avoid promising a dedicated Knowledge or RAG subsystem until the corresponding APIs and execution behavior are present in the project.

When those features are implemented, this document can be expanded to cover their concrete abstractions, providers, retrieval APIs, integrations, and execution lifecycle.

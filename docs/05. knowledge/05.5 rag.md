# Retrieval-Augmented Generation (RAG)

Retrieval-Augmented Generation (RAG) is an architecture that combines information retrieval with language model generation.

Instead of relying only on a model's internal knowledge, a RAG system retrieves relevant external information and provides it to the language model as additional context.

RAG is commonly used for applications that need to answer questions using external documents, databases, or other knowledge sources.

> **Current status:** RAG is an architectural concept and is not documented here as an implemented public BindAI feature unless the corresponding Knowledge, Retriever, embedding, and agent-integration APIs are present in the current project.

---

# What is RAG?

RAG combines two main operations:

1. **Retrieval** — finding relevant external information.
2. **Generation** — using that information to produce a response.

Conceptually:

```text
User Question

↓

Retrieve Relevant Information

↓

Language Model

↓

Answer
```

The retrieved information provides additional context for the language model.

---

# Why Use RAG?

Language models have limitations when working with external or application-specific information.

For example, a model may not have access to:

* private company documentation
* internal policies
* application-specific data
* recently updated information
* proprietary technical documentation

A retrieval system can provide this information at runtime.

---

# Typical RAG Pipeline

A complete RAG system commonly contains several stages:

```text
Documents

↓

Chunking

↓

Embeddings

↓

Vector Storage

↓

Retriever

↓

Relevant Chunks

↓

Language Model

↓

Response
```

The exact architecture depends on the retrieval and storage technologies used by the application.

This pipeline describes a general RAG architecture and should not be interpreted as the current BindAI execution pipeline.

---

# Documents

The process usually begins with external information.

Examples include:

* Markdown documentation
* PDF files
* product manuals
* company policies
* support articles
* API documentation
* knowledge bases

The documents are processed before they can be retrieved efficiently.

---

# Chunking

Large documents are commonly divided into smaller sections called **chunks**.

For example:

```text
Employee Handbook

↓

Vacation Policy

↓

Benefits

↓

Code of Conduct
```

Smaller chunks allow retrieval systems to identify more focused pieces of information.

The appropriate chunking strategy depends on the document structure and retrieval system.

---

# Embeddings

Many RAG systems convert document chunks into numerical vectors called **embeddings**.

Conceptually:

```text
Document Chunk

↓

Embedding Model

↓

Vector Representation
```

A user query can also be converted into an embedding:

```text
User Question

↓

Embedding Model

↓

Query Vector
```

The retrieval system can then compare the query vector with stored document vectors.

---

# Vector Storage

RAG systems commonly store document embeddings in a vector-capable storage system.

Conceptually:

```text
Document Chunks

↓

Embeddings

↓

Vector Storage
```

Examples of technologies commonly used in RAG systems include:

* Chroma
* Qdrant
* Pinecone
* Weaviate
* Milvus
* pgvector

These are examples from the broader RAG ecosystem, **not claims that BindAI currently integrates with each provider**.

---

# Retrieval

At runtime, the user's question is passed to a retrieval system.

A typical flow is:

```text
User Question

↓

Query Processing

↓

Retriever

↓

Relevant Results
```

The selected results are then provided to the language model.

Retriever functionality is described separately in `05.4 retrievers.md`.

---

# Generation

After retrieval, the application combines the question with the retrieved context.

Conceptually:

```text
User Question

+

Retrieved Context

↓

Language Model

↓

Generated Response
```

The model can use the supplied context when producing its response.

---

# Example

Suppose an application has the following documents:

```text
Employee Handbook

IT Policies

Vacation Policy

Security Guide
```

The user asks:

```text
How many vacation days do employees receive?
```

A RAG system could:

1. process the question
2. retrieve the relevant section of the vacation policy
3. provide that section to the language model
4. generate an answer using the retrieved information

The model does not need the entire employee handbook in its prompt.

---

# Without Retrieval

Without an external retrieval step, the model receives only the information already provided to it.

```text
Question

↓

Language Model

↓

Response
```

If the required information is not available in the model's context, the model may not be able to provide an accurate answer.

---

# With Retrieval

A RAG system adds an external retrieval stage:

```text
Question

↓

Retrieve Relevant Information

↓

Language Model

↓

Response
```

The model can then use the retrieved information as additional context.

---

Model Request

The exact prompt structure depends on the application and agent framework.

# RAG vs Fine-Tuning

RAG and fine-tuning address different problems.

| RAG                                        | Fine-Tuning                                              |
| ------------------------------------------ | -------------------------------------------------------- |
| Supplies external information at runtime   | Changes model parameters                                 |
| Knowledge can be updated independently     | Requires a training process                              |
| Useful for changing factual information    | Useful for behavior, style, or specialized task patterns |
| Does not require retraining the base model | Requires training/fine-tuning                            |

The two approaches can also be used together.

# Best Practices

When implementing a RAG system:

* Keep source documents current.
* Remove obsolete information.
* Use meaningful document chunks.
* Use the same embedding model for indexing and querying.
* Retrieve only relevant context.
* Avoid unnecessarily large prompts.
* Use metadata filtering when appropriate.
* Evaluate retrieval quality independently from generation quality.
* Monitor incorrect or missing retrievals.
* Keep retrieval and generation responsibilities separate.

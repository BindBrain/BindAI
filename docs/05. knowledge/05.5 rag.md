# Retrieval-Augmented Generation (RAG)

Retrieval-Augmented Generation (RAG) combines information retrieval with language-model generation.

Instead of relying only on a model's built-in knowledge, a RAG system retrieves relevant external information and supplies it as context during generation.

BindAI provides the Knowledge, embedding, retrieval, reranking, and agent-integration components required to build RAG applications.

---

# What Is RAG?

RAG combines two primary operations:

1. **Retrieval** — finding relevant external information.
2. **Generation** — using that information to produce a response.

A simplified flow is:

```text id="x7k2qm"
User Question
      |
      v
Knowledge Retrieval
      |
      v
Relevant Context
      |
      v
Language Model
      |
      v
Response
```

The retrieval stage provides information that may not be contained in the model's built-in knowledge.

---

# Why Use RAG?

Language models do not automatically have access to every application's private or current information.

Examples include:

* Company documentation
* Internal policies
* Product documentation
* Technical manuals
* Application-specific information
* Frequently changing reference data
* Domain-specific knowledge

RAG allows an application to retrieve relevant information at runtime.

# Chunking

Large documents are commonly divided into smaller chunks.

For example:

```text id="w5r9xk"
Employee Handbook
       |
       v
+----------------------+
| Vacation Policy      |
+----------------------+
| Benefits             |
+----------------------+
| Security Policy      |
+----------------------+
| Code of Conduct      |
+----------------------+
```

Chunking allows retrieval to select relevant sections rather than returning an entire document.

Chunk size and overlap should be selected according to the source material and retrieval requirements.

---

# Embeddings

Vector-based RAG commonly uses embeddings to represent document chunks numerically.

```text id="c2m7fs"

      |

      |
      v

```

BindAI provides an embedding abstraction with current implementations including:

* `RandomEmbeddingProvider`
* `OpenAIEmbeddingProvider`

The local/deterministic provider is useful for development and testing, while the OpenAI provider can generate hosted semantic embeddings.

---

# Query Embeddings

At runtime, the user's question can also be converted into an embedding.

```text id="v8q3md"
User Question
      |
      v
Embedding Provider
      |
      v
Query Vector
      |
      v
Vector Retrieval
```

The query and indexed document vectors must be compatible.

In particular, applications should use compatible embedding models and vector dimensions for indexing and querying.

---

# Vector Retrieval

Vector retrieval compares the query embedding against stored document or chunk embeddings.

```text id="p4y7nz"
Query Vector
     |
     v
Vector Retrieval
     |
     +---- Chunk A
     |
     +---- Chunk B
     |
     +---- Chunk C
     |
     v
Relevant Results
```

This allows semantic relationships to be identified even when the query and document use different wording.

---

# BM25 Retrieval

RAG does not require vector retrieval exclusively.

BindAI also provides BM25 retrieval for lexical matching.

```text id="e6x2qr"
Query
  |
  v
BM25
  |
  v
Relevant Chunks
```

BM25 can be particularly useful for exact terminology, names, identifiers, error messages, and technical vocabulary.

# Hybrid Retrieval

BindAI also supports hybrid retrieval.

Hybrid retrieval combines lexical and semantic signals:

```text id="j7m4pc"
                    Query

             +--------+--------+

             v                 v

             +--------+--------+
                      |

                      |
                      v

                      |
                      v
```

Hybrid retrieval can be useful when both exact terms and semantic similarity are important.

# Metadata Filtering

RAG systems can use metadata to restrict retrieval.

For example:

```text id="s3x8nv"

version = 2.0

```

A retrieval flow can then become:

```text id="m8p2cz"

    |
    v
Metadata Filter
    |
    v

    |
    v
Retriever
    |
    v

```

Metadata filtering is useful for document categories, versions, tenant boundaries, and application-defined scopes.

It should not be treated as a replacement for application-level authorization.

# Reranking

Initial retrieval can produce multiple candidate results.

Reranking can then improve their ordering.

```text id="q6n4yb"
Query
  |
  v
Initial Retrieval
  |
  v
Candidate Results
  |
  v
Reranker
  |
  v
Final Results
```

BindAI provides a reranker abstraction and lexical reranking implementation.

Reranking can be combined with vector, BM25, or hybrid retrieval.

# Retrieval Context

The purpose of retrieval in RAG is to provide relevant context to the model.

A simplified flow is:

```text id="d9w3fk"
User Question
      |
      v
Retriever
      |
      v
Relevant Knowledge
      |
      v
Model Context
      |
      v
Language Model
```

The goal is not to retrieve as much information as possible.

The goal is to retrieve information that is useful for answering the current question.

---

# Generation

Conceptually:

```text id="h2k7mv"
    Model Request
        |
        v
   Language Model
```

BindAI's agent execution layer is responsible for interacting with the configured model provider.

Knowledge retrieval supplies relevant external context to that execution.

# Example RAG Scenario

Suppose an application contains:

```text id="k9p4xs"
Product Documentation
├── Installation Guide
├── Configuration Guide
├── API Reference
└── Troubleshooting Guide
```

A user asks:

```text id="q3m8vf"
How do I configure authentication?
```

A RAG system can:

1. Interpret the query.
2. Search the Knowledge system.
3. Retrieve relevant configuration documentation.
4. Filter or rerank the results if configured.
5. Supply the relevant context to the agent.
6. Generate a response using the retrieved information.

The entire documentation collection does not need to be supplied to the model.

---

# RAG and Memory

RAG and Memory solve different problems.

| RAG / Knowledge                                    | Memory                                                         |
| -------------------------------------------------- | -------------------------------------------------------------- |
| Retrieves external/reference information           | Retains application or agent information                       |
| Uses documents and searchable knowledge            | Uses `MemoryRecord` objects                                    |
| Focuses on relevant external context               | Focuses on stored application state                            |
| Commonly used for documentation and reference data | Commonly used for preferences, state, and retained information |

An agent can use both.

```text id="n6x2qr"
                    Agent
                      |
          +-----------+-----------+
          |                       |
          v                       v
       Memory                  Knowledge
          |                       |
          v                       v
   Retained Context        Retrieved Context
          |                       |
          +-----------+-----------+
                      |
                      v
                Model Request
```

# RAG and Tools

Tools and RAG also serve different purposes.

Tools execute operations:



An agent can use both systems in the same application.

A tool can also provide live information that complements static Knowledge.

Important factors include:

* Source quality
* Parsing quality
* Chunking strategy
* Metadata quality
* Embedding model
* Retrieval strategy
* Filtering
* Reranking
* Query interpretation
* Model context construction

A useful diagnostic flow is:

```text id="m2q8zn"
Poor Answer
    |
    v

    |
   / \
 No   Yes
 |     |
 v     v
Check   Check

```

Retrieval quality should therefore be evaluated separately from model-generation quality.

# Evaluating Retrieval

A useful RAG evaluation set contains realistic questions with known relevant information.

For example:

```text id="p4k7xs"
Question:
How do I configure authentication?

Expected:
Authentication configuration documentation
```

Evaluation should consider:

* Whether the correct information was retrieved
* Whether irrelevant information was retrieved
* Whether important context was omitted
* Retrieval latency
* Final answer quality

This makes it easier to identify whether an issue belongs to ingestion, retrieval, reranking, or generation.

---

# RAG and Hallucination

RAG can reduce reliance on unsupported model knowledge by supplying relevant external context.

However, retrieval does not guarantee factual responses.

Possible failure modes include:

* Incorrect retrieval
* Missing information
* Outdated documents
* Poor chunking
* Ambiguous queries
* Incorrect interpretation of retrieved context
* Model-generated claims not supported by the retrieved information

Applications should therefore evaluate both retrieval and generation.

---

# Source Provenance

RAG applications should preserve information about where retrieved content originated.

Useful provenance information can include:

```text id="j8m4vc"
Document ID
Source
Section
Version
Metadata
```

This makes retrieved information easier to inspect and can support future citation features.

Applications should preserve provenance during ingestion and retrieval whenever practical.

---

# RAG and Security

RAG systems can expose private knowledge if retrieval boundaries are not enforced correctly.

Applications should consider:

* Tenant isolation
* Access control
* Metadata filtering
* Source permissions
* Secure storage
* Data retention
* Document deletion
* Query authorization

Retrieved Knowledge should only contain information that the requesting user is authorized to access.

Metadata filtering can help enforce retrieval scopes but should not be treated as the only authorization mechanism.

# RAG vs Fine-Tuning

RAG and fine-tuning address different problems.

| RAG                                        | Fine-Tuning                                               |
| ------------------------------------------ | --------------------------------------------------------- |
| Supplies external information at runtime   | Changes model behavior through training                   |
| Knowledge can be updated independently     | Model must be retrained or fine-tuned                     |
| Useful for changing factual information    | Useful for behavior, style, and specialized task patterns |
| Does not require retraining the base model | Requires a training/fine-tuning process                   |

The two approaches can also be combined.

Production RAG systems should consider:

* Document ingestion reliability
* Source freshness
* Chunking quality
* Embedding compatibility
* Retrieval accuracy
* Metadata design
* Access control
* Tenant isolation
* Reranking

* Model context limits
* Monitoring
* Evaluation
* Data retention

A production RAG system should be treated as a complete pipeline rather than only a vector search feature.

---

# Best Practices

* Keep source documents current.
* Use meaningful document chunks.
* Preserve source metadata and provenance.
* Use compatible embedding models for indexing and querying.
* Keep vector dimensions consistent.
* Choose retrieval strategies based on actual query patterns.
* Use hybrid retrieval when both lexical and semantic signals are valuable.
* Use metadata filtering for retrieval scope.
* Use reranking when candidate ordering needs additional refinement.
* Retrieve only the context needed for the current question.
* Evaluate retrieval independently from generation.
* Test with realistic documents and questions.
* Monitor retrieval and generation latency separately.
* Enforce authorization before exposing retrieved information.
* Reprocess knowledge when source content or embedding models change.
* Avoid treating retrieved context as automatically trustworthy.
* Keep ingestion and runtime retrieval as separate concerns where practical.

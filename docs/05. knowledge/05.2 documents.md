# Documents

Documents are a common source of external information for agent applications.

BindAI currently provides the tool abstraction that can be used to expose document-related operations to an agent. A dedicated `Document` or document-ingestion API should only be documented when that functionality is implemented by the framework.

---

# Documents and BindAI

An application may need an agent to work with:

* Markdown files
* text files
* PDFs
* API documentation
* product manuals
* knowledge-base content
* application-generated documents
* other external information

These sources can be accessed through application logic or tools.

For example, a tool can read a file and return its contents to the agent.

```python
from pathlib import Path

from bindai import tool


@tool
def read_file(path: str) -> str:
    return Path(path).read_text()
```

The agent can then invoke the tool when the user's request requires access to the file.

---

# Documents as Tool Data

A document does not need to be a special framework object to be useful to an agent.

An application can expose document operations through a tool:

```text
User

↓

Agent

↓

Language Model

↓

Document Tool

↓

Document Content

↓

Language Model

↓

Final Response
```

This uses BindAI's existing tool-calling mechanism rather than requiring a dedicated document subsystem.

---

# Reading Documents

For simple local files, normal Python file operations can be wrapped as tools.

```python
from pathlib import Path

from bindai import tool


@tool
def read_document(path: str) -> str:
    """
    Read a text document.
    """
    return Path(path).read_text()
```

The tool returns the document content as its normal Python return value.

BindAI wraps that return value in a `ToolResult`.

---

# Tool Results

Tool execution currently produces a `ToolResult` containing:

* `success`
* `value`
* `error`

For example, if a document-reading tool returns text:

```python
result = read_document(
    "docs/example.md",
)
```

The tool execution result is represented internally as a successful `ToolResult` whose `value` contains the returned document content.

If the function raises an exception, the `Tool` implementation captures the exception and returns a failed result.

---

# Document Processing

Applications may process documents before providing their contents to an agent.

For example:

```text
Document

↓

Application Processing

↓

Relevant Content

↓

Tool Result

↓

Agent
```

Processing may include application-specific operations such as:

* extracting text
* filtering content
* converting formats
* selecting relevant sections
* parsing structured data

These operations are not currently represented by a dedicated BindAI document-processing API.

---

# Document Search

Applications can also expose document search through tools.

For example:

```python
from bindai import tool


@tool
def search_documents(query: str) -> str:
    """
    Search the application's document store.
    """
    # Application-specific search implementation.
    ...
```

The search implementation belongs to the application.

BindAI provides the mechanism for exposing the function to the model; it does not currently define a built-in document-search index in the APIs verified for this project.

---

# Documents and Memory

Documents and Memory solve different problems.

| Documents                             | Memory                                                           |
| ------------------------------------- | ---------------------------------------------------------------- |
| External application information      | Stored memory records                                            |
| Usually supplied by an application    | Managed through `Memory`                                         |
| Can be accessed through tools         | Supports `set`, `get`, `search`, `delete`, `exists`, and `clear` |
| Storage format depends on application | Uses `MemoryRecord` objects                                      |

Memory is currently a concrete BindAI subsystem.

Documents are currently better treated as application data that can be exposed through tools unless a dedicated document API is added.

---

# Documents and Workflow Variables

Workflow state and document content are also different concepts.

| Workflow State                      | Documents                               |
| ----------------------------------- | --------------------------------------- |
| Runtime execution data              | External/reference information          |
| Used to coordinate execution        | Used as application data                |
| Execution-specific                  | Can exist independently of an execution |
| Managed by the workflow/application | Storage depends on the application      |

A workflow can pass document-related information through its existing execution mechanisms without requiring a dedicated `Document` object.

---

# Document Collections

Applications may organize documents into collections:

```text
Documentation

├── Installation

├── API Reference

├── Tutorials

├── FAQ

└── Troubleshooting
```

This is an application-level organizational pattern.

BindAI's current verified APIs do not establish a built-in document collection abstraction.

---

# Metadata

Applications may associate metadata with documents.

For example:

```text
Title: API Reference
Category: Documentation
Version: 2.0
```

If document information is stored through BindAI Memory, `MemoryRecord` itself supports metadata:

```python
from bindai import MemoryRecord


record = MemoryRecord(
    key="api-reference",
    value="...",
    metadata={
        "category": "documentation",
        "version": "2.0",
    },
)
```

However, this should not be confused with a dedicated BindAI `Document` model.

---

# Document Chunking

Large documents often need to be divided into smaller sections before being supplied to a language model.

A generic application architecture might be:

```text
Large Document

↓

Application Chunking

↓

Relevant Sections

↓

Tool

↓

Agent
```

Chunking is an application-level strategy unless a dedicated BindAI chunking API is implemented.

---

# Retrieval-Augmented Generation

A document-based RAG system commonly follows:

```text
Question

↓

Document Retrieval

↓

Relevant Content

↓

Language Model

↓

Answer
```

BindAI can participate in such an architecture through tools that perform the retrieval.

The framework documentation should not claim that BindAI currently performs document ingestion, chunking, indexing, embeddings, or automatic retrieval unless those APIs are implemented.

---

# Supported Formats

There is currently no verified BindAI `Document` loader API establishing a framework-level list of supported formats.

Applications can nevertheless implement tools for whatever formats they need.

For example:

```text
Markdown
PDF
DOCX
HTML
JSON
CSV
Plain Text
```

Support for these formats depends on the application's Python libraries and document-processing implementation.

---

# Updating Documents

When documents change, an application is responsible for updating its document source or retrieval system.

A typical application architecture might be:

```text
New Document

↓

Application Processing

↓

Storage / Search System

↓

Document Tool

↓

Agent
```

There is currently no verified BindAI document-index lifecycle such as:

```text
Load → Chunk → Index → Rebuild
```

so that lifecycle should not be presented as built-in framework behavior.

---

# Best Practices

* Treat documents as application data unless a dedicated document API exists.
* Use tools to expose document-reading or search operations to agents.
* Keep document-processing logic outside the agent when deterministic processing is required.
* Keep tool descriptions clear so the model knows when document access is appropriate.
* Handle missing or unreadable documents gracefully.
* Keep large document results reasonably scoped.
* Separate document storage from agent logic.
* Document application-specific document formats separately from BindAI's core APIs.
* Do not document planned document-ingestion or RAG features as currently supported.

---

# Current Project Status

The current verified BindAI package exposes tools as ordinary Python functions decorated with `@tool`.

For document access, the supported pattern can therefore be expressed as:

```text
Document Source

↓

Python Function

↓

@tool

↓

Agent

↓

Language Model
```

A dedicated document abstraction, document loader, chunking pipeline, index, or automatic RAG subsystem should be documented here only after it has been implemented and verified in the project.

---

# Summary

Documents can provide valuable external information to BindAI agents, but the current framework should not be documented as having a dedicated document or RAG subsystem unless that functionality exists in the implementation.

Today, applications can expose document operations through BindAI tools. The tool can read, search, parse, or otherwise process documents and return the resulting data to the agent.

This keeps the documentation aligned with the actual project while leaving room to document a dedicated document and knowledge layer when those features are implemented.

# Tool Execution

BindAI tools are ordinary Python functions wrapped by the `@tool` decorator.

When an agent decides to use a tool, BindAI looks up the registered tool and executes the underlying Python function with the arguments supplied to it.

The current tool execution model is intentionally simple and predictable.

---

# How Tool Execution Works

The basic execution flow is:

```text
User
  │
  ▼
Agent
  │
  ▼
Language Model
  │
  ▼
Tool Request
  │
  ▼
Tool Registry
  │
  ▼
Tool Executor
  │
  ▼
Python Function
  │
  ▼
ToolResult
  │
  ▼
Agent
  │
  ▼
Final Response
```

The `ToolExecutor` is responsible for finding the requested tool and invoking it.

---

# Creating a Tool

Create a tool by decorating a Python function with `@tool`.

```python
from bindai import tool


@tool
def greet(name: str) -> str:
    return f"Hello, {name}!"
```

The decorator converts the function into a BindAI `Tool`.

---

# Tool Objects

The underlying `Tool` object contains three main pieces of information:

```python
Tool(
    name="greet",
    description="",
    function=greet,
)
```

The constructor is:

```python
Tool(
    name: str,
    description: str,
    function: Callable,
)
```

The tool therefore keeps:

* A name
* A description
* The Python function that performs the operation

---

# Tool Names

By default, the tool name comes from the Python function name.

```python
@tool
def get_weather(city: str):
    ...
```

The resulting tool is named:

```text
get_weather
```

You can provide an explicit name when necessary.

```python
@tool(name="weather")
def get_weather(city: str):
    ...
```

The registered tool is now named:

```text
weather
```

Explicit names are useful when you want the model-facing tool name to differ from the Python function name.

---

# Tool Descriptions

By default, the tool description comes from the function's docstring.

```python
@tool
def get_weather(city: str):
    """
    Return the weather for a city.
    """
    ...
```

You can also provide an explicit description.

```python
@tool(
    name="weather",
    description="Return the current weather for a city.",
)
def get_weather(city: str):
    ...
```

Clear descriptions help identify the purpose of a tool.

---

# Registering a Tool

Tools can be registered directly on an agent.

```python
agent.tool(get_weather)
```

A tool can also be registered with an `AgentBuilder`.

```python
from bindai import AgentBuilder

agent = (
    AgentBuilder()
    .tools(get_weather)
    .build()
)
```

Multiple tools can be registered together:

```python
agent = (
    AgentBuilder()
    .tools(
        get_weather,
        search,
        calculate,
    )
    .build()
)
```

---

# The Tool Registry

Registered tools are stored in a `ToolRegistry`.

The registry is responsible for finding a tool by name.

Conceptually:

```text
Tool name
    │
    ▼
ToolRegistry
    │
    ▼
Tool
```

When a tool name is requested, the registry returns the corresponding `Tool`.

---

# Tool Executor

BindAI uses `ToolExecutor` to execute registered tools.

Its constructor accepts a `ToolRegistry`:

```python
ToolExecutor(registry)
```

The execution method is:

```python
executor.execute(
    tool_name,
    *args,
    **kwargs,
)
```

For example:

```python
result = executor.execute(
    "get_weather",
    "Tokyo",
)
```

The executor looks up the tool and calls it with the supplied arguments.

---

# What Happens During Execution?

Internally, the executor follows a simple process:

```text
Requested Tool Name
        │
        ▼
Look up ToolRegistry
        │
        ├── Tool found ──────► Execute function
        │                           │
        │                           ▼
        │                       ToolResult
        │
        └── Tool missing ────► Failed ToolResult
```

The current implementation does not require an `ExecutionContext` to execute a tool.

---

# Tool Arguments

Arguments are passed directly to the underlying Python function.

For example:

```python
@tool
def add(a: int, b: int) -> int:
    return a + b
```

The executor can invoke it as:

```python
result = executor.execute(
    "add",
    10,
    20,
)
```

The underlying function receives:

```python
add(10, 20)
```

Keyword arguments are also supported:

```python
result = executor.execute(
    "add",
    a=10,
    b=20,
)
```

The function receives:

```python
add(
    a=10,
    b=20,
)
```

---

# Tool Results

Tool execution returns a `ToolResult`.

A successful execution may look like:

```python
ToolResult(
    success=True,
    output=30,
    error=None,
)
```

The result provides a consistent way to represent the outcome of a tool execution.

---

# Unknown Tools

If the executor receives a tool name that is not registered, it does not attempt to call a function.

Instead, it returns a failed `ToolResult`.

Example:

```python
result = executor.execute(
    "unknown_tool",
)
```

Result:

```python
ToolResult(
    success=False,
    error="Unknown tool 'unknown_tool'",
)
```

This prevents an invalid tool name from being executed.

---

# Tool Errors

The executor delegates execution to the registered tool.

For expected application-level failures, tools can return an appropriate value or handle the failure themselves.

For example:

```python
from bindai import tool


@tool
def divide(a: float, b: float):
    if b == 0:
        return "Division by zero is not allowed."

    return a / b
```

Keep expected failures understandable to the rest of the application.

---

# Tool Context

The current BindAI tool API does **not** expose an `ExecutionContext` or `context.variables` interface through the public `bindai` package.

Therefore, tools should use explicit function parameters for the information they require.

For example:

```python
@tool
def get_customer(customer_id: int):
    ...
```

Instead of relying on an undocumented global context.

This makes tool interfaces explicit and easier to test.

---

# Passing Application State

If a tool needs application-specific state, pass the required information explicitly.

```python
@tool
def create_report(
    customer_id: int,
    format: str,
):
    ...
```

The agent or application can provide the required values when invoking the tool.

For more advanced dependency-management patterns, use normal Python mechanisms rather than assuming a hidden execution context.

---

# Avoid Global State

Avoid storing request-specific information in global variables.

Avoid:

```python
CURRENT_CUSTOMER = None
```

Prefer explicit parameters:

```python
@tool
def get_customer(customer_id: int):
    ...
```

Explicit inputs keep tools easier to test and reason about.

---

# Tool Execution and Workflows

Tools can be used as part of larger application workflows.

A workflow can provide the values required by a tool and use the resulting `ToolResult` in later processing.

The important distinction is:

* **Tool parameters** represent the inputs required by the function.
* **ToolResult** represents the result of execution.
* **Workflow state** belongs to the workflow implementation rather than an implicit `ExecutionContext` API.

---

# Tool Lifecycle

A complete tool lifecycle is:

```text
Define Function
      │
      ▼
@tool Decorator
      │
      ▼
Tool Object
      │
      ▼
Register Tool
      │
      ▼
ToolRegistry
      │
      ▼
ToolExecutor
      │
      ▼
Python Function
      │
      ▼
ToolResult
```

This model keeps tool execution independent from the specific language model provider.

---

# Complete Example

```python
from bindai import AgentBuilder, tool


@tool(
    name="multiply",
    description="Multiply two integers.",
)
def multiply(
    a: int,
    b: int,
) -> int:
    return a * b


agent = (
    AgentBuilder()
    .model("openai:gpt-5")
    .instructions("You are a helpful assistant.")
    .tools(multiply)
    .build()
)

result = agent.run("What is 14 × 9?")

if result.success:
    print(result.output)
else:
    print(result.error)
```

The tool is registered with the agent and becomes available during execution.

---

# Best Practices

* Use explicit function parameters for tool inputs.
* Add Python type hints.
* Give tools clear names.
* Write concise descriptions.
* Use docstrings when an explicit description is not required.
* Keep tools focused on one responsibility.
* Avoid request-specific global state.
* Handle expected application failures clearly.
* Keep tool outputs predictable.
* Do not depend on undocumented execution-context APIs.

---

# Summary

BindAI's current tool execution model is intentionally straightforward.

A Python function is converted into a `Tool` using `@tool`, registered with an agent, stored in a `ToolRegistry`, and executed through `ToolExecutor`.

The executor passes arguments directly to the underlying Python function and returns a `ToolResult`.

For the current API, tools should use explicit parameters rather than relying on an `ExecutionContext` or `context.variables` abstraction.

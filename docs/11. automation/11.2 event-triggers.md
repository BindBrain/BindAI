# Event Triggers

Event triggers allow BindAI automation logic to react when an event is published through an `EventBus`.

The current implementation provides a lightweight `EventTrigger` abstraction. An `EventTrigger` subscribes to one named event and calls a target function whenever that event is published.

This makes event-driven automation possible without coupling the trigger to a specific agent, workflow, or application object.

For background execution, an event-trigger target can invoke an `AutomationWorker`. Event triggering and background execution remain separate responsibilities.

---

## EventTrigger

The implementation is located at:

```text
packages/bindai-automation/src/bindai_automation/event_trigger.py
```

`EventTrigger` extends the base `Trigger` class and requires three values:

- an `EventBus`
- an event name
- a callable target

Conceptually:

```python
from bindai_automation import EventTrigger

trigger = EventTrigger(
    bus=event_bus,
    event_name="agent.finished",
    target=handle_event,
)
```

The target receives the published `Event` object.

```python
def handle_event(event):
    print(event.name)
    print(event.payload)
```

The trigger does not create or own the event bus. It subscribes to an existing bus supplied by the application.

---

## Trigger Lifecycle

Every trigger inherits from the base `Trigger` abstraction.

The base class provides:

```python
trigger.enable()
trigger.disable()
```

It also defines:

```python
trigger.attach()
trigger.detach()
```

`EventTrigger` implements these lifecycle operations by subscribing and unsubscribing from its configured `EventBus`.

### Attaching

Calling:

```python
trigger.attach()
```

subscribes the trigger to its configured event.

After attachment, matching events are delivered to the trigger.

Calling `attach()` more than once does not create duplicate subscriptions. The implementation tracks whether the trigger is already attached.

### Detaching

Calling:

```python
trigger.detach()
```

removes the trigger's subscription from the event bus.

Calling `detach()` when the trigger is already detached is safe.

---

## Enabling and Disabling

Triggers are enabled by default.

A trigger can be temporarily disabled:

```python
trigger.disable()
```

When disabled, the trigger ignores published events.

It can later be enabled again:

```python
trigger.enable()
```

The trigger remains attached to the event bus while disabled; it simply does not invoke its target.

This allows applications to pause an attached trigger without rebuilding its subscription.

---

## Event Bus

`EventTrigger` does not create its own event system.

Instead, it receives an existing `EventBus`:

```python
trigger = EventTrigger(
    bus=event_bus,
    event_name="some.event",
    target=handle_event,
)
```

The event bus is responsible for publishing events and dispatching them to subscribed handlers.

This keeps event triggers independent from the source of the events.

For example, an event bus can belong to an `ExecutionContext`:

```python
from bindai_core.context import ExecutionContext

context = ExecutionContext()

trigger = EventTrigger(
    bus=context.events,
    event_name="some.event",
    target=handle_event,
)

trigger.attach()
```

The trigger only depends on the `EventBus` interface. It does not need to know which component created the event bus.

---

## Event Names

`EventTrigger` subscribes to the event name supplied when it is created:

```python
trigger = EventTrigger(
    bus=event_bus,
    event_name="agent.finished",
    target=handle_event,
)
```

The trigger subscribes through the event bus:

```python
bus.subscribe(event_name, handler)
```

Therefore, the trigger follows the event naming and dispatch behavior of the configured `EventBus`.

Use event names that correspond to events actually published by the application.

BindAI currently publishes structured events for areas including:

- application lifecycle
- agent execution
- workflow execution
- workflow nodes
- human tasks
- model requests and responses
- tool execution
- memory operations
- MCP connection lifecycle

The exact event names should be based on the events published by the connected BindAI components.

---

## Event Objects

The target receives the complete `Event` instance:

```python
def handle_event(event):
    print(event.name)
    print(event.id)
    print(event.timestamp)
    print(event.payload)
```

This allows the target to inspect the event's structured information rather than receiving only a raw payload.

The exact payload fields depend on the specific event being published.

---

## Example with an Execution Context

A simple event-driven setup can use the event bus owned by an `ExecutionContext`:

```python
from bindai_core.context import ExecutionContext
from bindai_automation import EventTrigger


def handle_agent_event(event):
    print(f"Received: {event.name}")
    print(event.payload)


context = ExecutionContext()

trigger = EventTrigger(
    bus=context.events,
    event_name="agent.finished",
    target=handle_agent_event,
)

trigger.attach()
```

When a matching event is published through `context.events`, the trigger calls `handle_agent_event`.

When the trigger is no longer required:

```python
trigger.detach()
```

---

## Trigger Targets

The target must be a callable that accepts an `Event`:

```python
def handle_event(event):
    ...
```

Callable objects can also be used:

```python
class EventHandler:
    def __call__(self, event):
        print(event.name)


handler = EventHandler()

trigger = EventTrigger(
    bus=event_bus,
    event_name="agent.finished",
    target=handler,
)
```

The current `EventTrigger` implementation does not impose a special target interface beyond the callable receiving an `Event`.

---

## Multiple Triggers

Multiple triggers can subscribe to the same event bus.

For example:

```python
trigger_a = EventTrigger(
    bus=event_bus,
    event_name="agent.finished",
    target=handle_agent_finished,
)

trigger_b = EventTrigger(
    bus=event_bus,
    event_name="workflow.finished",
    target=handle_workflow_finished,
)

trigger_a.attach()
trigger_b.attach()
```

Each trigger listens for its configured event name.

This allows different automation actions to react to different events while sharing the same event source.

---

## Multiple Triggers for One Event

Multiple triggers can also subscribe to the same event:

```python
first = EventTrigger(
    bus=event_bus,
    event_name="agent.finished",
    target=first_handler,
)

second = EventTrigger(
    bus=event_bus,
    event_name="agent.finished",
    target=second_handler,
)

first.attach()
second.attach()
```

Both targets can receive the matching event according to the configured `EventBus` dispatch behavior.

---

## Trigger Lifecycle and Application Lifecycle

Triggers should normally be attached during application or automation initialization and detached when they are no longer required.

A typical lifecycle is:

```text
Create EventBus
      |
      v
Create EventTrigger
      |
      v
Attach trigger
      |
      v
Events are published
      |
      v
Trigger receives matching events
      |
      v
Target callable executes
      |
      v
Detach trigger
```

The trigger itself does not provide application lifecycle management.

The application is responsible for deciding when triggers should be created, attached, disabled, enabled, and detached.

---

## EventTrigger and Automation

An `EventTrigger` is a trigger mechanism. It does not itself define an automation workflow or persist automation state.

Its responsibility is intentionally small:

```text
EventBus
   |
   | matching event
   v
EventTrigger
   |
   | Event
   v
Target callable
```

If the target starts a larger automation process, that behavior belongs to the target or to the automation components it invokes.

This separation keeps event subscription independent from automation execution.

---

## EventTrigger and AutomationWorker

`EventTrigger` and `AutomationWorker` solve different problems.

`EventTrigger` determines **when** application logic should run:

```text
EventBus
   |
   v
EventTrigger
   |
   v
Target
```

`AutomationWorker` determines **how an automation definition is executed**:

```text
AutomationDefinition
   |
   v
AutomationWorker
   |
   v
AutomationRun
```

An application can combine them when an event should start a background automation.

For example:

```python
from bindai_automation import EventTrigger, AutomationWorker


worker = AutomationWorker()


def handle_event(event):
    worker.submit(
        automation,
        input=event.payload,
    )


trigger = EventTrigger(
    bus=event_bus,
    event_name="agent.finished",
    target=handle_event,
)

trigger.attach()
```

The conceptual flow is:

```text
EventBus
   |
   v
EventTrigger
   |
   v
Target Callable
   |
   v
AutomationWorker
   |
   v
AutomationDefinition
   |
   v
AutomationRun
```

The important distinction is that `EventTrigger` itself does **not** create a background worker.

If the target calls `AutomationWorker.submit()`, the application explicitly chooses background execution.

---

## AutomationWorker Execution Model

In BindAI v0.1, `AutomationWorker` provides both synchronous and background execution.

Synchronous execution:

```python
worker = AutomationWorker()

run = worker.run(
    automation,
    input={"message": "hello"},
)
```

Background execution:

```python
future = worker.submit(
    automation,
    input={"message": "hello"},
)

run = future.result()
```

The background worker uses an in-process `ThreadPoolExecutor`.

Conceptually:

```text
Application Process
       |
       +-- AutomationWorker
               |
               +-- Thread
               +-- Thread
               +-- Thread
```

The worker is therefore process-local.

It is not a separate worker service and does not provide distributed queue coordination.

---

## Background Event Handling

An event trigger can explicitly delegate work to an `AutomationWorker`:

```python
def handle_event(event):
    worker.submit(
        automation,
        input=event.payload,
    )
```

This produces:

```text
Event
  |
  v
EventBus
  |
  v
EventTrigger
  |
  v
Target
  |
  v
AutomationWorker
  |
  v
AutomationRun
```

This pattern is useful when the event handler should hand work to the in-process background executor rather than perform the entire automation directly inside the event handler.

The worker lifecycle remains the responsibility of the application:

```python
worker.shutdown()
```

It can also be used as a context manager:

```python
with AutomationWorker() as worker:
    worker.submit(automation)
```

---

## EventTrigger and Workflows

An event trigger can be used as the entry point for application logic that invokes a workflow.

For example:

```python
def handle_event(event):
    workflow.run(...)
```

The exact workflow invocation depends on how the application has configured its workflow and execution context.

`EventTrigger` itself does not contain workflow-specific logic.

The same principle applies when a trigger invokes another BindAI executable.

---

## EventTrigger and Agents

An event trigger can listen to an event bus associated with an execution context used by agent execution.

For example:

```python
context = ExecutionContext()

trigger = EventTrigger(
    bus=context.events,
    event_name="agent.finished",
    target=handle_event,
)

trigger.attach()
```

The important abstraction is the `EventBus`, not a hard-coded `agent.events` attribute.

Applications should pass the event bus that actually publishes the events they want to observe.

---

## EventTrigger and Connections

An event trigger can also invoke application logic that uses a BindAI Connection.

For example:

```text
EventBus
   |
   v
EventTrigger
   |
   v
Target
   |
   v
Connection
   |
   v
External Service
```

The automation package does not directly manage Connections.

Connection configuration and lifecycle remain the responsibility of the application or integration layer.

## Wildcard Events

The underlying `EventBus` supports wildcard subscriptions through the `"*"` event name.

For example:

```python
event_bus.subscribe("*", handle_all_events)
```

This is an `EventBus` capability rather than special behavior implemented by `EventTrigger`.

`EventTrigger` subscribes using the event name supplied to its constructor:

```python
self.bus.subscribe(
    self.event_name,
    self._handle_event,
)
```

Therefore, wildcard behavior should be understood as part of the configured `EventBus` semantics.

---

## Handler Execution

When a matching event is received, `EventTrigger` checks whether it is enabled:

```python
if not self.enabled:
    return
```

If the trigger is enabled, it invokes its target:

```python
self.target(event)
```

The current implementation does not add a separate retry, queue, persistence, or scheduling layer around the target call.

Those concerns belong to the surrounding application or automation architecture.

---

## Synchronous Event Dispatch

The underlying BindAI `EventBus` dispatches subscribed handlers synchronously.

Conceptually:

```text
publish(event)
      |
      v
EventTrigger
      |
      v
target(event)
```

`EventTrigger` itself does not create a background thread or process.

If the target calls `AutomationWorker.submit()`, background execution begins explicitly through the worker.

This distinction is important:

```text
EventTrigger
= event subscription and target invocation

AutomationWorker
= automation execution and background execution
```

The trigger should not be treated as a distributed job queue.

---

## Trigger Registry

Trigger registration and lookup are separate from the `EventTrigger` implementation.

`EventTrigger` itself does not maintain a global registry.

If an application uses `TriggerRegistry`, the registry is responsible for managing trigger instances while `EventTrigger` remains responsible for subscribing to and unsubscribing from its event source.

For example:

```python
from bindai_automation import TriggerRegistry

registry = TriggerRegistry()

registry.register(
    "agent-events",
    trigger,
)

registered = registry.get("agent-events")
```

Registering a trigger does not automatically attach it to its event source.

Attachment remains explicit:

```python
trigger.attach()
```

---

## Error Handling

`EventTrigger` does not wrap the target callable in its own retry or error-management mechanism.

The target is invoked directly:

```python
self.target(event)
```

The underlying `EventBus` isolates exceptions raised by event handlers and logs the failure rather than allowing one handler failure to prevent other subscribed handlers from being processed.

Applications should still handle expected failures at the appropriate application or automation layer.

For example:

```python
def handle_event(event):
    try:
        process_event(event)
    except Exception:
        log_failure(event)
```

Do not assume that `EventTrigger` automatically retries failed targets.

---

## Security Considerations

Event payloads may contain application data.

Targets should therefore treat incoming events as application input and validate or sanitize values when necessary.

Recommended practices include:

- validate event payloads before performing sensitive actions
- avoid exposing secrets through event payloads
- avoid logging credentials or tokens
- restrict which components can publish sensitive events
- keep event targets narrowly scoped
- use appropriate authorization before performing external actions

An event trigger should not be treated as an authorization boundary by itself.

When an event starts an automation that performs external side effects, the target or automation should apply the appropriate authorization and validation controls.

---

## Testing Event Triggers

Event triggers can be tested using an isolated `EventBus`.

Example:

```python
from bindai_core.events import EventBus
from bindai_automation import EventTrigger


received = []


def handle_event(event):
    received.append(event)


bus = EventBus()

trigger = EventTrigger(
    bus=bus,
    event_name="test.event",
    target=handle_event,
)

trigger.attach()

# Publish a matching event through the event bus.

assert len(received) == 1

trigger.detach()
```

Tests should verify at least:

- the trigger attaches correctly
- matching events invoke the target
- disabled triggers do not invoke the target
- detached triggers no longer receive events
- repeated `attach()` does not duplicate subscriptions
- repeated `detach()` is safe
- multiple triggers can receive the same event according to `EventBus` behavior

When testing a trigger that starts background automation, the worker can be tested separately from the event subscription itself.

## Current Implementation

The current event-trigger implementation provides:

- `Trigger` base abstraction
- trigger enable/disable state
- `attach()` lifecycle
- `detach()` lifecycle
- `EventTrigger`
- explicit `EventBus` dependency
- event-name subscription through `EventBus.subscribe()`
- callable event targets
- delivery of the original `Event` object
- duplicate-attachment protection
- safe repeated detachment

The related automation package also provides `AutomationWorker` for explicit synchronous or in-process background execution.

The trigger and worker remain separate abstractions.

---

## Current Limitations

The current `EventTrigger` implementation does not provide:

- persistent trigger state
- durable event delivery
- distributed event processing
- trigger-specific queues
- automatic retries
- dead-letter handling
- built-in scheduling
- built-in authentication
- built-in authorization
- distributed worker coordination

The current `AutomationWorker` also does not provide:

- distributed job queues
- cross-process worker coordination
- automatic failover
- worker autoscaling
- durable distributed execution

These capabilities require additional infrastructure outside the current trigger abstraction.

## Architecture

The current relationship can be summarized as:

```text
┌──────────────────────┐
│     Event Source     │
└──────────┬───────────┘
           │
           │ publishes Event
           ▼
┌──────────────────────┐
│       EventBus       │
└──────────┬───────────┘
           │
           │ matching event
           ▼
┌──────────────────────┐
│    EventTrigger      │
│                      │
│ enabled / disabled   │
│ attach / detach      │
└──────────┬───────────┘
           │
           │ Event
           ▼
┌──────────────────────┐
│   Target Callable    │
└──────────┬───────────┘
           │
           │ optional
           ▼
┌──────────────────────┐
│  AutomationWorker    │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│ AutomationDefinition │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│    AutomationRun     │
└──────────────────────┘
```

This separation makes it possible to connect existing BindAI event sources to application-specific automation behavior without embedding automation execution into the event bus.

## Relationship to Observability

BindAI also provides structured events for runtime observability.

An `EventRecorder` can subscribe to an `EventBus` and retain events in memory for inspection.

This is separate from `EventTrigger`:

```text
                         ┌───────────────┐
                         │ EventRecorder │
                         └───────▲───────┘
                                 │
                                 │ records
                                 │
Event Source ──► EventBus ───────┼──────► EventTrigger
                                 │               │
                                 │               ▼
                                 │        Target Callable
                                 │
                                 └──► other subscribers
```

A recorder observes events, while an `EventTrigger` reacts to a configured event by invoking a target.

The same `EventBus` can therefore have multiple independent subscribers.

---

## Current Scope

For BindAI v0.1, event triggers provide a simple foundation for event-driven automation.

The recommended architecture is:

```text
BindAI EventBus
      |
      ├── EventTrigger ──► application action
      |                         |
      |                         └──► optional AutomationWorker
      |
      ├── EventRecorder ─► in-memory observability
      |
      └── other handlers
```

This is sufficient for lightweight in-process event-driven behavior.

Background execution remains explicit through `AutomationWorker`.

---

## Future Direction

Future versions can build on this foundation to provide more advanced event-driven execution, including:

- durable event processing
- queue-backed automation
- distributed workers
- retry policies
- dead-letter handling
- persistent trigger state
- richer event routing
- external event sources
- distributed scheduling
- production tracing and metrics

These capabilities are not part of the current `EventTrigger` implementation and should not be assumed to be available in BindAI v0.1.

## Summary

`EventTrigger` connects an existing `EventBus` to a callable target.

The basic lifecycle is:

```python
trigger = EventTrigger(
    bus=event_bus,
    event_name="agent.finished",
    target=handle_event,
)

trigger.attach()

# Events are published through event_bus.

trigger.detach()
```

The trigger can be enabled or disabled without recreating the subscription:

```python
trigger.disable()

trigger.enable()
```

When an event should start background automation, the target can explicitly submit an automation to `AutomationWorker`:

```python
def handle_event(event):
    worker.submit(
        automation,
        input=event.payload,
    )
```

The responsibilities remain separate:

```text
EventBus
   |
   v
EventTrigger
   |
   v
Target Callable
   |
   v
AutomationWorker
   |
   v
AutomationRun
```

The current implementation intentionally focuses on one responsibility:

**When a configured event is published, invoke the configured target if the trigger is enabled.**

`AutomationWorker` provides the separate in-process execution capability when the application needs background automation.

More advanced durable and distributed automation capabilities remain separate roadmap work.

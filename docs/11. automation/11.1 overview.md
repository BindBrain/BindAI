# Automation

BindAI Automation provides the foundation for building executable automation definitions, tracking automation runs, reacting to events, and executing automation in the background.

The current automation package provides:

- Automation definitions
- Automation execution state
- Automation run history
- Event triggers
- Trigger management
- Background automation workers
- Synchronous automation execution
- In-memory state and history implementations

The architecture is intentionally lightweight so that persistent storage, distributed workers, advanced routing, and additional trigger types can be added independently in future releases.

---

# Automation Architecture

The current automation architecture separates automation definitions, execution state, historical records, event triggers, and background execution.

```text
AutomationDefinition
        |
        v
  AutomationRun
        |
        +----------------------+
        |                      |
        v                      v
AutomationStateStore   AutomationRunHistory
        |                      |
        v                      v
 Current Run State       Historical Runs
```

Event-driven automation is provided through BindAI's existing event system:

```text
Event Source
     |
     v
  EventBus
     |
     v
EventTrigger
     |
     v
Application Target
```

Background execution is provided through `AutomationWorker`:

```text
AutomationDefinition
        |
        v
AutomationWorker
        |
        v
AutomationRun
        |
        +----------------------+
        |                      |
        v                      v
AutomationStateStore   AutomationRunHistory
```

These are separate concerns:

- `EventTrigger` determines when matching events invoke application logic.
- `AutomationWorker` provides synchronous and background execution.
- `AutomationRun` represents one execution.
- `AutomationStateStore` stores the current state of a run.
- `AutomationRunHistory` records completed or failed runs.

# Automation Definitions

`AutomationDefinition` describes an automation and the executable target it invokes.

```python
from bindai_automation import AutomationDefinition

automation = AutomationDefinition(
    name="my-automation",
    target=my_executable,
)
```

A definition provides:

- `id` — unique automation definition identifier
- `name` — human-readable automation name
- `version` — definition version, starting at `1`
- `target` — executable target associated with the definition
- `metadata` — optional application-defined metadata

Definitions can be cloned to create a new version:

```python
version_2 = automation.clone()

assert version_2.version == 2
assert automation.version == 1
```

The automation definition describes **what runs**.

Triggers and workers determine how execution is initiated.

---

# Automation Runs

`AutomationRun` represents one execution of an automation definition.

```python
from bindai_automation import AutomationRun

run = AutomationRun(
    definition_id=automation.id,
    definition_version=automation.version,
    input={"message": "hello"},
)

run.start()

# Execute the automation target here.

run.complete(output={"result": "done"})
```

An automation run provides:

- `id` — unique execution identifier
- `definition_id` — automation definition identifier
- `definition_version` — definition version associated with the execution
- `status` — execution state
- `input` — optional execution input stored on the run
- `output` — execution output
- `error` — failure information when execution fails
- `created_at` — run creation timestamp
- `started_at` — execution start timestamp
- `completed_at` — execution completion timestamp

Runs expose lifecycle methods:

```python
run.start()

run.complete(output={"result": "done"})

run.fail("execution failed")
```

The run object represents execution state independently from the automation definition.

---

# Automation State

`AutomationStateStore` defines the storage contract for the current state of automation runs.

```python
from bindai_automation import AutomationStateStore


class CustomAutomationStateStore(AutomationStateStore):
    def save(self, run):
        ...

    def load(self, run_id):
        ...

    def delete(self, run_id):
        ...
```

The state store is intentionally separate from `AutomationRun`.

This allows execution state to be stored in memory or backed by another persistence implementation without coupling the run model to a specific storage system.

The state store represents the **current execution state** of a run.

---

# In-Memory State Store

`MemoryAutomationStateStore` provides an in-memory implementation of the automation state store.

```python
from bindai_automation import MemoryAutomationStateStore

store = MemoryAutomationStateStore()

store.save(run)

loaded = store.load(run.id)

assert loaded is run
```

Runs can also be removed:

```python
store.delete(run.id)

assert store.load(run.id) is None
```

The in-memory state store is the default state store used by `AutomationWorker` when no custom state store is supplied.

Because it is in-memory, state is process-local and is not durable across application restarts.

Applications requiring durable state can provide another `AutomationStateStore` implementation.

---

# Automation Run History

`AutomationRunHistory` defines the history contract for recording and retrieving automation runs.

```python
from bindai_automation import AutomationRunHistory


class CustomAutomationRunHistory(AutomationRunHistory):
    def record(self, run):
        ...

    def get(self, run_id):
        ...

    def list(self):
        ...
```

Run history is intentionally separate from `AutomationStateStore`.

The state store answers:

> What is the current execution state of this run?

Run history answers:

> What automation runs have been recorded?

The history contract provides:

- `record(run)` — record an automation run
- `get(run_id)` — retrieve a historical run by ID
- `list()` — retrieve recorded runs

This separation allows current execution state and historical records to evolve independently.

---

# In-Memory Run History

`MemoryAutomationRunHistory` provides an in-memory implementation of `AutomationRunHistory`.

```python
from bindai_automation import MemoryAutomationRunHistory

history = MemoryAutomationRunHistory()

run = AutomationRun(
    definition_id=automation.id,
    definition_version=automation.version,
)

run.start()
run.complete(output={"result": "done"})

history.record(run)

stored = history.get(run.id)

assert stored is not None
assert stored.id == run.id
```

Recorded runs are stored as snapshots.

Later changes to the original `AutomationRun` do not modify the historical record.

```python
run.output = {"result": "changed"}

stored = history.get(run.id)

assert stored is not None
assert stored.output == {"result": "done"}
```

The current implementation is intentionally lightweight and provides a foundation for future persistent run-history backends.

# Automation Worker

`AutomationWorker` executes automation definitions and manages the lifecycle of their `AutomationRun` objects.

It supports:

- Synchronous execution
- Background execution
- Configurable state storage
- Configurable run history
- Configurable maximum worker count
- Worker shutdown
- Context-manager usage

```python
from bindai_automation import AutomationWorker

worker = AutomationWorker()

run = worker.run(
    automation,
    input={"message": "hello"},
)

future = worker.submit(
    automation,
    input={"message": "hello"},
)

background_run = future.result()

worker.shutdown()
```

The worker is responsible for:

- Creating an `AutomationRun`
- Saving the run through the configured state store
- Starting the run
- Executing the automation definition
- Completing or failing the run
- Saving the final run state
- Recording the run in history

---

# Worker Configuration

`AutomationWorker` accepts optional state and history implementations.

```python
worker = AutomationWorker(
    state_store=custom_state_store,
    history=custom_history,
    max_workers=4,
)
```

The defaults are:

- `MemoryAutomationStateStore`
- `MemoryAutomationRunHistory`
- `max_workers=4`

The worker rejects an invalid worker count:

```python
worker = AutomationWorker(max_workers=0)
```

This raises:

```text
ValueError: max_workers must be at least 1.
```

Custom state and history implementations can be used when applications need different persistence behavior.

---

# Synchronous Execution

The worker supports synchronous execution through `run()`.

```python
worker = AutomationWorker()

run = worker.run(
    automation,
    input={"message": "hello"},
)
```

The call executes the automation in the current thread and returns an `AutomationRun` after execution completes or fails.

Conceptually:

```text
Application
    |
    v
worker.run()
    |
    v
AutomationDefinition
    |
    v
AutomationRun
    |
    v
Completed / Failed
```

Synchronous execution does not submit work to the worker thread pool.

---

# Background Submission

The worker supports background execution through `submit()`.

```python
worker = AutomationWorker()

future = worker.submit(
    automation,
    input={"message": "hello"},
)

run = future.result()
```

`submit()` returns a `Future[AutomationRun]`.

The future resolves when the background execution has completed.

The worker uses its internal thread pool for background execution.

---

# Submit With Run

Applications that need the run object immediately can use `submit_with_run()`.

```python
worker = AutomationWorker()

run, future = worker.submit_with_run(
    automation,
    input={"message": "hello"},
)

print(run.id)

completed_run = future.result()
```

The important difference is that `submit_with_run()` returns the `AutomationRun` immediately while execution continues in the background.

The run is persisted before the background execution starts.

Conceptually:

```text
submit_with_run()
       |
       +---- Create AutomationRun
       |
       +---- Save initial state
       |
       +---- Submit background execution
       |
       +---- Return run + Future
```

This behavior is useful when an application needs a run identifier before the automation has completed.

---

# Background Worker Model

In BindAI v0.1, `AutomationWorker` uses an in-process `ThreadPoolExecutor`.

Conceptually:

```text
BindAI Application Process

|
+-- AutomationWorker
       |
       +-- Thread
       +-- Thread
       +-- Thread
       +-- Thread
```

The default maximum worker count is `4`.

Applications can configure it:

```python
worker = AutomationWorker(max_workers=8)
```

The worker is part of the application process.

It is not a separate worker service and does not use a distributed queue.

---

# Worker Lifecycle

Workers should be shut down when they are no longer required:

```python
worker.shutdown()
```

The shutdown method supports:

```python
worker.shutdown(
    wait=True,
    cancel_futures=False,
)
```

`wait` controls whether shutdown waits for running work to finish.

`cancel_futures` controls whether pending futures are cancelled when supported by the underlying executor.

---

# Context Manager

`AutomationWorker` can also be used as a context manager:

```python
with AutomationWorker() as worker:
    run = worker.run(automation)
```

Leaving the context shuts down the worker.

This provides a convenient lifecycle for applications that create a worker for a bounded period.

---

# Run Execution

When the worker executes an automation, it performs the following lifecycle:

```text
Create AutomationRun
        |
        v
Save Initial State
        |
        v
Start Run
        |
        v
Execute Definition
        |
        +----------+
        |          |
        v          v
    Success      Failure
        |          |
        v          v
   Complete      Fail
        |          |
        +-----+----+
              |
              v
       Save Final State
              |
              v
        Record History
```

The worker catches exceptions raised during definition execution and records the exception message as the run failure.

---

# Automation Input

Automation runs accept an optional `input` value:

```python
run = AutomationRun(
    definition_id=automation.id,
    definition_version=automation.version,
    input={
        "message": "hello",
    },
)
```

The worker also accepts input:

```python
future = worker.submit(
    automation,
    input={
        "message": "hello",
    },
)
```

The input is stored on the resulting `AutomationRun`.

**Current implementation note:** the worker passes the definition to `definition.run()` without passing the `AutomationRun.input` value as an argument. Therefore, applications should not assume that the worker automatically injects `input` into the automation target.

This behavior may be expanded in a future execution model.

---

# Automation Output

A successful definition execution produces a result.

The worker checks the result's success state and uses its output to complete the run.

Conceptually:

```text
AutomationDefinition.run()
        |
        v
Execution Result
        |
        +---- success
        |       |
        |       v
        |   run.complete(output)
        |
        +---- failure
                |
                v
            run.fail(error)
```

The exact result type depends on the current automation definition implementation.

---

# Automation Failures

If the automation execution raises an exception, the worker catches it and marks the run as failed.

```text
AutomationDefinition
        |
        v
Exception
        |
        v
AutomationRun.fail(...)
        |
        v
Save State
        |
        v
Record History
```

Applications can inspect the run's `status` and `error` fields after execution.

# Worker and Event Triggers

`AutomationWorker` and `EventTrigger` solve different problems.

`EventTrigger` connects an event source to application logic:

```text
EventBus
   |
   v
EventTrigger
   |
   v
Target
```

`AutomationWorker` executes an `AutomationDefinition`:

```text
AutomationDefinition
   |
   v
AutomationWorker
   |
   v
AutomationRun
```

An application can combine the two:

```text
EventBus
   |
   v
EventTrigger
   |
   v
Application Target
   |
   v
AutomationWorker
   |
   v
AutomationDefinition
```

The automation package does not require every event trigger to use a background worker.

# Trigger

`Trigger` is the base abstraction for automation triggers.

```python
from bindai_automation import Trigger
```

A trigger has an enabled state and lifecycle operations:

```python
trigger.enable()
trigger.disable()
trigger.attach()
trigger.detach()
```

The base interface provides:

- `enabled`
- `enable()`
- `disable()`
- `attach()`
- `detach()`

Concrete trigger implementations determine how events are received and how targets are invoked.

---

# Enabling and Disabling Triggers

Triggers can be temporarily disabled without removing their subscription.

```python
trigger.disable()
```

A disabled trigger remains attached but does not process incoming events.

It can be enabled again:

```python
trigger.enable()
```

This provides a simple way to temporarily pause trigger behavior without changing its configuration.

---

# Event Triggers

`EventTrigger` connects a BindAI `EventBus` to a target callable.

```python
from bindai_automation import EventTrigger
```

A trigger is configured with:

- an event bus
- an event name
- a target callable

For example:

```python
trigger = EventTrigger(
    bus=context.events,
    event_name="tool.executed",
    target=handle_event,
)
```

The target receives the matching event:

```python
def handle_event(event):
    print(event)
```

The exact event names depend on the events published by the connected BindAI event source.

---

# BindAI Event System

BindAI's execution context contains an `EventBus`:

```python
context.events
```

The event bus is used by BindAI runtime components to publish structured execution events.

Current event categories include areas such as:

- Application lifecycle
- Agent execution
- Workflow execution
- Workflow nodes
- Human tasks
- Model requests and responses
- Tool execution
- Memory operations
- MCP connection lifecycle

An `EventTrigger` can subscribe to an event bus and react to matching event names.

---

# Attaching an Event Trigger

An `EventTrigger` must be attached before it receives matching events.

```python
trigger.attach()
```

The flow is:

```text
EventBus
   |
   | matching event
   v
EventTrigger
   |
   v
target(event)
```

Calling `attach()` repeatedly does not create duplicate subscriptions.

---

# Detaching an Event Trigger

An attached trigger can be removed from its event source:

```python
trigger.detach()
```

After detaching, the trigger no longer receives events from that subscription.

Calling `detach()` when the trigger is already detached is safe.

A typical lifecycle is:

```python
trigger.attach()

# Automation is active.

trigger.detach()
```

---

# Event Matching

`EventTrigger` subscribes to a specific event name.

For example:

```python
trigger = EventTrigger(
    bus=context.events,
    event_name="tool.executed",
    target=handle_event,
)
```

Only events matching that subscription are delivered to the trigger by the underlying event bus.

The event object is passed to the target callable.

---

# Event-Driven Automation

A simple event-driven automation flow is:

```text
Execution Component
        |
        v
     EventBus
        |
        v
   EventTrigger
        |
        v
Application Target
```

For example:

```python
def handle_tool_event(event):
    print("Tool event received:", event)


trigger = EventTrigger(
    bus=context.events,
    event_name="tool.executed",
    target=handle_tool_event,
)

trigger.attach()
```

The trigger does not need to modify the tool execution implementation.

---

# Targets

An `EventTrigger` accepts a callable target.

```python
def handle_event(event):
    ...
```

The target can contain application-specific automation logic.

For example:

```python
def notify(event):
    print("Automation triggered")
```

Then:

```python
trigger = EventTrigger(
    bus=context.events,
    event_name="tool.executed",
    target=notify,
)
```

The automation package does not impose a higher-level target type.

The target can therefore be a function, callable object, or another compatible callable.

# Trigger State

Triggers have two independent lifecycle concepts:

```text
Attached
   |
   +---- Enabled
   |
   +---- Disabled
```

An attached trigger can be disabled:

```python
trigger.attach()
trigger.disable()
```

It can later be re-enabled:

```python
trigger.enable()
```

Alternatively, its subscription can be completely removed:

```python
trigger.detach()
```

# Trigger Registry

`TriggerRegistry` provides a registry for trigger instances.

```python
from bindai_automation import TriggerRegistry

registry = TriggerRegistry()
```

A trigger can be registered under a key:

```python
registry.register(
    "tool-events",
    trigger,
)
```

It can then be retrieved:

```python
trigger = registry.get("tool-events")
```

A non-throwing lookup is also available:

```python
trigger = registry.get_or_none("tool-events")
```

---

# Registry Operations

`TriggerRegistry` provides operations for managing registered triggers.

```python
registry.register("tool-events", trigger)

registry.get("tool-events")

registry.get_or_none("tool-events")

registry.contains("tool-events")

registry.remove("tool-events")

registry.clear()
```

The registry also exposes:

```python
registry.keys()
registry.values()
registry.items()
```

and supports:

```python
len(registry)
```

The registry is useful when an application needs to manage multiple triggers dynamically.

Registering a trigger does not automatically attach it to its event source.

# Automation and Agents

Agents can participate in automation through BindAI's execution event system.

A conceptual flow is:

```text
Agent Execution
      |
      v
ExecutionContext
      |
      v
EventBus
      |
      v
EventTrigger
      |
      v
Application Action
```

This allows automation logic to react to agent execution events without embedding automation behavior directly inside the agent implementation.

The event bus belongs to the execution context used by the relevant runtime operation.

Applications should use the event bus available through that execution context rather than assuming every agent object exposes a separate event bus.

```http

GET /api/v1/runs/{run_id}
```

The API submits an existing automation definition to the configured `AutomationWorker`.

Conceptually:

```text

    v
BindAI API
    |
    v
AutomationWorker
    |
    v
AutomationDefinition
    |
    v
AutomationRun
```

The API returns a run identifier so clients can inspect the run later.

See the [Background Runs](../10.%20api/10.10%20background-runs) documentation for the HTTP API details.

# Automation State and the REST API

The REST API can expose the state of a background automation run.

The run model can contain:

- Run ID
- Automation definition ID
- Definition version
- Status
- Input
- Output
- Error
- Creation timestamp
- Start timestamp
- Completion timestamp

This provides a lightweight execution-status API for v0.1.

It should not be confused with a distributed run-state database.

# Background Runs and Process Lifetime

The current background worker is process-local.

Conceptually:

```text
Application Process
|
+-- BindAI API
|
+-- AutomationWorker
      |
      +-- Background Run
```

If the application process stops, in-process background work can be interrupted.

The worker does not automatically transfer unfinished work to another process or machine.

---

# Horizontal Scaling

Running multiple API instances does not automatically create one shared background worker pool.

For example:

```text
Load Balancer
      |
      +---- API Instance A
      |        |
      |        +---- AutomationWorker A
      |
      +---- API Instance B
               |
               +---- AutomationWorker B
```

The workers operate independently.

The current v0.1 worker does not provide cross-process coordination or a distributed queue.

Applications requiring coordinated background execution should use an external queue or job system until BindAI provides a dedicated distributed execution architecture.

---

# Persistent State and History

The default state and history implementations are in-memory:

```text
AutomationWorker
      |
      +---- MemoryAutomationStateStore
      |
      +---- MemoryAutomationRunHistory
```

Applications can provide custom implementations:

```python
worker = AutomationWorker(
    state_store=custom_state_store,
    history=custom_history,
)
```

This allows persistent storage to be introduced without changing the core `AutomationRun` abstraction.

The default in-memory implementations are process-local and do not provide durable persistence across application restarts.

---

# Error Handling

The underlying BindAI `EventBus` isolates exceptions raised by individual event handlers.

An exception raised by one handler is logged rather than preventing other subscribed handlers from being invoked.

`EventTrigger` does not provide a separate universal retry or failure-recovery system.

For background automation execution, `AutomationWorker` catches exceptions raised by the automation definition and records the resulting failure on the `AutomationRun`.

Applications requiring additional retries, persistence, or failure recovery should implement those concerns at the appropriate automation or workflow layer.

---

# Synchronous Event Processing

The current core `EventBus` processes handlers synchronously.

Conceptually:

```text
publish(event)
      |
      v
EventTrigger
      |
      v
target(event)
```

An `EventTrigger` does not automatically create a background worker or persistent job.

If event handling needs explicit background execution, the application can invoke an `AutomationWorker` or another application-level execution mechanism from the target.

This keeps event delivery and background execution as separate responsibilities.

# Security Considerations

Automation can cause actions to occur automatically in response to events.

Applications should therefore consider:

- Which events can trigger automation
- Which targets can be invoked
- Whether the target performs external side effects
- Credential and secret handling
- Authorization boundaries
- Input validation
- Audit requirements

Automation targets should not expose secrets or credentials through event payloads unnecessarily.

State-changing automation should receive appropriate validation and authorization controls.

---

# Production Considerations

The in-process worker model is suitable for the initial v0.1 deployment foundation, but production deployments should consider process lifetime and failure behavior.

Important considerations include:

- Application restarts
- Container restarts
- Long-running automation
- Worker capacity
- External-service failures
- Retry behavior
- Idempotency
- Monitoring
- Run-state persistence
- Failure recovery

The default state store and history are also in-memory.

For durable distributed execution, an external queue, persistent state store, and appropriate worker architecture are required.

# Design Principles

BindAI Automation follows several principles:

- Keep triggers small and composable.
- Reuse the existing event system.
- Separate event detection from automation actions.
- Make trigger lifecycle explicit.
- Keep background execution explicit.
- Keep external-service concerns outside the trigger abstraction.
- Allow future trigger types without changing the core event infrastructure.
- Keep automation state separate from event subscriptions.
- Keep current execution state separate from historical run records.
- Keep the initial history API small so persistent backends can be added later.
- Keep background execution explicit through `AutomationWorker`.
- Avoid implying distributed execution where only process-local execution exists.
- Document automation input behavior according to the actual execution path.

# API Accuracy

The current automation documentation intentionally describes APIs implemented by the current `bindai-automation` package and its integration with BindAI's event system.

The current automation package provides:

```python
AutomationDefinition(...)

AutomationRun(...)

AutomationStateStore(...)

MemoryAutomationStateStore(...)

AutomationRunHistory(...)

MemoryAutomationRunHistory(...)

AutomationWorker(...)

Trigger(...)

EventTrigger(...)

TriggerRegistry(...)
```

`AutomationWorker` currently provides:

```python
worker.run(...)

worker.submit(...)

worker.submit_with_run(...)

worker.shutdown(...)
```

It also supports context-manager usage:

```python
with AutomationWorker() as worker:
    ...
```

The worker uses an in-process `ThreadPoolExecutor`.

The default state store is `MemoryAutomationStateStore`.

The default run history implementation is `MemoryAutomationRunHistory`.

The current automation layer does not claim to provide higher-level APIs such as:

```python
automation.schedule(...)

automation.persist(...)

automation.worker(...)

trigger.retry(...)

trigger.schedule(...)
```

unless those capabilities are explicitly implemented elsewhere in BindAI.

Automation run history is currently available through the `AutomationRunHistory` contract and its in-memory implementation, `MemoryAutomationRunHistory`.

Persistent database-backed history remains future infrastructure.

Background execution is currently available through `AutomationWorker`.

One important implementation detail is that `AutomationWorker` stores submitted `input` on `AutomationRun`, but its current `_execute()` implementation calls:

```python
definition.run()
```

without passing the stored input into the definition execution call.

Documentation should therefore not claim that worker input is automatically provided to the automation target.

Advanced event routing, persistent storage backends, distributed execution, and broader automation orchestration remain future infrastructure.

# Summary

BindAI Automation provides a lightweight foundation for stateful and event-driven automation.

The current architecture separates automation definitions, execution state, historical records, triggers, and background execution:

```text
AutomationDefinition
        |
        v
  AutomationRun
        |
        +----------------------+
        |                      |
        v                      v
AutomationStateStore   AutomationRunHistory
        |                      |
        v                      v
 Current Run State       Historical Runs
```

Event-driven automation is provided through:

```text
Event Source
     |
     v
  EventBus
     |
     v
EventTrigger
     |
     v
Application Target
```

Background execution is provided through:

```text
AutomationDefinition
        |
        v
AutomationWorker
        |
        v
AutomationRun
        |
        +----------------------+
        |                      |
        v                      v
AutomationStateStore   AutomationRunHistory
```

The main public abstractions are:

```python
from bindai_automation import (
    AutomationDefinition,
    AutomationRun,
    AutomationRunHistory,
    AutomationStateStore,
    AutomationWorker,
    MemoryAutomationRunHistory,
    MemoryAutomationStateStore,
    Trigger,
    EventTrigger,
    TriggerRegistry,
)
```

`EventTrigger` connects BindAI's existing `EventBus` system to application-defined callable targets.

`AutomationRun` provides execution state, `AutomationStateStore` provides current-state persistence, and `AutomationRunHistory` provides a separate interface for historical execution records.

`AutomationWorker` provides explicit synchronous and background execution for automation definitions using an in-process thread pool.

The REST API can submit and inspect background automation runs through:

```http
POST /api/v1/runs
GET /api/v1/runs/{run_id}
```

The current v0.1 architecture is intentionally lightweight.

Persistent storage backends, distributed queues, coordinated workers, advanced event routing, automatic input propagation, and broader automation orchestration can be introduced in future releases without changing the basic separation between definitions, runs, state, history, triggers, and execution.

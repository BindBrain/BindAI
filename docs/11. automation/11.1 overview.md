# Automation

BindAI Automation provides the foundation for building event-driven applications and workflows.

Automation allows an application to react when something happens, such as an agent event, tool execution, workflow event, or another event published through BindAI's event system.

The current automation package provides three core abstractions:

* `Trigger`
* `EventTrigger`
* `TriggerRegistry`

The architecture is intentionally small so that additional trigger types and automation capabilities can be added incrementally.

---

# Automation Architecture

The current architecture is:

```text
Event Source
     |
     v
  EventBus
     |
     v
EventTrigger
     |
     v
   Target
```

Triggers provide the boundary between an event source and an automation action.

For example:

```text
Agent
  |
  v
EventBus
  |
  v
EventTrigger
  |
  v
Workflow / Function / Application Logic
```

This allows automation behavior to remain separate from the components that produce events.

# Automation Package

The automation package is provided by:

```python
import bindai_automation
```

The public API currently includes:

```python
from bindai_automation import (
    Trigger,
    EventTrigger,
    TriggerRegistry,
)
```

# Trigger

`Trigger` is the base abstraction for automation triggers.

```python
from bindai_automation import Trigger
```

A trigger has an enabled state and provides lifecycle operations:

```python
trigger.enable()
trigger.disable()

trigger.attach()
trigger.detach()
```

The base interface defines:

* `enabled`
* `enable()`
* `disable()`
* `attach()`
* `detach()`

Concrete trigger implementations determine how events are received and how automation is started.

---

# Enabling and Disabling Triggers

Triggers can be temporarily disabled without removing them from their event source.

```python
trigger.disable()
```

A disabled trigger remains attached but ignores incoming events.

It can be enabled again:

```python
trigger.enable()
```

This provides a simple mechanism for controlling automation without destroying the trigger configuration.

---

# Event Triggers

`EventTrigger` connects a BindAI `EventBus` to a target callable.

```python
from bindai_automation import EventTrigger
```

A trigger is created with:

* an event bus
* an event name
* a target callable

For example:

```python
trigger = EventTrigger(
    bus=agent.events,
    event_name="tool.executed",
    target=handle_event,
)
```

The target receives the published event:

```python
def handle_event(event):
    print(event)
```

---

# Attaching an Event Trigger

An `EventTrigger` must be attached to begin receiving events.

```python
trigger.attach()
```

Once attached, matching events published through the configured `EventBus` are passed to the target.

```text
EventBus
   |
   | matching event
   v
EventTrigger
   |
   v
target(event)
```

Calling `attach()` multiple times does not create duplicate subscriptions.

---

# Detaching an Event Trigger

An attached trigger can be removed from its event source:

```python
trigger.detach()
```

After detaching, the trigger no longer receives events from that subscription.

Calling `detach()` when the trigger is already detached is safe.

A typical lifecycle is:

```python
trigger.attach()

# automation is active

trigger.detach()
```

---

# Event Matching

`EventTrigger` subscribes to a specific event name.

For example:

```python
trigger = EventTrigger(
    bus=agent.events,
    event_name="tool.executed",
    target=handle_event,
)
```

Only events whose `name` matches the configured event name are delivered to the trigger by the underlying event bus subscription.

The event itself is passed unchanged to the target callable.

---

# Agent Events

BindAI agents expose an `EventBus` through:

```python
agent.events
```

This makes the agent event system a natural source for automation triggers.

For example:

```python
from bindai_automation import EventTrigger

def handle_tool_event(event):
    print("Tool event received:", event)

trigger = EventTrigger(
    bus=agent.events,
    event_name="tool.executed",
    target=handle_tool_event,
)

trigger.attach()
```

The automation layer therefore builds on the existing BindAI event infrastructure rather than introducing a separate event mechanism.

---

# Tool Execution Events

Agent tool execution publishes `ToolExecutedEvent` through the agent's event bus.

An automation trigger can subscribe to the corresponding event name.

Conceptually:

```text
Agent
  |
  +-- execute_tool()
          |
          v
    ToolExecutedEvent
          |
          v
       EventBus
          |
          v
     EventTrigger
          |
          v
        Target
```

This can be used to react to tool activity without modifying the tool execution pipeline.

---

# Targets

An `EventTrigger` accepts a callable target:

```python
def handle_event(event):
    ...
```

The target can contain application-specific automation logic.

For example:

```python
def notify(event):
    print("Automation triggered")
```

Then:

```python
trigger = EventTrigger(
    bus=agent.events,
    event_name="tool.executed",
    target=notify,
)
```

The automation package does not impose a specific target type.

The target can therefore be a function, callable object, or another compatible callable.

---

# Trigger State

Triggers have two independent lifecycle concepts:

```text
Attached
    |
    +---- Enabled
    |
    +---- Disabled
```

An attached trigger can be disabled:

```python
trigger.attach()
trigger.disable()
```

Events can still reach the trigger's subscription, but the trigger ignores them while disabled.

It can later be re-enabled:

```python
trigger.enable()
```

Alternatively, the subscription can be completely removed:

```python
trigger.detach()
```

---

# Trigger Registry

`TriggerRegistry` provides a registry for trigger instances.

```python
from bindai_automation import TriggerRegistry

registry = TriggerRegistry()
```

A trigger can be registered under a key:

```python
registry.register(
    "tool-events",
    trigger,
)
```

It can then be retrieved:

```python
trigger = registry.get("tool-events")
```

A non-throwing lookup is also available:

```python
trigger = registry.get_or_none("tool-events")
```

---

# Registry Operations

`TriggerRegistry` provides operations for managing registered triggers.

```python
registry.register("tool-events", trigger)

registry.get("tool-events")

registry.get_or_none("tool-events")

registry.contains("tool-events")

registry.remove("tool-events")

registry.clear()
```

The registry also exposes:

```python
registry.keys()
registry.values()
registry.items()
```

and supports:

```python
len(registry)
```

The registry is useful when an application needs to manage multiple automation triggers dynamically.

---

# Example

A simple event-driven automation setup can look like this:

```python
from bindai_automation import EventTrigger


def handle_event(event):
    print("Automation received:", event.name)


trigger = EventTrigger(
    bus=agent.events,
    event_name="tool.executed",
    target=handle_event,
)

trigger.attach()
```

The flow is:

```text
Agent
  |
  v
EventBus
  |
  v
EventTrigger
  |
  v
handle_event()
```

When the automation is no longer required:

```python
trigger.detach()
```

---

# Multiple Triggers

An application can create multiple triggers for different events.

```python
tool_trigger = EventTrigger(
    bus=agent.events,
    event_name="tool.executed",
    target=handle_tool_event,
)

agent_trigger = EventTrigger(
    bus=agent.events,
    event_name="agent.finished",
    target=handle_agent_event,
)
```

Each trigger can have its own lifecycle:

```python
tool_trigger.attach()
agent_trigger.attach()
```

This keeps individual automation rules isolated.

# Automation and Workflows

Automation triggers can be used as an integration boundary around workflows.

Conceptually:

```text
Event
  |
  v
EventTrigger
  |
  v
Workflow
```

The current automation package does not define a dedicated workflow-trigger execution API.

Instead, the trigger target is a generic callable:

```python
def start_automation(event):
    ...
```

Application code can use that callable to invoke whatever workflow or executable behavior is appropriate.

Higher-level automation orchestration is a future layer of the framework.

# Automation and Agents

Agents can act as event sources for automation.

For example:

```text
Agent
  |
  +-- EventBus
        |
        v
   EventTrigger
        |
        v
   Application Action
```

This allows applications to react to agent activity without coupling automation logic directly to the agent implementation.

# Automation and Connections

Automation can also be combined with BindAI Connections.

For example:

```text
Agent Event
    |
    v
EventTrigger
    |
    v
Application Action
    |
    v
Connection
    |
    v
External Service
```

An application could use a trigger target to send information to an external service through a connection.

The current automation package does not directly manage connections. That remains the responsibility of the application or integration layer.

---

# Error Handling

The underlying BindAI `EventBus` isolates exceptions raised by individual event handlers.

This means an exception raised while processing one event handler is logged by the event bus rather than preventing other subscribed handlers from being invoked.

An `EventTrigger` itself does not introduce a separate retry or error-management system.

Applications that require retries, persistence, or failure recovery should implement those concerns at the appropriate higher-level automation or workflow layer.

---

# Synchronous Execution

The current `EventBus` implementation is synchronous.

Therefore, an event handler is invoked as part of event publication.

Conceptually:

```text
publish(event)
      |
      v
EventTrigger
      |
      v
target(event)
```

The current `EventTrigger` does not create background workers or persistent automation jobs.

Those capabilities belong to future automation infrastructure.

---

# Trigger Lifecycle

A recommended lifecycle is:

```text
Create
  |
  v
Configure
  |
  v
Attach
  |
  v
Enabled
  |
  +---- Disable
  |       |
  |       v
  |     Disabled
  |       |
  |       v
  |     Enable
  |       |
  +-------+
  |
  v
Detach
```

For long-running applications, triggers should be detached when their subscription is no longer required.

# Testing Automation

Automation components should be tested independently from the external services they eventually control.

Useful tests include:

* Trigger construction
* Enable/disable behavior
* Attach behavior
* Detach behavior
* Event matching
* Target invocation
* Duplicate attachment protection
* Registry operations
* Handler failure behavior

Event buses can be used with test events and test callables so that automation behavior can be verified without external services.

---

# Security Considerations

Automation can cause actions to occur automatically in response to events.

Applications should therefore consider:

* Which events can trigger automation
* Which targets can be invoked
* Whether the target performs external side effects
* Credential and secret handling
* Authorization boundaries
* Input validation
* Audit requirements

Automation targets should not expose secrets or credentials to event payloads unnecessarily.

State-changing automation should receive appropriate validation and authorization controls.

# Future Automation Capabilities

The broader BindAI automation roadmap includes additional capabilities such as:

* Event trigger framework expansion
* Unified trigger management
* Automation definitions

* Background automation workers

---

# Design Principles

BindAI Automation follows several principles:

* Keep triggers small and composable.
* Reuse the existing event system.
* Separate event detection from automation actions.
* Make trigger lifecycle explicit.
* Avoid hidden background execution.
* Keep external-service concerns outside the trigger abstraction.
* Allow future trigger types without changing existing event infrastructure.
* Keep automation state and persistence separate from basic event subscription.

---

# API Accuracy

The current automation documentation intentionally describes only APIs implemented by the current `bindai-automation` package.

The current package does **not** claim to provide higher-level APIs such as:

```python
automation.run(...)
automation.schedule(...)
automation.persist(...)
automation.history(...)
automation.worker(...)
trigger.retry(...)
trigger.schedule(...)
```

unless those capabilities are explicitly implemented elsewhere in BindAI.

The current automation layer is the foundation for those future capabilities.

# Summary

BindAI Automation provides a lightweight event-driven foundation.

The current architecture is:

```text
Event Source
     |
     v
  EventBus
     |
     v
EventTrigger
     |
     v
   Target
```

The main public abstractions are:

```python
from bindai_automation import (
    Trigger,
    EventTrigger,
    TriggerRegistry,
)
```

Triggers can be attached, detached, enabled, and disabled. `EventTrigger` connects BindAI's existing `EventBus` system to application-defined callable targets, while `TriggerRegistry` provides centralized trigger management.

This foundation can later support broader automation features such as persistent automation definitions, background workers, run history, unified trigger management, and advanced event routing.

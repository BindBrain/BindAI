Deployment Options

BindAI v0.1 supports several deployment approaches.

Local Python Deployment

For development and lightweight applications, BindAI can run directly inside a Python environment.

pip install bindai

The application can then be started using the BindAI CLI or through Python code.

REST API Deployment

BindAI v0.1 includes a REST API package:

pip install bindai-api

The API provides endpoints for:

Health checks

Agent execution

Agent streaming

Workflow execution

Project access

Background automation runs

Run status

The API can be served with Uvicorn:

uv run uvicorn bindai_api.app:app --host 0.0.0.0 --port 8000

The default development address is:

http://localhost:8000

Docker Deployment

The BindAI repository includes a Dockerfile for running the BindAI API.

Build the image from the repository root:

docker build -t bindai-api .

Run the container on Windows PowerShell:

docker run --rm -p 8000:8000 `
  -e BINDAI_API_KEY=your-secret-key `
  bindai-api

On macOS or Linux:

docker run --rm -p 8000:8000 \
  -e BINDAI_API_KEY=your-secret-key \
  bindai-api

The API will then be available at:

http://localhost:8000

Docker Compose

The repository also includes a docker-compose.yml configuration.

Start the API service with:

docker compose up --build

Stop the service with:

docker compose down

The API is exposed on port 8000.

Health Checks

The BindAI API provides a public health endpoint:

GET /health

Example:

curl http://localhost:8000/health

The response contains the service status:

```json
{
  "status": "ok",
  "service": "bindai-api"
}
```
The health endpoint does not require an API key.

It can be used by local deployment scripts, container checks, or external infrastructure that needs a basic service-health signal.

API Authentication

Protected REST API endpoints require an API key.

Configure the key through:

BINDAI_API_KEY=your-secret-key

Clients authenticate using a Bearer token:

Authorization: Bearer your-secret-key

For example:

curl \
  -H "Authorization: Bearer your-secret-key" \
  http://localhost:8000/api/v1/projects

The following endpoint is public:

GET /health

Resource endpoints are protected.

The v0.1 authentication implementation intentionally uses a simple environment-based API key.

Persistent API-key management, user authentication, and advanced authorization are future capabilities.

REST API Resources

The v0.1 API exposes several resource areas.

Agents

Agent endpoints provide agent discovery and execution.

GET  /api/v1/agents
POST /api/v1/agents/{agent_name}/run
POST /api/v1/agents/{agent_name}/stream

The run endpoint executes an agent synchronously.

The stream endpoint provides streamed output.

Workflows

Workflow endpoints provide workflow discovery and execution.

GET /api/v1/workflows
POST /api/v1/workflows/{workflow_id}/run

Workflow execution accepts variables that are passed into the workflow execution context.

Projects

Projects can be exposed through:

GET /api/v1/projects
GET /api/v1/projects/{project_name}

The v0.1 API uses the configured in-process project registry.

It does not provide a persistent project management database.

Background Runs

Background automation runs are exposed through:

POST /api/v1/runs
GET  /api/v1/runs/{run_id}

A run can be submitted and queried later using its run ID.

Background Execution

BindAI v0.1 provides background execution through the AutomationWorker.

The worker executes automation runs in the application process using an in-process thread pool.

Conceptually:

API Request
    |
    v
Automation Worker
    |
    v
Automation Definition
    |
    v
Execution

This is suitable for the initial v0.1 deployment model.

However, it is important to understand the current limitation:

The v0.1 worker is not a distributed queue-based worker system.

The worker is tied to the running application process.

If the process stops, in-process work can be interrupted.

For production systems that require durable distributed background processing, an external queue or persistent job system should be introduced.

Queue-based execution is planned for a future BindAI release and is not required for the v0.1 release.

Worker Scaling

The v0.1 background worker should not be treated as a distributed worker cluster.

For example, running:

Application Instance A
    |
    +---- Automation Worker


Application Instance B
    |
    +---- Automation Worker

does not automatically provide coordinated distributed execution.

Each application process has its own in-process worker.

A production deployment that requires coordinated workers should use a persistent queue and worker architecture.

That capability is outside the initial v0.1 scope.

Scaling

A deployment may eventually require multiple application instances.

Conceptually:

Load Balancer
      |
      +---- Application Instance A
      +---- Application Instance B
      +---- Application Instance C

However, horizontal scaling is not automatic simply because an application uses BindAI.

Before running multiple instances, verify that application state and external resources support the deployment model.

Important considerations include:

Shared databases

Memory persistence

Workflow state

Scheduler coordination

Connection management

Idempotency

Concurrent execution

Task ownership

Background worker coordination

Stateful components require particular attention when scaling horizontally.

The v0.1 in-process automation worker does not provide cross-instance coordination.

Stateless vs Stateful Components

A useful deployment distinction is:

Stateless

Components can usually be recreated without losing important application state.

Examples may include:

Agent configuration

Tool definitions

Workflow definitions

Application code

API application processes

Stateful

Components retain information required across executions.

Examples include:

Persistent Memory

Knowledge indexes

Databases

Workflow state

Human Task state

Background run state

Stateful resources require appropriate persistence and backup strategies.

Containerized Deployment

BindAI v0.1 can be packaged into a standard Python container.

The repository includes a Dockerfile that:

Starts from Python 3.12.

Copies the BindAI workspace into the container.

Installs uv.

Synchronizes workspace dependencies.

Exposes port 8000.

Starts the BindAI API with Uvicorn.

The conceptual container structure is:

Container

├── Application Code
├── BindAI Packages
├── Python Dependencies
└── Configuration

The container runtime, orchestration platform, networking, storage, and secrets management remain deployment-environment concerns.

Docker Environment Configuration

When running the BindAI API in Docker, provide required environment variables explicitly.

For example:

docker run --rm -p 8000:8000 \
  -e BINDAI_API_KEY=your-secret-key \
  -e OPENAI_API_KEY=your-openai-key \
  bindai-api

Do not hardcode secrets into:

Dockerfiles

Source code

Docker images

Git repositories

Public configuration files

For production deployments, use the secret-management capabilities provided by the hosting environment.

Current BindAI v0.1 Deployment Scope

BindAI v0.1 provides:

Python application execution

REST API

API key authentication

Agent execution endpoints

Agent streaming endpoints

Workflow execution endpoints

Project endpoints

Background automation run endpoints

Health checks

Docker deployment

Docker Compose deployment

In-process background workers

Runtime execution events

In-memory event recording

Connections and external integrations

The v0.1 deployment model is intentionally lightweight.

It is designed to provide a usable public API and deployment foundation without requiring a distributed infrastructure stack.

Not Yet Required for v0.1

The following capabilities are not required to release BindAI v0.1:

Distributed job queues

Durable distributed workers

Kubernetes deployment

Automatic horizontal worker coordination

Managed cloud deployment

Built-in multi-tenant infrastructure

Built-in billing

Enterprise RBAC

Hosted observability dashboards

These capabilities can be added after the initial public release.

Queue-based execution is particularly important for future distributed background workloads, but it should not block the v0.1 release.

Future Distributed Deployment

A future distributed architecture can introduce a persistent queue:

Client
   |
   v
BindAI API
   |
   v
Persistent Queue
   |
   +---- Worker A
   +---- Worker B
   +---- Worker C
   |
   v
Persistent State / External Services

This architecture would allow background execution to survive individual API process lifecycles and support multiple coordinated workers.

Queue-based execution is outside the current v0.1 deployment scope.

Kubernetes

Kubernetes is also outside the initial v0.1 deployment scope.

A future Kubernetes deployment could provide:

Multiple API replicas

Multiple worker replicas

Service discovery

Rolling deployments

Autoscaling

Health checks

Persistent volumes

Secret management

These capabilities should be introduced when the underlying distributed execution model requires them.

For v0.1, Docker and Docker Compose provide the supported container deployment foundation.

# Memory Overview

Memory provides a storage and retrieval layer for BindAI applications.

Unlike conversation history, which belongs to an individual agent execution flow, BindAI Memory stores explicit records that can be retrieved, searched, updated, and deleted.

Memory is provider-based, allowing the same `Memory` interface to work with different storage implementations.

---

# What is Memory?

A `Memory` object provides a simple interface for storing and retrieving `MemoryRecord` objects.

```python
from bindai import Memory, MemoryRecord

memory = Memory()

record = MemoryRecord(
    key="user_name",
    value="Alice",
)

memory.set(record)

result = memory.get("user_name")

print(result.value)
```

Memory records contain a key, value, namespace, type, metadata, and optional lifecycle information.

---

# Attaching Memory to an Agent

Agents can use a `Memory` instance through `use_memory()`.

```python
from bindai import Agent, Memory

memory = Memory()

agent = Agent(
    instructions="You are a helpful assistant.",
)

agent.use_memory(memory)
```

The `use_memory()` method accepts a `Memory` instance and returns the agent, allowing it to be used as part of an agent configuration.

```python
agent.use_memory(memory)
```

Memory is therefore an explicit component of an agent rather than a provider-specific feature.

---

# Memory Providers

Memory uses a provider abstraction.

The current BindAI package includes:

* `InMemoryProvider`
* `SQLiteMemoryProvider`
* `VectorMemoryProvider`

The base provider interface is represented by `MemoryProvider`.

This allows storage implementations to expose the same basic operations through the `Memory` abstraction.

---

# In-Memory Storage

`InMemoryProvider` stores memory records in application memory.

```python
from bindai import InMemoryProvider, Memory

memory = Memory(
    provider=InMemoryProvider(),
)
```

This is useful when memory only needs to exist for the lifetime of the running application.

---

# SQLite Storage

BindAI also provides `SQLiteMemoryProvider`.

```python
from bindai import Memory, SQLiteMemoryProvider

provider = SQLiteMemoryProvider(
    "memory.db",
)

memory = Memory(
    provider=provider,
)
```

SQLite provides file-backed storage through SQLite's database engine.

This makes it possible to retain memory records outside the lifetime of an individual Python object.

---

# Vector Memory

BindAI includes a `VectorMemoryProvider` for memory operations that can use vector representations.

```python
from bindai import Memory, VectorMemoryProvider

memory = Memory(
    provider=VectorMemoryProvider(),
)
```

Vector memory supports the same core memory operations while providing functionality for vector-based search.

---

# Memory Records

The fundamental unit of stored memory is `MemoryRecord`.

A record requires:

* `key`
* `value`

It also supports additional fields such as:

* `namespace`
* `type`
* `metadata`
* `importance`
* `access_count`
* `last_accessed`
* `expires_at`
* `embedding`
* `score`
* `tags`
* `source`
* `relationships`
* `related_keys`
* `created_at`
* `updated_at`

Example:

```python
from bindai import MemoryRecord

record = MemoryRecord(
    key="user_name",
    value="Alice",
    namespace="users",
)
```

---

# Namespaces

Memory records can be organized into namespaces.

```python
record = MemoryRecord(
    key="user_name",
    value="Alice",
    namespace="users",
)
```

Memory operations accept a namespace:

```python
result = memory.get(
    "user_name",
    namespace="users",
)
```

Namespaces allow applications to separate logically different groups of records.

---

# Memory Types

Records have a memory type.

The default type is `long_term`.

```python
record = MemoryRecord(
    key="user_name",
    value="Alice",
    type="long_term",
)
```

BindAI exposes `MemoryType` for representing memory categories.

---

# Storing Memory

Use `set()` to store a `MemoryRecord`.

```python
record = MemoryRecord(
    key="favorite_color",
    value="blue",
)

result = memory.set(record)

print(result)
```

The operation returns a `MemoryResult`.

---

# Retrieving Memory

Use `get()` to retrieve a record by key.

```python
result = memory.get(
    "favorite_color",
)

print(result.value)
```

The namespace can also be specified:

```python
result = memory.get(
    "favorite_color",
    namespace="users",
)
```

---

# Searching Memory

Memory supports search operations.

```python
results = memory.search(
    "favorite color",
)
```

Search supports additional parameters:

```python
results = memory.search(
    query="favorite color",
    namespace="users",
    limit=10,
)
```

Metadata can also be supplied as a search filter:

```python
results = memory.search(
    query="favorite color",
    metadata={
        "source": "profile",
    },
)
```

The exact search behavior depends on the configured memory provider.

---

# Checking for Memory

Use `exists()` to check whether a record exists.

```python
exists = memory.exists(
    "favorite_color",
)

print(exists)
```

Namespaces can also be supplied.

```python
exists = memory.exists(
    "favorite_color",
    namespace="users",
)
```

---

# Deleting Memory

Use `delete()` to remove a specific record.

```python
result = memory.delete(
    "favorite_color",
)
```

The namespace can be specified when necessary.

---

# Clearing Memory

Use `clear()` to remove records from a namespace.

```python
result = memory.clear(
    namespace="users",
)
```

This provides a simple way to reset a logical memory collection.

---

# Memory Results

Memory operations return `MemoryResult` objects.

This provides a consistent result abstraction for memory providers.

```text
Memory Operation

↓

MemoryResult
```

The result type is separate from `AgentResult` and `ToolResult`.

---

# Memory Lifecycle Management

BindAI includes a `MemoryManager` for managing the lifecycle of memory records.

```python
from bindai import MemoryManager

manager = MemoryManager()
```

The manager provides operations including:

* `touch()`
* `reinforce()`
* `weaken()`
* `decay()`
* `promote()`
* `forget()`
* `should_promote()`
* `should_forget()`
* `set_expiration()`
* `clear_expiration()`

---

# Importance

Memory records contain an `importance` value.

```python
record = MemoryRecord(
    key="important_fact",
    value="...",
    importance=0.9,
)
```

The memory manager can modify the importance of a record.

```python
manager.reinforce(
    record,
)
```

or weaken it:

```python
manager.weaken(
    record,
)
```

The manager can also apply decay:

```python
manager.decay(
    record,
)
```

---

# Promotion and Forgetting

The memory manager can determine whether a record should be promoted or forgotten.

```python
if manager.should_promote(record):
    manager.promote(record)
```

Similarly:

```python
if manager.should_forget(record):
    manager.forget(record)
```

These operations provide lifecycle management without requiring applications to implement their own memory-state logic.

---

# Expiration

Memory records support expiration.

```python
manager.set_expiration(
    record,
    days=30,
)
```

Expiration can later be removed:

```python
manager.clear_expiration(
    record,
)
```

Records also expose an `expires_at` field.

---

# Access Tracking

Memory records track access information.

A record includes fields such as:

```python
access_count
last_accessed
```

Records can be touched explicitly:

```python
record.touch()
```

The memory manager also provides:

```python
manager.touch(record)
```

This allows applications to track memory usage over time.

---

# Tags

Memory records support tags.

```python
record.add_tag("profile")
record.add_tag("user")
```

Tags can be checked:

```python
record.has_tag("profile")
```

and removed:

```python
record.remove_tag("profile")
```

Tags provide a lightweight way to classify records.

---

# Relationships

Memory records can represent relationships with other records.

```python
record.add_relationship(
    "related_to",
    "other_record",
)
```

Relationships can be retrieved:

```python
related = record.get_relationships(
    "related_to",
)
```

Records also provide convenience methods for adding, removing, and checking relations.

---

# Metadata

Memory records support arbitrary metadata.

```python
record = MemoryRecord(
    key="user_name",
    value="Alice",
    metadata={
        "source": "profile",
        "confidence": 0.95,
    },
)
```

Metadata can be used by applications and can also participate in memory searches where supported.

---

# Embeddings

`MemoryRecord` supports an optional embedding field.

```python
record = MemoryRecord(
    key="document",
    value="BindAI is an agent framework.",
    embedding=[0.12, 0.45, 0.78],
)
```

Vector-based providers can use embeddings as part of their search behavior.

---

# Serialization

Memory records can be converted to dictionaries.

```python
data = record.to_dict()
```

They can also be reconstructed from dictionaries.

```python
record = MemoryRecord.from_dict(data)
```

This makes memory records easier to serialize, inspect, and move between application boundaries.

---

# Memory Registry

BindAI includes a `MemoryRegistry` for registering memory providers.

```python
from bindai import MemoryRegistry

registry = MemoryRegistry()
```

Providers can be registered by name:

```python
registry.register(
    "custom",
    CustomMemoryProvider,
)
```

They can later be retrieved:

```python
provider = registry.provider(
    "custom",
)
```

Available providers can be inspected:

```python
providers = registry.providers()
```

Providers can also be unregistered:

```python
registry.unregister(
    "custom",
)
```

---

# Memory vs Tool Context

Memory and execution context serve different purposes.

| Memory                        | Execution Context                     |
| ----------------------------- | ------------------------------------- |
| Stores memory records         | Stores execution state                |
| Can be backed by a provider   | Exists for an execution               |
| Supports retrieval and search | Coordinates runtime data              |
| Supports lifecycle metadata   | Holds temporary execution information |

Use Memory for information that belongs in the memory system.

Use execution context for temporary runtime state.

---

# Memory vs Knowledge

Memory and Knowledge are also separate concepts.

**Memory** stores application memory records.

**Knowledge** is used for external information retrieval.

They should not be treated as interchangeable storage systems.

---

# Resource Management

`Memory` supports closing its underlying provider.

```python
memory.close()
```

It can also be used as a context manager:

```python
with Memory(
    provider=provider,
) as memory:
    result = memory.get("user_name")
```

This is particularly useful for providers that maintain resources such as database connections.

---

# Best Practices

* Choose a memory provider appropriate for the application.
* Use namespaces to separate logical memory collections.
* Use `MemoryRecord` rather than relying on undocumented storage structures.
* Add metadata when records need additional context.
* Use tags to classify related records.
* Use relationships when records need explicit links.
* Use expiration for temporary memory.
* Use `MemoryManager` for lifecycle operations.
* Use SQLite when file-backed storage is appropriate.
* Use in-memory storage when persistence is not required.
* Keep vector-based memory separate from ordinary key-based assumptions.
* Close providers when they own external resources.

---

# Summary

BindAI Memory is a provider-based system for storing and retrieving `MemoryRecord` objects.

The current implementation includes:

* `Memory`
* `MemoryProvider`
* `InMemoryProvider`
* `SQLiteMemoryProvider`
* `VectorMemoryProvider`
* `MemoryRecord`
* `MemoryResult`
* `MemoryManager`
* `MemoryRegistry`

Memory supports key-based retrieval, search, namespaces, metadata, tags, relationships, embeddings, expiration, access tracking, and memory lifecycle management.

Agents can explicitly attach a `Memory` instance through:

```python
agent.use_memory(memory)
```

The memory API is designed to keep storage implementation separate from the application code using it.

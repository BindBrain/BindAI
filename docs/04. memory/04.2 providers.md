# Memory Providers

Memory providers define **where** and **how** BindAI stores conversational memory.

The memory system is provider-independent, allowing you to change storage backends without modifying your agents or workflows.

This separation makes it easy to move from local development to production as your application grows.

---

# Why Memory Providers?

Different applications have different storage requirements.

For example:

- local development
- production deployments
- distributed applications
- cloud-hosted assistants
- enterprise systems

Instead of coupling agents to a specific database, BindAI delegates persistence to a memory provider.

---

# Architecture

```text
Agent

↓

Memory

↓

Memory Provider

↓

Storage Backend
```

The agent communicates only with the `Memory` abstraction.

The memory object delegates all persistence operations to the configured provider.

---

# Available Providers

BindAI currently includes:

- In-Memory Provider

Planned providers include:

- SQLite
- PostgreSQL
- Redis
- MongoDB
- Vector databases
- Cloud storage

Every provider follows the same interface.

---

# In-Memory Provider

The default provider stores everything in process memory.

```python
from bindai_memory import Memory, InMemoryProvider

memory = Memory(
    provider=InMemoryProvider(),
)
```

This provider is ideal for:

- development
- testing
- tutorials
- examples

All data is lost when the application exits.

---

# Attaching Memory

Attach a memory instance to an agent.

```python
agent.use_memory(memory)
```

Once configured, BindAI automatically loads memory before generation and stores new messages after execution.

---

# Provider Responsibilities

Every memory provider is responsible for operations such as:

- storing messages
- loading conversations
- updating existing records
- deleting conversations
- clearing memory
- managing conversation sessions

The execution engine uses the provider through a common interface, regardless of the underlying storage technology.

---

# Persistent Storage

Persistent providers retain data after the application stops.

```text
Conversation

↓

Memory Provider

↓

Database

↓

Restart Application

↓

Conversation Restored
```

This enables assistants that remember users across sessions.

---

# Session Isolation

Memory is typically organized by session.

```text
Session A

↓

Conversation A


Session B

↓

Conversation B
```

Each session remains isolated, preventing unrelated conversations from sharing context.

---

# Distributed Applications

Centralized providers allow multiple application instances to share the same memory.

```text
Agent A

↓

Shared Database

↑

Agent B
```

This is useful for scalable deployments behind load balancers or multiple worker processes.

# Choosing a Provider

General recommendations:

### In-Memory

Use when:

- learning BindAI
- running examples
- testing locally

### SQLite

Suitable for:

- desktop applications
- lightweight projects

### PostgreSQL

Recommended for:

- production APIs
- enterprise systems
- long-term persistence

### Redis

Ideal for:

- distributed deployments
- shared conversational state
- high-performance access

### Vector Databases

Useful when:

- memories should be retrieved semantically
- similarity search is required
- conversational context becomes very large

---

# Switching Providers

Because providers implement the same interface, switching storage usually requires only replacing the provider.

```python
memory = Memory(
    provider=SomeOtherProvider(),
)
```

The rest of the application remains unchanged.

---

# Custom Providers

Organizations can implement their own providers.

A custom provider typically implements operations such as:

- load
- save
- update
- delete
- clear

Once registered, it behaves exactly like any built-in provider.

---

# Best Practices

- Use In-Memory during development.
- Use persistent providers in production.
- Separate conversations by session.
- Store only useful conversational context.
- Define retention policies for long-lived applications.
- Choose a storage backend appropriate for your expected scale.

---

# Summary

Memory providers determine how BindAI stores and retrieves conversational information.

By separating persistence from agent logic, BindAI allows applications to evolve from simple local prototypes to scalable production systems without changing the programming model.

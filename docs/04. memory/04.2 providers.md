# Memory Providers

Memory providers define where and how BindAI stores memory.

BindAI separates memory operations from storage through the `MemoryProvider` interface. A `Memory` instance delegates storage and retrieval operations to its configured provider.

This allows the same memory API to work with different storage implementations.

---

# Why Memory Providers?

Different applications need different storage behavior.

For example:

* in-memory storage is useful for development and testing;
* SQLite provides local persistent storage;
* vector memory can support embedding-based storage and similarity search.

The agent interacts with the `Memory` abstraction rather than directly with a storage backend.

---

# Architecture

```text
Agent

↓

Memory

↓

MemoryProvider

↓

Storage Backend
```

The `Memory` class provides the application-facing API.

The configured provider implements the actual storage operations.

---

# Available Providers

The current BindAI package provides:

* `InMemoryProvider`
* `SQLiteMemoryProvider`
* `VectorMemoryProvider`

These providers implement the `MemoryProvider` interface.

No external database-specific provider is required to use the core memory API.

---

# In-Memory Provider

`InMemoryProvider` stores memory records in the running Python process.

```python
from bindai import InMemoryProvider, Memory

memory = Memory(
    provider=InMemoryProvider(),
)
```

This provider is useful for:

* development
* testing
* examples
* temporary application state

Because the data is held in process memory, it is lost when the application terminates.

---

# SQLite Provider

BindAI also includes `SQLiteMemoryProvider` for persistent local storage.

SQLite stores memory records in a database file, allowing data to survive application restarts.

```python
from bindai import Memory, SQLiteMemoryProvider

memory = Memory(
    provider=SQLiteMemoryProvider("memory.db"),
)
```

This is useful for applications that need persistence without running a separate database server.

Typical use cases include:

* local applications
* desktop applications
* prototypes requiring persistence
* small deployments
* development environments where memory should survive restarts

---

# Vector Memory Provider

BindAI also includes `VectorMemoryProvider`.

This provider is designed for memory storage that can use vector representations and similarity-based retrieval.

```python
from bindai import Memory, VectorMemoryProvider

memory = Memory(
    provider=VectorMemoryProvider(),
)
```

Vector memory is useful when memory retrieval should be based on semantic similarity rather than only an exact key.

The provider exposes the same core memory operations as the other providers while adding vector-oriented storage and search behavior.

---

# Attaching Memory to an Agent

A `Memory` instance can be attached to an agent using `use_memory()`.

```python
from bindai import Agent, Memory

memory = Memory()

agent = Agent(
    model="openai:gpt-5",
)

agent.use_memory(memory)
```

The agent now has access to the configured memory system.

The important separation is:

```text
Agent
  │
  ▼
Memory
  │
  ▼
Provider
```

The agent does not need to know which provider is being used.

---

# Memory Provider Interface

All memory providers implement the common `MemoryProvider` interface.

The core operations include:

```python
set(record)
get(key, namespace="default")
search(query, namespace="default", limit=10, metadata=None)
delete(key, namespace="default")
exists(key, namespace="default")
clear(namespace="default")
```

The `Memory` class exposes these operations through the configured provider.

For example:

```python
result = memory.get(
    "customer_name",
)
```

Or:

```python
result = memory.search(
    "customer preferences",
)
```

This keeps application code independent of the underlying storage implementation.

---

# Memory Records

Providers store `MemoryRecord` objects.

A record contains a key, value, namespace, and memory metadata.

```python
from bindai import MemoryRecord

record = MemoryRecord(
    key="customer_name",
    value="Alice",
)
```

A record can also contain information such as:

* memory type
* metadata
* importance
* access count
* expiration
* tags
* source
* relationships
* timestamps
* embeddings
* search score

For example:

```python
record = MemoryRecord(
    key="customer_name",
    value="Alice",
    namespace="customer-123",
    tags=["profile"],
    importance=0.8,
)
```

The exact fields available are defined by `MemoryRecord`.

---

# Namespaces

Memory records can be separated using namespaces.

```python
record = MemoryRecord(
    key="customer_name",
    value="Alice",
    namespace="customer-123",
)
```

Memory operations can then target a specific namespace.

```python
result = memory.get(
    "customer_name",
    namespace="customer-123",
)
```

Namespaces provide a simple way to isolate different groups of memory records.

---

# Searching Memory

Providers expose a search operation.

```python
results = memory.search(
    "customer preferences",
    limit=10,
)
```

The search behavior depends on the configured provider.

The common API allows application code to request memory without depending on a specific storage implementation.

---

# Persistent vs Temporary Storage

The main difference between the current providers is how memory is stored.

| Provider               | Persistence        | Typical Use                        |
| ---------------------- | ------------------ | ---------------------------------- |
| `InMemoryProvider`     | No                 | Development and testing            |
| `SQLiteMemoryProvider` | Yes                | Local persistent applications      |
| `VectorMemoryProvider` | Provider-dependent | Vector and similarity-based memory |

`InMemoryProvider` keeps records in the current process.

`SQLiteMemoryProvider` persists records in SQLite storage.

`VectorMemoryProvider` provides vector-oriented memory storage and retrieval.

---

# Switching Providers

Because providers implement the same memory abstraction, an application can change providers without changing the rest of its memory access code.

For example:

```python
from bindai import InMemoryProvider, Memory

memory = Memory(
    provider=InMemoryProvider(),
)
```

The application can instead configure a different provider:

```python
from bindai import Memory, SQLiteMemoryProvider

memory = Memory(
    provider=SQLiteMemoryProvider("memory.db"),
)
```

The application continues to use the same `Memory` API.

---

# Provider Registry

BindAI includes a `MemoryRegistry` for provider registration and lookup.

```python
from bindai import MemoryRegistry

print(MemoryRegistry.providers())
```

A provider can be registered under a name:

```python
MemoryRegistry.register(
    "custom",
    CustomMemoryProvider,
)
```

It can then be retrieved through the registry:

```python
provider = MemoryRegistry.provider(
    "custom",
)
```

Providers can also be removed:

```python
MemoryRegistry.unregister(
    "custom",
)
```

This makes the memory system extensible without changing the core `Memory` abstraction.

---

# Custom Providers

Applications can implement custom memory providers by implementing the `MemoryProvider` interface.

The provider is responsible for implementing the standard memory operations:

```text
set
get
search
delete
exists
clear
```

A custom provider can then be registered with `MemoryRegistry`.

This allows applications to integrate their own storage systems while continuing to use the standard BindAI memory API.

---

# Choosing a Provider

### InMemoryProvider

Use `InMemoryProvider` when memory only needs to exist during the current process.

Good for:

* development
* testing
* examples
* temporary state

### SQLiteMemoryProvider

Use `SQLiteMemoryProvider` when memory should persist locally.

Good for:

* local applications
* desktop applications
* prototypes
* small persistent deployments

### VectorMemoryProvider

Use `VectorMemoryProvider` when the application requires vector-oriented memory storage or similarity-based retrieval.

Good for:

* semantic memory
* similarity search
* embedding-based retrieval
* applications working with larger collections of memories

---

# Best Practices

* Choose the provider based on the required persistence and retrieval behavior.
* Use `InMemoryProvider` for temporary development and testing state.
* Use `SQLiteMemoryProvider` when local persistence is required.
* Use `VectorMemoryProvider` when vector-based retrieval is required.
* Keep application code dependent on `Memory`, not provider-specific implementations.
* Use namespaces to isolate different groups of memory records.
* Store only information that is useful to the application.
* Use `MemoryRegistry` when custom or dynamically selected providers are required.

---

# Summary

BindAI currently provides three memory provider implementations:

* `InMemoryProvider`
* `SQLiteMemoryProvider`
* `VectorMemoryProvider`

All providers integrate through the common `MemoryProvider` abstraction.

Applications interact with `Memory`, while the configured provider handles storage and retrieval. This keeps memory functionality independent from the underlying storage implementation and allows the provider to be changed without rewriting application-level memory logic.

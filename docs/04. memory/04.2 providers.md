# Memory Providers

Memory providers define where and how BindAI stores memory.

BindAI separates memory operations from storage through the `MemoryProvider` interface. A `Memory` instance delegates storage and retrieval operations to its configured provider.

This allows the same memory API to work with different storage implementations.

---

# Why Memory Providers?

Different applications need different storage and retrieval behavior.

For example:

* in-memory storage is useful for development and testing;
* SQLite provides local persistent storage;
* vector memory supports embedding-based storage and similarity search;
* PostgreSQL provides persistent relational storage;
* Pinecone provides managed vector storage and semantic retrieval.

The application interacts with the `Memory` abstraction rather than directly with a storage backend.

---

# Architecture

```text
Agent
  │
  ▼
Memory
  │
  ▼
MemoryProvider
  │
  ▼
Storage Backend
```

The `Memory` class provides the application-facing API.

The configured provider implements the actual storage and retrieval operations.

---

# Available Providers

BindAI currently provides five memory providers:

* `InMemoryProvider`
* `SQLiteMemoryProvider`
* `VectorMemoryProvider`
* `PostgreSQLMemoryProvider`
* `PineconeMemoryProvider`

All providers implement the common `MemoryProvider` interface.

The provider can be selected directly:

```python
from bindai import Memory, SQLiteMemoryProvider

memory = Memory(
    provider=SQLiteMemoryProvider("memory.db"),
)
```

---

# In-Memory Provider

`InMemoryProvider` stores memory records in the running Python process.

```python
from bindai import InMemoryProvider, Memory

memory = Memory(
    provider=InMemoryProvider(),
)
```

This provider is useful for:

* development
* testing
* examples
* temporary application state

Because the data is held in process memory, it is lost when the application terminates.

---

# SQLite Provider

`SQLiteMemoryProvider` provides persistent local storage using SQLite.

```python
from bindai import Memory, SQLiteMemoryProvider

memory = Memory(
    provider=SQLiteMemoryProvider("memory.db"),
)
```

SQLite is useful when memory should survive application restarts without requiring a separate database server.

Typical use cases include:

* local applications
* desktop applications
* prototypes
* small deployments
* development environments requiring persistence

---

# Vector Memory Provider

`VectorMemoryProvider` is designed for vector-oriented memory storage and similarity-based retrieval.

```python
from bindai import Memory, VectorMemoryProvider

memory = Memory(
    provider=VectorMemoryProvider(),
)
```

Vector memory is useful when records need to be retrieved based on semantic similarity rather than only by exact key or text matching.

Typical use cases include:

* semantic memory
* similarity search
* embedding-based retrieval
* applications working with larger collections of memories

---

# PostgreSQL Provider

`PostgreSQLMemoryProvider` stores memory records in PostgreSQL.

A PostgreSQL connection string is passed to the provider:

```python
from bindai import Memory, PostgreSQLMemoryProvider

memory = Memory(
    provider=PostgreSQLMemoryProvider(
        "postgresql://postgres:postgres@localhost:5432/bindai"
    ),
)
```

The provider creates its `memory` table automatically when initialized.

PostgreSQL is useful when an application requires:

* persistent server-side storage;
* relational database infrastructure;
* JSON metadata storage;
* namespace isolation;
* memory persistence across application processes.

The provider supports the standard memory operations:

```text
set
get
search
delete
exists
clear
```

The `search()` operation performs text-based matching within the selected namespace and can filter records by metadata.

---

# Pinecone Provider

`PineconeMemoryProvider` provides managed vector-backed memory using Pinecone.

```python
from bindai import Memory, PineconeMemoryProvider

memory = Memory(
    provider=PineconeMemoryProvider(
        index_name="my-memory-index",
    ),
)
```

The provider reads the Pinecone API key from the `PINECONE_API_KEY` environment variable by default.

```text
PINECONE_API_KEY=your-api-key
```

An API key can also be supplied explicitly:

```python
provider = PineconeMemoryProvider(
    index_name="my-memory-index",
    api_key="your-api-key",
)
```

Pinecone memory uses embeddings for semantic retrieval. By default, the provider uses the registered `openai` embedding provider.

```python
provider = PineconeMemoryProvider(
    index_name="my-memory-index",
    embedding="openai",
)
```

The Pinecone index must use a compatible vector dimension with the configured embedding model.

Pinecone is useful for:

* semantic memory;
* similarity search;
* managed vector storage;
* applications with larger memory collections;
* cloud-based retrieval infrastructure.

---

# Namespaces

Memory records can be separated using namespaces.

```python
from bindai import MemoryRecord

record = MemoryRecord(
    key="customer_name",
    value="Alice",
    namespace="customer-123",
)
```

Memory operations can then target a specific namespace:

```python
result = memory.get(
    "customer_name",
    namespace="customer-123",
)
```

Namespaces provide a simple way to isolate different groups of memory records.

This is particularly useful for:

* users
* conversations
* tenants
* agents
* applications

Providers that support namespaces keep records separated according to the configured namespace.

---

# Searching Memory

All memory providers expose a common `search()` operation:

```python
results = memory.search(
    "customer preferences",
    limit=10,
)
```

The search behavior depends on the provider.

For example:

* `InMemoryProvider` performs provider-specific in-memory retrieval;
* `SQLiteMemoryProvider` searches persisted local records;
* `VectorMemoryProvider` provides vector-oriented retrieval;
* `PostgreSQLMemoryProvider` performs text matching within a namespace;
* `PineconeMemoryProvider` performs embedding-based semantic search.

The common API allows application code to request memory without depending on a specific storage backend.

---

# Metadata Filtering

Memory searches can optionally provide metadata filters:

```python
results = memory.search(
    "customer preferences",
    metadata={
        "category": "customer",
    },
)
```

Metadata filtering behavior depends on the provider.

For PostgreSQL, metadata is stored as JSONB and can be matched directly against record metadata.

For Pinecone, metadata used for filtering must be represented in Pinecone-compatible metadata fields.

---

# Memory Provider Interface

All memory providers implement the common `MemoryProvider` interface.

The core operations are:

```python
set(record)
get(key, namespace="default")
search(query, namespace="default", limit=10, metadata=None)
delete(key, namespace="default")
exists(key, namespace="default")
clear(namespace="default")
```

For example:

```python
result = memory.get(
    "customer_name",
)
```

Or:

```python
results = memory.search(
    "customer preferences",
)
```

This keeps application code independent of the underlying storage implementation.

# Memory Records

Providers store `MemoryRecord` objects.

A record contains a key, value, namespace, and memory metadata.

```python
from bindai import MemoryRecord

record = MemoryRecord(
    key="customer_name",
    value="Alice",
)
```

A record can also contain information such as:

* memory type
* metadata
* importance
* access count
* expiration
* tags
* source
* relationships
* timestamps
* embeddings
* search score

For example:

```python
record = MemoryRecord(
    key="customer_name",
    value="Alice",
    namespace="customer-123",
    tags=["profile"],
    importance=0.8,
)
```

The exact fields available are defined by `MemoryRecord`.

# Choosing a Provider

### InMemoryProvider

Use `InMemoryProvider` when memory only needs to exist during the current process.

Good for:

* development
* testing
* examples
* temporary state

### SQLiteMemoryProvider

Use `SQLiteMemoryProvider` when persistent local storage is required.

Good for:

* local applications
* desktop applications
* prototypes
* small persistent deployments

### VectorMemoryProvider

Use `VectorMemoryProvider` when vector-oriented memory storage or similarity-based retrieval is required.

Good for:

* semantic memory
* similarity search
* embedding-based retrieval

### PostgreSQLMemoryProvider

Use `PostgreSQLMemoryProvider` when persistent relational storage is required.

Good for:

* server applications
* multi-process applications
* relational infrastructure
* persistent metadata-rich memory

### PineconeMemoryProvider

Use `PineconeMemoryProvider` when managed vector storage and semantic retrieval are required.

Good for:

* semantic memory
* large memory collections
* cloud applications
* embedding-based retrieval
* managed vector infrastructure

# Switching Providers

Because providers implement the same memory abstraction, an application can change providers without changing the rest of its memory access code.

For example:

```python
from bindai import InMemoryProvider, Memory

memory = Memory(
    provider=InMemoryProvider(),
)
```

The application can instead configure SQLite:

```python
from bindai import Memory, SQLiteMemoryProvider

memory = Memory(
    provider=SQLiteMemoryProvider("memory.db"),
)
```

Or PostgreSQL:

```python
from bindai import Memory, PostgreSQLMemoryProvider

memory = Memory(
    provider=PostgreSQLMemoryProvider(
        "postgresql://postgres:postgres@localhost:5432/bindai"
    ),
)
```

The rest of the application continues to use the same `Memory` API.

---

# Provider Registry

BindAI includes a `MemoryRegistry` for provider registration and lookup.

```python
from bindai import MemoryRegistry

print(MemoryRegistry.providers())
```

A provider can be registered under a name:

```python
MemoryRegistry.register(
    "custom",
    CustomMemoryProvider,
)
```

It can then be retrieved through the registry:

```python
provider = MemoryRegistry.provider(
    "custom",
)
```

Providers can also be removed:

```python
MemoryRegistry.unregister(
    "custom",
)
```

This makes the memory system extensible without changing the core `Memory` abstraction.

# Custom Providers

Applications can implement custom memory providers by implementing the `MemoryProvider` interface.

The provider is responsible for implementing:

```text
set
get
search
delete
exists
clear
```

A custom provider can then be registered with `MemoryRegistry`.

```python
MemoryRegistry.register(
    "custom",
    CustomMemoryProvider,
)
```

This allows applications to integrate their own storage systems while continuing to use the standard BindAI memory API.

# Best Practices

* Choose the provider based on the required persistence and retrieval behavior.
* Use `InMemoryProvider` for temporary development and testing state.
* Use `SQLiteMemoryProvider` when local persistence is required.
* Use `VectorMemoryProvider` for vector-oriented memory.
* Use `PostgreSQLMemoryProvider` when relational persistent storage is required.
* Use `PineconeMemoryProvider` for managed semantic vector retrieval.
* Keep application code dependent on `Memory`, not provider-specific implementations.
* Use namespaces to isolate different groups of memory records.
* Use metadata to attach structured information to memory records.
* Store only information that is useful to the application.
* Use `MemoryRegistry` when custom or dynamically selected providers are required.

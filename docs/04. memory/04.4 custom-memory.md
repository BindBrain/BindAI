# Custom Memory Providers

BindAI allows applications to implement custom memory providers.

A custom provider can be used when an application needs to store `MemoryRecord` objects in a storage system that is not covered by the built-in providers.

The provider integrates with the existing `Memory` abstraction, so application code can continue using the same memory operations.

---

# Why Create a Custom Memory Provider?

A custom provider is useful when you need to:

* integrate with an existing database
* use a proprietary storage system
* connect to an external service
* implement application-specific persistence
* add custom indexing or retrieval behavior
* integrate with existing infrastructure
* implement specialized memory policies

The application continues to interact with `Memory` rather than directly depending on the storage implementation.

---

# Memory Architecture

The memory system follows this structure:

```text
Application / Agent

↓

Memory

↓

MemoryProvider

↓

Custom Storage
```

`Memory` provides the public interface.

The provider implements the storage operations behind that interface.

---

# MemoryProvider

Custom providers implement the `MemoryProvider` abstraction.

The provider interface defines the core memory operations:

```text
set()
get()
search()
delete()
exists()
clear()
```

These operations work with `MemoryRecord` objects and `MemoryResult` values.

---

# Provider Interface

The provider abstraction is designed around memory records rather than conversation-specific objects.

A provider is responsible for implementing operations equivalent to:

```python
set(record)
get(key, namespace)
search(query, namespace, limit, metadata)
delete(key, namespace)
exists(key, namespace)
clear(namespace)
```

The exact storage implementation is up to the provider.

For example, a provider could store records in:

```text
MemoryRecord

↓

Custom Provider

↓

Database / API / File Store / Other Storage
```

---

# Memory Records

Custom providers operate on `MemoryRecord` objects.

A record contains a key and value together with optional memory metadata.

```python
from bindai import MemoryRecord

record = MemoryRecord(
    key="customer_name",
    value="Alice",
    namespace="user-123",
)
```

Records can also contain additional information such as:

* metadata
* importance
* expiration
* tags
* source
* relationships
* timestamps
* embeddings

A custom provider decides how these fields are represented in its underlying storage.

---

# Implementing a Provider

A custom provider should implement the operations required by `MemoryProvider`.

Conceptually:

```python
class MyMemoryProvider(MemoryProvider):

    def set(self, record):
        ...

    def get(self, key, namespace="default"):
        ...

    def search(
        self,
        query,
        namespace="default",
        limit=10,
        metadata=None,
    ):
        ...

    def delete(self, key, namespace="default"):
        ...

    def exists(self, key, namespace="default"):
        ...

    def clear(self, namespace="default"):
        ...
```

The storage logic inside these methods is application-specific.

For example, `set()` might insert or update a database record, while `search()` might execute a database query.

---

# Using a Custom Provider

Once the provider is implemented, it can be passed to `Memory`.

```python
from bindai import Memory

memory = Memory(
    provider=MyMemoryProvider(),
)
```

The rest of the application can continue using the `Memory` API.

For example:

```python
memory.set(record)

result = memory.get(
    "customer_name",
    namespace="user-123",
)
```

The application does not need to know how the provider stores the record.

---

# Attaching Memory to an Agent

A `Memory` instance can be attached to an agent using `use_memory()`.

```python
agent.use_memory(memory)
```

This keeps the agent coupled to the `Memory` abstraction rather than to a particular storage backend.

---

# Registering a Provider

BindAI includes a `MemoryRegistry` for registering providers by name.

```python
from bindai import MemoryRegistry

MemoryRegistry.register(
    "custom",
    MyMemoryProvider,
)
```

The provider can then be discovered through the registry.

```python
provider = MemoryRegistry.provider(
    "custom",
)
```

Applications can also inspect registered providers:

```python
providers = MemoryRegistry.providers()
```

This returns the registered provider mapping.

---

# Unregistering a Provider

A registered provider can be removed from the registry.

```python
MemoryRegistry.unregister(
    "custom",
)
```

The registry can also be cleared:

```python
MemoryRegistry.clear()
```

# Storage Design

The storage implementation is entirely controlled by the custom provider.

For example:

```text
Application

↓

Memory

↓

MyMemoryProvider

↓

SQL Database
```

or:

```text
Application

↓

Memory

↓

MyMemoryProvider

↓

External Storage API
```

or:

```text
Application

↓

Memory

↓

MyMemoryProvider

↓

Custom Storage Engine
```

The `Memory` interface remains the same in each case.

---

# Namespaces

Custom providers should respect memory namespaces.

For example:

```python
MemoryRecord(
    key="company",
    value="Acme",
    namespace="user-123",
)
```

and:

```python
MemoryRecord(
    key="company",
    value="Example Corp",
    namespace="user-456",
)
```

These records use the same key but belong to different namespaces.

A provider should therefore preserve namespace isolation when implementing `get()`, `search()`, `delete()`, `exists()`, and `clear()`.

---

# Search

Custom providers must also decide how memory search is implemented.

The `Memory` API supports:

```python
memory.search(
    query,
    namespace="default",
    limit=10,
    metadata=None,
)
```

A simple provider might perform a text-based search.

A more specialized provider could use:

* database indexes
* full-text search
* vector similarity
* metadata filtering
* application-specific retrieval logic

The retrieval strategy belongs to the provider.

---

# Persistence

Whether data survives application restarts depends on the custom provider's storage implementation.

An in-process provider may lose data when the process exits.

A database-backed provider can persist records across restarts.

```text
Memory

↓

Custom Provider

↓

Persistent Storage

↓

Application Restart

↓

Records Available Again
```

Persistence is therefore a property of the provider rather than the `Memory` abstraction itself.

---

# Error Handling

Providers should return the appropriate `MemoryResult` values when operations fail.

For example, a provider may encounter:

* database connection failures
* network errors
* serialization errors
* authentication failures
* unavailable storage
* invalid stored data

The provider should handle expected storage failures consistently with the `MemoryProvider` contract.

---

# Testing a Custom Provider

A custom provider should be tested against the operations exposed by the memory abstraction.

At minimum, verify:

* storing a record
* retrieving a record
* searching records
* checking record existence
* deleting a record
* clearing a namespace
* preserving namespaces
* handling missing records
* preserving record metadata where applicable
* handling storage failures

A provider should behave consistently regardless of the underlying storage technology.

---

# Custom Provider and Memory Abstraction

The important separation is:

```text
Application

↓

Memory API

↓

MemoryProvider

↓

Storage Implementation
```

Application code should use:

```python
memory.set(...)
memory.get(...)
memory.search(...)
memory.delete(...)
memory.exists(...)
memory.clear(...)
```

rather than directly accessing the custom storage system.

This keeps the storage implementation replaceable.

---

# Best Practices

* Implement the `MemoryProvider` contract completely.
* Preserve `MemoryRecord` information required by the application.
* Respect namespaces.
* Return the appropriate `MemoryResult` values.
* Keep storage-specific logic inside the provider.
* Avoid coupling agents directly to storage systems.
* Test every provider operation.
* Handle storage failures predictably.
* Use `MemoryRegistry` when the provider needs to be discoverable by name.
* Keep custom providers interchangeable with other providers.

---

# Summary

Custom memory providers extend BindAI's memory system without changing the application-facing `Memory` API.

The core relationship is:

```text
Memory
    ↓
MemoryProvider
    ↓
Custom Storage
```

A custom provider implements the memory operations used by `Memory`:

```text
set
get
search
delete
exists
clear
```

Providers can also be registered with `MemoryRegistry` when named provider discovery is useful.

This allows applications to integrate their own storage systems while keeping agent code independent from storage-specific implementation details.

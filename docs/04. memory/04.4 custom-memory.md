# Custom Memory

BindAI allows you to create your own memory providers.

While the built-in providers are suitable for many applications, some projects require custom persistence layers, proprietary storage systems, cloud services, or specialized business requirements.

Custom providers let you integrate these systems without changing your agents or workflows.

---

# Why Create a Custom Memory Provider?

A custom provider is useful when you need to:

- store conversations in an existing database
- integrate with enterprise infrastructure
- use cloud storage services
- encrypt conversation history
- implement custom retention policies
- share memory across multiple applications
- optimize storage for your specific workload

The rest of your application continues using the same memory API.

---

# Architecture

A custom provider fits into the existing memory architecture.

```text
Agent

↓

Memory

↓

Custom Memory Provider

↓

Your Storage
```

The agent communicates only with the `Memory` abstraction.

The provider is responsible for persistence.

---

# Provider Responsibilities

A memory provider typically manages operations such as:

- loading conversations
- saving new messages
- updating existing conversations
- clearing conversation history
- retrieving messages by session
- deleting conversations

The implementation is entirely under your control.

---

# Basic Structure

A simplified provider might look like this.

```python
class MyMemoryProvider:
    def load(self, session_id): ...

    def save(self, session_id, messages): ...

    def clear(self, session_id): ...
```

Production providers usually implement additional functionality such as indexing, batching, or caching.

---

# Creating a Memory Instance

Once your provider has been implemented, create a memory instance.

```python
memory = Memory(
    provider=MyMemoryProvider(),
)
```

The agent does not need to know how data is stored.

---

# Attaching Memory

Attach the memory instance to an agent.

```python
agent.use_memory(memory)
```

Conversation loading and saving now happen automatically.

---

# Example: SQL Database

A provider may store conversations in a relational database.

```text
Conversation

↓

Memory Provider

↓

SQL Database
```

Each conversation becomes a collection of persisted messages that can be restored later.

---

# Example: Cloud Storage

Providers can also communicate with cloud services.

```text
Agent

↓

Memory Provider

↓

Cloud Storage API

↓

Persistent Storage
```

This enables conversations to survive application restarts and scale across multiple servers.

---

# Example: Encrypted Storage

Sensitive applications may encrypt conversations before storing them.

```text
Conversation

↓

Encrypt

↓

Storage

↓

Decrypt

↓

Conversation
```

Encryption is handled entirely by the provider, keeping the rest of the framework unchanged.

---

# Session Management

Most providers organize memory by session identifier.

```text
Session ID

↓

Load Conversation

↓

Append Messages

↓

Save Conversation
```

This ensures conversations remain isolated from one another.

---

# Performance Considerations

Production providers should consider:

- indexing conversations
- efficient querying
- batching writes
- caching frequently accessed sessions
- asynchronous persistence
- database connection pooling

The optimal approach depends on the chosen storage backend.

---

# Error Handling

Custom providers should handle expected failures gracefully.

Examples include:

- database unavailable
- network interruptions
- authentication failures
- serialization errors
- storage timeouts

Applications may choose to retry, log failures, or temporarily continue without persistence.

---

# Testing

Before deploying a provider, verify that it correctly:

- loads conversations
- stores new messages
- restores previous sessions
- updates existing conversations
- clears conversation history
- handles concurrent access
- recovers from failures

Reliable testing helps prevent conversation loss and data corruption.

---

# Best Practices

- Keep providers focused on persistence only.
- Separate storage logic from business logic.
- Support session isolation.
- Handle failures predictably.
- Avoid blocking operations when possible.
- Encrypt sensitive conversations where appropriate.
- Document retention and deletion policies.
- Keep provider implementations interchangeable.

---

# Summary

Custom memory providers allow BindAI to integrate with virtually any storage system.

Because the memory abstraction separates persistence from execution, applications can evolve from simple local prototypes to enterprise-scale deployments without changing agent or workflow code.

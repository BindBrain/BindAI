# Agents

Agents are the core building block of BindAI.

An agent combines a language model provider with instructions and optional capabilities such as tools, memory, knowledge, middleware, and retrieval.

Agents provide a consistent interface for executing AI tasks without requiring application code to manage provider-specific execution details.

---

# What Is an Agent?

A BindAI agent is responsible for:

* Receiving user input
* Executing an AI model
* Applying configured instructions
* Calling registered tools
* Using optional memory
* Using optional knowledge or retrieval
* Returning an `AgentResult`

The `Agent` class provides the primary execution interface.

---

# Creating an Agent

The `Agent` constructor requires a `name` and `provider`.

```python
from bindai import Agent

agent = Agent(
    name="assistant",
    provider="openai",
    instructions="You are a helpful assistant.",
)
```

The constructor signature is:

```python
Agent(
    *,
    name: str,
    provider,
    instructions: str = "",
    prompt=None,
)
```

The model configuration is normally handled through the provider or through `AgentBuilder`.

---

# Running an Agent

Use the `run()` method to execute an agent.

```python
result = agent.run("Explain what BindAI is.")

print(result.output)
```

`run()` returns an `AgentResult`.

You can inspect the result:

```python
print(result.success)
print(result.output)
print(result.error)
```

A successful execution can therefore be handled consistently regardless of the underlying model provider.

---

# AgentResult

Agent execution returns an `AgentResult`.

```python
result = agent.run("Hello!")

if result.success:
    print(result.output)
else:
    print(result.error)
```

The result exposes the execution status, generated output, and any execution error.

---

# Configuring Models with AgentBuilder

For most applications, `AgentBuilder` provides the recommended fluent API for configuring agents.

```python
from bindai import AgentBuilder

agent = (
    AgentBuilder()
    .name("assistant")
    .model("openai:gpt-4.1-mini")
    .instructions("You are a helpful assistant.")
    .build()
)
```

The builder separates model configuration from the lower-level `Agent` constructor.

The model is specified using a provider-qualified model string:

```text
provider:model
```

For example:

```python
.model("openai:gpt-4.1-mini")
```

---

# Builder Configuration

`AgentBuilder` provides methods for configuring common agent capabilities.

```python
agent = (
    AgentBuilder()
    .name("assistant")
    .model("openai:gpt-4.1-mini")
    .instructions("You are a helpful assistant.")
    .temperature(0.7)
    .build()
)
```

The builder supports configuration for:

* Name
* Provider
* Model
* Instructions
* Temperature
* Maximum tokens
* Maximum tool iterations
* Tools
* Memory
* Knowledge
* Retriever
* Middleware
* Events
* Hooks

Additional configuration can be added incrementally through the fluent API.

---

# Sending Prompts

The primary execution method is:

```python
result = agent.run("Explain dependency injection.")
```

The method accepts a message and an optional structured-output type.

```python
result = agent.run(
    "Generate a fictional person.",
    output=Person,
)
```

The method signature is:

```python
agent.run(
    message: str,
    output: type | None = None,
)
```

---

# Structured Output

BindAI supports structured output using a Python type.

For example, a Pydantic model can define the expected result:

```python
from pydantic import BaseModel


class Person(BaseModel):
    name: str
    age: int
```

Pass the model to `run()`:

```python
result = agent.run(
    "Generate a fictional person.",
    output=Person,
)

print(result.output)
```

The resulting output is structured according to the supplied type.

---

# Streaming Responses

Agents also support streaming execution.

```python
for chunk in agent.stream(context):
    print(chunk)
```

The `stream()` method operates on an `ExecutionContext`.

For interactive applications, BindAI also exposes:

```python
agent.stream_chat(
    "Explain neural networks."
)
```

Streaming is useful for applications that need to display model output progressively rather than waiting for the complete execution.

---

# Chat Execution

BindAI provides a `chat()` interface for conversational execution.

```python
result = agent.chat(
    "Explain what BindAI is."
)

print(result.output)
```

The method accepts the same optional structured-output type as `run()`:

```python
result = agent.chat(
    "Generate a fictional person.",
    output=Person,
)
```

Use `run()` for general agent execution and `chat()` when working with conversational application flows.

---

# Adding Tools

Agents can execute registered tools.

A tool can be attached directly to an agent:

```python
agent.tool(add)
```

The equivalent `add_tool()` method is also available:

```python
agent.add_tool(add)
```

For example:

```python
from bindai import tool


@tool
def add(a: int, b: int):
    return a + b


agent.tool(add)
```

The tool then becomes part of the agent's available execution capabilities.

Multiple tools can be registered:

```python
agent.tool(add)
agent.tool(weather)
agent.tool(search)
```

Tools can also be configured through `AgentBuilder`:

```python
agent = (
    AgentBuilder()
    .name("assistant")
    .model("openai:gpt-4.1-mini")
    .instructions("You are a helpful assistant.")
    .tools(add, weather, search)
    .build()
)
```

---

# Memory

Memory is optional and can be attached to an agent.

```python
agent.use_memory(memory)
```

Memory providers are responsible for storing and retrieving information used by the agent.

For example:

```python
from bindai import InMemoryMemory

memory = InMemoryMemory()

agent.use_memory(memory)
```

Memory can also be configured through the builder:

```python
agent = (
    AgentBuilder()
    .name("assistant")
    .model("openai:gpt-4.1-mini")
    .memory(memory)
    .build()
)
```

Memory is distinct from the agent's immediate execution input and can be configured independently from the model provider.

---

# Knowledge

Agents can be connected to knowledge sources.

```python
agent.use_knowledge(knowledge)
```

Knowledge can also be configured through `AgentBuilder`:

```python
agent = (
    AgentBuilder()
    .name("assistant")
    .model("openai:gpt-4.1-mini")
    .knowledge(knowledge)
    .build()
)
```

Knowledge integration allows applications to provide external information to agent execution, including Retrieval-Augmented Generation workflows.

---

# Retrievers

A retriever can be attached directly to an agent:

```python
agent.use_retriever(retriever)
```

Or configured through the builder:

```python
agent = (
    AgentBuilder()
    .name("assistant")
    .model("openai:gpt-4.1-mini")
    .retriever(retriever)
    .build()
)
```

Retrievers are useful when an application needs to search a knowledge source and provide relevant information to an agent.

---

# Middleware

Middleware can be attached to an agent using:

```python
agent.use_middleware(middleware)
```

The builder provides the corresponding configuration method:

```python
agent = (
    AgentBuilder()
    .name("assistant")
    .model("openai:gpt-4.1-mini")
    .middleware(middleware)
    .build()
)
```

Middleware can be used to add reusable behavior around agent execution.

Typical applications include:

* Logging
* Authentication
* Telemetry
* Metrics
* Request processing
* Response processing

---

# Hooks and Events

Agents expose lifecycle-related APIs including:

```python
agent.before_run(...)
agent.after_run(...)
agent.on_error(...)
agent.hook(...)
agent.on(...)
```

These APIs can be used to integrate custom behavior into agent execution.

For example, lifecycle hooks can be used for:

* Logging
* Auditing
* Monitoring
* Analytics
* Notifications
* Debugging

The exact hook signatures depend on the event or lifecycle integration being used.

---

# Loading an Agent from a Project

BindAI can configure agents from the current project.

```python
from bindai import AgentBuilder

agent = (
    AgentBuilder()
    .from_project()
    .build()
)
```

The project configuration can provide shared defaults such as:

* Provider configuration
* Model configuration
* Environment configuration
* Registered project tools
* Other agent settings

This allows application code to remain small while configuration is maintained at the project level.

---

# Multi-Provider Models

`AgentBuilder.model()` accepts provider-qualified model names.

For example:

OpenAI:

```python
AgentBuilder().model("openai:gpt-4.1-mini")
```

Anthropic:

```python
AgentBuilder().model("anthropic:claude-sonnet-4")
```

Ollama:

```python
AgentBuilder().model("ollama:llama3")
```

LM Studio:

```python
AgentBuilder().model("lmstudio:qwen3")
```

The application-level agent interface remains the same while the model configuration changes.

---

# Agents in Applications

A typical application can keep the agent configuration in one place:

```python
from bindai import AgentBuilder


agent = (
    AgentBuilder()
    .name("assistant")
    .model("openai:gpt-4.1-mini")
    .instructions(
        "You are a helpful AI assistant."
    )
    .build()
)


result = agent.run(
    "What is BindAI?"
)

print(result.output)
```

As the application grows, additional capabilities can be attached:

```python
agent.tool(search)
agent.use_memory(memory)
agent.use_knowledge(knowledge)
agent.use_retriever(retriever)
agent.use_middleware(middleware)
```

This allows an agent to evolve without changing the fundamental execution interface.

---

# Agents and Workflows

Agents can be used as components within larger BindAI workflows.

A workflow can coordinate agents with other workflow operations such as:

* Conditions
* Loops
* Parallel execution
* Retries
* Timeouts
* Human tasks
* Scheduling

This makes it possible to keep individual agents focused on specific responsibilities while using workflows for higher-level orchestration.

---

# Best Practices

* Give each agent a clear responsibility.
* Keep instructions focused.
* Prefer reusable tools over increasingly complex prompts.
* Use memory for information that must persist beyond a single execution.
* Use knowledge and retrievers for external information.
* Use middleware for reusable cross-cutting behavior.
* Use `AgentBuilder` when configuring agents with multiple capabilities.
* Use project configuration for shared defaults.
* Use workflows when multiple agents or execution steps need to be coordinated.

The result is a modular architecture where individual agents remain simple while larger AI applications can be composed from reusable components.

# Execution

Execution is the process BindAI uses to run an agent against an input and produce a result.

An execution can involve the configured model, instructions, tools, memory, knowledge, retrieval, middleware, conversation context, execution configuration, and event handling depending on how the agent is configured.

The main execution interface is the agent's `run()` method.

---

# Running an Agent

A basic execution starts with `agent.run()`:

```python id="5tq4q0"
result = agent.run("Explain what BindAI is.")

print(result.output)
```

The primary execution call accepts a message and can optionally receive an output type for structured results:

```python id="q0n4xp"
result = agent.run(
    "Generate a fictional person.",
    output=Person,
)
```

The first argument is the user message.

The optional `output` argument specifies a Python type for structured output.

---

# Execution Result

`agent.run()` returns an `AgentResult`.

```python id="6nq5pk"
result = agent.run("Hello!")

print(result.success)
print(result.output)
print(result.error)
```

The result provides a consistent interface for checking whether execution succeeded and accessing the generated output or error.

A typical application can therefore use:

```python id="4k3c9d"
if result.success:
    print(result.output)
else:
    print(result.error)
```

This keeps application-level result handling independent of the underlying model provider.

---

# Structured Output

Execution can return structured results instead of plain text.

For example, a Pydantic model can define the expected structure:

```python id="9z2p7r"
from pydantic import BaseModel


class User(BaseModel):
    name: str
    age: int
```

Pass the type to `run()`:

```python id="1q7x4s"
result = agent.run(
    "Generate a fictional user.",
    output=User,
)

print(result.output)
```

The application can then work with the structured result rather than parsing raw text manually.

Structured output is useful when downstream application code requires predictable data.

---

# Tool Execution

Agents can be configured with tools.

For example:

```python id="m5z8c2"
from bindai import Agent

agent = (
    Agent.builder()
    .name("assistant")
    .model("openai:gpt-4.1-mini")
    .instructions("You are a helpful assistant.")
    .tools(search, calculator)
    .build()
)
```

Tools become part of the agent's execution capabilities.

A model may request a registered tool during execution. BindAI then coordinates the tool execution and subsequent agent processing.

Conceptually:

```text id="3n1b6y"
User Input
    |
    v
  Agent
    |
    v
  Model
    |
    +----> Tool Call
    |          |
    |          v
    |      Tool Registry
    |          |
    |          v
    |      Tool Execution
    |          |
    |          v
    |      Tool Result
    |          |
    +----------+
    |
    v
Final Result
```

The number and order of tool interactions depend on the request, model behavior, configured tools, and execution settings.

---

# Tool Iterations

Tool-using agents may perform multiple model/tool interaction cycles during a single execution.

BindAI provides execution configuration for controlling runtime behavior such as tool execution limits.

For example, when an agent is configured with a maximum tool-iteration setting, the application can prevent an execution from continuing indefinitely through repeated tool interactions.

The appropriate limit depends on the application's requirements and the complexity of the tools being used.

Tool iteration limits are especially useful for agents that:

* Use multiple tools
* Perform multi-step tool calls
* Depend on external services
* Need predictable execution boundaries

---

# Memory

Memory can be attached to an agent:

```python id="h8v3d1"
agent.use_memory(memory)
```

Or configured when building the agent:

```python id="6m0x8c"
agent = (
    Agent.builder()
    .name("assistant")
    .model("openai:gpt-4.1-mini")
    .memory(memory)
    .build()
)
```

Memory is an optional execution capability.

It can provide stored information to an agent when the configured memory implementation supports it.

BindAI supports multiple memory implementations, including in-memory, SQLite, PostgreSQL, vector, Pinecone, and Chroma-backed memory.

---

# Conversation Context

Agent execution can also incorporate conversation context.

Conversation support is useful when an application needs to preserve the relationship between multiple messages.

A conversational execution can conceptually combine:

```text id="f6z8k4"
Agent Instructions
        +
Conversation Context
        +
Current User Input
        +
Optional Memory / Knowledge
        =
Model Execution
```

Conversation context and long-term memory are related but distinct.

Conversation represents the current interaction, while memory can provide information that persists independently of a particular conversation.

---

# Knowledge

Knowledge can also be attached to an agent:

```python id="p7k2w1"
agent.use_knowledge(knowledge)
```

Or configured through the builder:

```python id="r5y1x8"
agent = (
    Agent.builder()
    .name("assistant")
    .model("openai:gpt-4.1-mini")
    .knowledge(knowledge)
    .build()
)
```

Knowledge systems allow applications to provide external information to agent execution.

BindAI's knowledge capabilities include document ingestion, parsing, chunking, embeddings, metadata, retrieval, reranking, conversational retrieval, and knowledge pipelines.

The exact retrieval behavior depends on the configured knowledge and retrieval components.

# Retrievers

Agents can use a retriever directly:

```python id="k1m8q3"
agent.use_retriever(retriever)
```

The builder provides the corresponding configuration:

```python id="w4z6n2"
agent = (
    Agent.builder()

    .model("openai:gpt-4.1-mini")

```

Retrievers are useful when an application needs to locate relevant information for an agent.

BindAI supports retrieval strategies including:

* Vector retrieval
* BM25 retrieval
* Hybrid retrieval

Retrieved information can then be incorporated into agent execution as relevant context.

# Retrieval-Augmented Generation

Middleware allows these concerns to remain separate from the core agent instructions and application logic.

# Execution Context

Some BindAI execution APIs operate with an `ExecutionContext`.

For example, the low-level `stream()` API accepts an execution context:

```python id="3b7m0x"
agent.stream(context)
```

The execution context provides runtime information required by the relevant execution operation.

Context-aware APIs are particularly useful when integrating agents with larger application or workflow runtimes.

Execution context helps execution components share runtime state without requiring every component to maintain independent state.

---

# Streaming

BindAI exposes streaming APIs for execution.

The low-level `stream()` method accepts an `ExecutionContext`:

```python id="5q8v2c"
for chunk in agent.stream(context):
    print(chunk)
```

For conversational applications, BindAI also provides `stream_chat()`:

```python id="n4k7x1"
for chunk in agent.stream_chat(
    "Explain neural networks."
):
    print(chunk)
```

Streaming is useful when an application needs to process output progressively.

Common use cases include:

* Chat interfaces
* Interactive applications
* Long-running responses
* Real-time user interfaces

Streaming is different from normal `run()` execution because the application can consume output as it becomes available.

---

# Chat Execution

BindAI also provides a `chat()` method:

```python id="x5m2p9"
result = agent.chat(
    "Explain what BindAI is."
)

print(result.output)
```

Like `run()`, `chat()` can accept an optional structured-output type:

```python id="j8v4q0"
result = agent.chat(
    "Generate a fictional user.",
    output=User,
)
```

Use the execution interface that best matches the application's interaction model.

For conversational applications, `chat()` can be combined with BindAI's conversation and memory capabilities.

# Events

Agents can participate in the BindAI event system.

Applications can register handlers with the agent's event APIs, including `on()`:

```python id="m3z6v8"
agent.on(...)
```

Events can be used to integrate execution with:

* Monitoring
* Logging
* Analytics
* Auditing
* Observability
* Notifications

The exact event types and callback signatures depend on the event integration being used.

Events provide an event-driven way to observe execution without coupling application code to internal execution steps.

# Hooks and Callbacks

Agents expose lifecycle and callback mechanisms for execution-related behavior.

These mechanisms can be used around agent execution for purposes such as:

* Custom logging
* Notifications
* Auditing
* Metrics
* External integrations
* Debugging

Hooks should generally remain focused on cross-cutting behavior rather than containing the application's core business logic.

This keeps the execution lifecycle separate from the primary responsibilities of the agent.

---

# Execution Configuration

BindAI supports execution configuration for controlling runtime behavior.

Execution configuration can be used for concerns such as:

* Tool execution limits
* Execution boundaries
* Runtime options
* Other agent execution settings

Execution configuration should be kept separate from behavioral instructions whenever possible.

For example, an instruction should describe what an agent should do, while an execution setting can control how the runtime limits or manages that work.

This separation makes the same agent configuration easier to reuse in different environments.

# Error Handling

Always check the returned `AgentResult` when application behavior depends on successful execution.

```python id="b5n7x0"
result = agent.run(
    "Perform the requested operation."
)

if not result.success:
    print("Execution failed:")
    print(result.error)
else:
    print(result.output)
```

This keeps application-level error handling independent from provider-specific response formats.

Applications should decide how execution failures are surfaced, retried, logged, or returned to users based on their requirements.

# Execution Boundaries

Agent execution can involve multiple components:

```text id="q6m2v9"
Input
  |
  v
Agent
  |
  +---- Instructions
  |
  +---- Conversation
  |
  +---- Memory
  |
  +---- Knowledge / Retrieval
  |
  +---- Tools
  |
  +---- Middleware
  |
  v
Model Provider
  |
  v

```

Keeping these responsibilities separate makes execution easier to understand and maintain.

For example:

* Instructions define behavior.
* Conversation provides interaction context.
* Memory provides persisted information.
* Knowledge and retrieval provide external information.
* Tools provide actions.
* Middleware provides reusable execution behavior.
* The model provider performs model inference.
* `AgentResult` provides the application-facing result.

# A Complete Execution Example

The following example combines several agent capabilities:

```python id="h2v6q8"
from bindai import Agent


agent = (
    Agent.builder()
    .name("assistant")
    .model("openai:gpt-4.1-mini")
    .instructions(
        """
        You are a helpful AI assistant.

        Provide clear and concise answers.
        """
    )
    .build()
)

result = agent.run(
    "Explain what BindAI is."
)

if result.success:
    print(result.output)
else:
    print(result.error)
```

The same agent can later be extended with additional capabilities:

```python id="v9k3m1"
agent.tool(search)
agent.use_memory(memory)
agent.use_knowledge(knowledge)
agent.use_retriever(retriever)
agent.use_middleware(middleware)
```

This allows the execution layer to grow with the application while keeping the primary agent interface consistent.

---

# Execution Best Practices

* Use `run()` for general agent execution.
* Use `chat()` for conversational execution.
* Use streaming when output needs to be processed progressively.
* Use structured output when downstream code requires predictable data.
* Configure reasonable execution and tool limits for tool-using agents.
* Use memory when persisted information is required.
* Use knowledge and retrievers for external information.
* Use middleware for reusable cross-cutting behavior.
* Use hooks and events for lifecycle integrations.
* Check `AgentResult.success` when execution failure needs to be handled explicitly.
* Keep runtime configuration separate from behavioral instructions.
* Use workflows when multiple agents or execution stages need to be coordinated.
* Use specialist agents when responsibilities are clearly separated.
* Keep external integrations behind connections or tools.
* Use MCP when an external MCP service provides capabilities that should be exposed to an agent.

BindAI keeps the primary execution interface simple while allowing applications to compose tools, memory, knowledge, retrieval, middleware, workflows, and multi-agent execution around the same agent abstraction.

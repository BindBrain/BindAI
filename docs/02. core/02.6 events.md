# Events

BindAI includes a lightweight event system that allows applications to observe what happens during agent and workflow execution.

Events are useful for building:

- Logging
- Monitoring
- Analytics
- Auditing
- Metrics
- Notifications
- Debugging tools
- Custom integrations

Instead of modifying the framework itself, you can subscribe to events and react whenever important execution stages occur.

---

# Why Events?

An AI request involves several internal steps.

For example:

```text
User Request
      │
      ▼
Agent Started
      │
      ▼
Model Request
      │
      ▼
Model Response
      │
      ▼
Tool Execution
      │
      ▼
Agent Finished
```

Each stage can publish an event.

Applications can observe these events without modifying the execution pipeline.

---

# Event Bus

Every agent contains an `EventBus`.

```python
agent.events
```

The event bus is responsible for publishing events and notifying subscribers.

An `EventBus` can also be shared across multiple agents.

```python
from bindai_core.events import EventBus

events = EventBus()

agent.events = events
```

This is useful for centralized monitoring.

---

# Built-in Events

BindAI publishes several lifecycle events.

| Event | Description |
|--------|-------------|
| `AgentStartedEvent` | Agent execution begins |
| `AgentFinishedEvent` | Agent execution completes |
| `ModelRequestEvent` | Request sent to the model |
| `ModelResponseEvent` | Response received from the provider |
| `ToolExecutedEvent` | A tool finishes execution |

Additional events may be introduced as the framework evolves.

---

# Subscribing to Events

Register a listener using the event bus.

```python
def on_event(event):
    print(type(event).__name__)

agent.events.subscribe(
    on_event,
)
```

Every published event is delivered to all subscribers.

---

# Example

```python
from bindai import AgentBuilder


agent = (
    AgentBuilder()
    .model("openai:gpt-5")
    .instructions("You are a helpful assistant.")
    .build()
)


def logger(event):
    print(type(event).__name__)


agent.events.subscribe(logger)

agent.run("Hello!")
```

Example output

```text
AgentStartedEvent
ModelRequestEvent
ModelResponseEvent
AgentFinishedEvent
```

# Model Events

## ModelRequestEvent

Published immediately before the provider receives a request.

Useful for:

- Prompt logging
- Debugging
- Analytics
- Request inspection

---

## ModelResponseEvent

Published after the provider returns a response.

Useful for:

- Measuring latency
- Usage tracking
- Response logging
- Performance monitoring

---

# Tool Events

Whenever an agent executes a tool, BindAI publishes:

```text
ToolExecutedEvent
```

This event can be used for:

- Tool usage statistics
- API auditing
- Performance monitoring
- Debugging

If no tools are executed, this event is not emitted.

---

# Lifecycle Events

Every successful execution follows the same lifecycle.

```text
AgentStartedEvent

↓

ModelRequestEvent

↓

ModelResponseEvent

↓

ToolExecutedEvent
(optional)

↓

AgentFinishedEvent
```

Tool events only appear when the model actually invokes a tool.

---

# Custom Events

Applications may publish their own events.

```python
class MyCustomEvent:
    pass


agent.events.publish(
    MyCustomEvent(),
)
```

This makes BindAI easy to integrate into existing event-driven systems.

---

# Shared Event Bus

Multiple agents can publish to the same event bus.

```python
events = EventBus()

agent1.events = events
agent2.events = events
```

A single subscriber can now observe activity from every agent.

This is especially useful for production monitoring.

---

# Typical Use Cases

The event system is commonly used for:

- Logging every prompt
- Measuring response latency
- Counting model requests
- Recording tool usage
- Monitoring production systems
- Exporting metrics
- Sending notifications
- Auditing AI activity

Because events are independent of execution, these features can be added without modifying agents or workflows.

---

# Events vs Hooks

BindAI provides both events and hooks.

| Events | Hooks |
|--------|-------|
| Broadcast notifications | Agent-specific callbacks |
| Multiple subscribers | Single callback registration |
| Observe execution | Extend agent behavior |
| Best for monitoring | Best for application logic |

Use events when you want to observe what happened.

Use hooks when you want to execute additional application logic around agent execution.

---

# Events vs Middleware

Middleware and events serve different purposes.

| Middleware | Events |
|------------|--------|
| Runs inside execution | Runs after publication |
| Can modify requests | Cannot modify execution |
| Can stop execution | Observation only |
| Used for authentication and validation | Used for logging and monitoring |

Middleware participates in execution.

Events observe execution.

---

# Best Practices

- Keep event handlers lightweight.
- Avoid long-running operations inside subscribers.
- Do not perform blocking network requests directly inside event handlers.
- Use events for monitoring rather than business logic.
- Share a single event bus when monitoring multiple agents.
- Prefer middleware when execution behavior must change.

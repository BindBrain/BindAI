# Events

BindAI provides a structured event system for observing execution and connecting BindAI components with application integrations.

Events can be used for:

- Logging
- Monitoring
- Auditing
- Debugging
- Analytics
- Automation triggers
- Execution inspection
- Custom integrations
- Future tracing and metrics integrations

BindAI has two related concepts:

- **Agent-level callbacks** for lightweight application behavior.
- **Core events** published through `EventBus` for structured execution events.

The core event system is the foundation used by BindAI Runtime and its observability capabilities.

---

# Event Architecture

The core event architecture is:

```text
ExecutionContext
      |
      v
   EventBus
      |
      +---- Event handlers
      |
      +---- EventRecorder
      |
      +---- EventTrigger
      |
      +---- Application integrations
```

An execution context owns an event bus:

```python
from bindai_core.context import ExecutionContext

context = ExecutionContext()

bus = context.events
```

Components can publish structured events through this bus.

Consumers can subscribe to those events without requiring the component that produced the event to know about the consumer.

This keeps execution logic separate from logging, observability, automation, and application integrations.

---

# Event Objects

Core events are represented by `Event` objects.

```python
from bindai_core.events import Event


class MyEvent(Event):

    @property
    def name(self) -> str:
        return "my.event"
```

An event can carry structured data through its payload:

```python
event = MyEvent(
    payload={
        "message": "hello",
    },
)
```

Core events also contain framework-managed metadata including:

- Event ID
- Timestamp
- Event name
- Event payload

The event ID is generated automatically.

The timestamp is recorded when the event is created.

---

# Event Payloads

Event-specific information is stored in the event payload.

For example:

```python
event = MyEvent(
    payload={
        "message": "hello",
        "execution_id": "execution-123",
    },
)
```

The payload is a dictionary and can contain information relevant to the event.

Applications consuming framework events should prefer the documented event type and its payload contract rather than assuming fields that are not guaranteed by the event definition.

---

# EventBus

BindAI provides `EventBus` for structured event communication.

```python
from bindai_core.events import EventBus

bus = EventBus()
```

Subscribe to an event:

```python
def handle_event(event):
    print(event.name)
    print(event.payload)


bus.subscribe(
    "my.event",
    handle_event,
)
```

Publish an event:

```python
bus.publish(
    MyEvent(
        payload={
            "message": "hello",
        },
    )
)
```

The event bus invokes handlers registered for the event name.

---

# Wildcard Subscriptions

`EventBus` supports wildcard subscriptions.

```python
def handle_all(event):
    print(event.name)


bus.subscribe(
    "*",
    handle_all,
)
```

A wildcard handler receives events regardless of their specific event name.

Wildcard subscriptions are particularly useful for:

- Observability
- Logging
- Auditing
- Debugging
- Event recording

For example, BindAI Runtime's `EventRecorder` uses a wildcard subscription to record events emitted through an execution context.

---

# Unsubscribing

Handlers can be removed with `unsubscribe()`.

```python
bus.unsubscribe(
    "my.event",
    handle_event,
)
```

Wildcard subscriptions can also be removed:

```python
bus.unsubscribe(
    "*",
    handle_all,
)
```

Components that create long-lived subscriptions should remove them when they are no longer needed.

---

# Event Handler Isolation

The `EventBus` isolates handler failures from the component publishing the event.

Conceptually:

```text
EventBus.publish()
      |
      +----> Handler A
      |
      +----> Handler B
      |
      +----> Handler C
```

If one handler raises an exception, the event bus logs the handler failure and continues processing the remaining handlers.

This prevents optional integrations such as logging or observability from unnecessarily breaking the primary execution path.

Event handlers should nevertheless remain small and reliable.

# Framework Event Types

BindAI defines structured events for important execution activities.

Current framework events include categories such as:

- Application started
- Application stopped
- Agent started
- Agent finished
- Workflow started
- Workflow finished
- Node started
- Node completed
- Human task created
- Human task completed
- Model requested
- Model responded
- Tool executed
- Memory read
- Memory written
- MCP connected
- MCP disconnected

The exact event name and payload should be obtained from the corresponding BindAI event type.

Applications should avoid hard-coding undocumented event names or payload fields.

---

# Agent Execution Events

Agent execution produces structured lifecycle events.

An agent execution can emit events such as:

```text
Agent Started
     |
     v
Model Requested
     |
     v
Model Responded
     |
     +---- Tool Executed
     |
     v
Agent Finished
```

These events allow applications to observe execution without modifying the agent's core execution logic.

For example, an observability integration can record:

- When an agent started
- When model execution began
- When the model responded
- Which tools were executed
- When the agent finished

---

# Execution IDs

Execution events can include an `execution_id` in their payload.

The execution ID allows related events to be grouped together.

For example:

```text
execution_id = abc-123

AgentStarted
    |
    +---- ModelRequested
    |
    +---- ModelResponded
    |
    +---- ToolExecuted
    |
    +---- AgentFinished
```

Applications can use the execution ID to correlate events belonging to the same execution.

This is particularly useful for:

- Debugging
- Execution history
- Observability
- Audit records
- Custom monitoring

---

# Model Events

Model interactions are represented by structured events.

The model lifecycle includes events such as:

```text
Model Requested
       |
       v
Model Provider
       |
       v
Model Responded
```

A model request event can be used to observe when a model invocation begins.

A model response event can be used to observe when the provider returns.

These events provide useful timing and execution boundaries for future metrics and tracing integrations.

Applications should not assume that every provider exposes identical metadata.

---

# Tool Events

Tool execution can produce a `ToolExecutedEvent`.

The event can be consumed through the execution event bus.

For example:

```python
def handle_tool_event(event):
    print(
        "Tool event:",
        event.payload,
    )


context.events.subscribe(
    "tool.executed",
    handle_tool_event,
)
```

The exact event name should be taken from the corresponding BindAI event definition.

Tool events are useful for:

- Logging
- Auditing
- Monitoring
- Debugging
- Metrics
- Automation

For detailed tool behavior, see the Tools documentation.

---

# Workflow Events

Workflow execution can also produce structured events.

The workflow lifecycle can be represented conceptually as:

```text
Workflow Started
       |
       v
Node Started
       |
       v
Node Completed
       |
       v
Workflow Finished
```

These events can be used to observe workflow execution without embedding monitoring logic into every workflow node.

Workflow events are particularly useful for:

- Execution history
- Debugging
- Monitoring
- Automation
- Application analytics

---

# Node Events

Workflow nodes can emit lifecycle events such as:

- Node started
- Node completed

This provides visibility into individual workflow steps.

A workflow execution can therefore be inspected at both the workflow and node levels.

For example:

```text
Workflow
   |
   +---- Node A started
   |
   +---- Node A completed
   |
   +---- Node B started
   |
   +---- Node B completed
   |
   v
Workflow completed
```

---

# Memory Events

Memory operations can produce structured events.

Current event categories include:

- Memory read
- Memory written

These events can help applications observe memory activity without coupling monitoring logic directly to a particular memory implementation.

They can be useful for:

- Debugging
- Auditing
- Performance analysis
- Custom observability

Applications should avoid logging sensitive memory contents unless explicitly required and appropriately protected.

---

# MCP Events

BindAI's current MCP-related event categories include:

- MCP connected
- MCP disconnected

These events provide an event boundary for observing MCP connection lifecycle activity.

BindAI's current MCP implementation is a lightweight HTTP-based bridge rather than a complete implementation of every MCP protocol capability.

See the MCP documentation for the current supported scope.

---

# EventRecorder

BindAI Runtime provides `EventRecorder` for lightweight in-memory event recording.

```python
from bindai_runtime import BindRuntime

runtime = BindRuntime()

events = runtime.observability
```

The recorder subscribes to the runtime execution context's event bus and keeps emitted events in memory.

This makes it useful for:

- Development
- Debugging
- Execution inspection
- Tests
- Lightweight observability
- Building future integrations

---

# Reading Recorded Events

All recorded events can be retrieved with:

```python
events.all()
```

For example:

```python
recorded_events = events.all()

for event in recorded_events:
    print(
        event.name,
        event.payload,
    )
```

The returned collection contains the events recorded by the recorder.

---

# Reading Events for an Execution

Events can be filtered by execution ID.

```python
execution_events = events.for_execution(
    "execution-123",
)
```

This makes it possible to inspect the event sequence belonging to one execution.

For example:

```python
for event in events.for_execution("execution-123"):
    print(event.name)
```

This is useful when an application needs to inspect one agent or workflow execution without processing unrelated events.

---

# Clearing Recorded Events

The recorder can be cleared:

```python
events.clear()
```

This removes the currently recorded events from memory.

This can be useful in tests or development tools that need to reset execution history between runs.

---

# Closing the EventRecorder

When the recorder is no longer needed, it can be closed:

```python
events.close()
```

Closing the recorder removes its subscription from the event bus.

This is useful for components with an explicit lifecycle.

---

# EventRecorder Storage

The v0.1 `EventRecorder` is intentionally **in-memory**.

It does not provide:

- Persistent event storage
- Distributed event storage
- Distributed tracing
- Metrics aggregation
- Dashboards
- Alerting
- Hosted observability

Recorded events are therefore tied to the lifetime of the running process.

If the process exits, in-memory recorded events are lost.

Applications that require durable observability should connect BindAI events to an external storage or monitoring system.

---

# Observability Architecture

A simple BindAI observability architecture is:

```text
BindAI Execution
       |
       v
ExecutionContext
       |
       v
EventBus
       |
       +---- EventRecorder
       |
       +---- Logger
       |
       +---- Metrics Integration
       |
       +---- Tracing Integration
       |
       +---- EventTrigger
       |
       +---- Custom Integration
```

The event bus provides the integration boundary.

Different consumers can observe the same execution without requiring the execution engine to know how those consumers store or process events.

---

# Runtime Observability

`BindRuntime` creates an execution context and attaches an `EventRecorder`.

Conceptually:

```text
BindRuntime
    |
    +---- ExecutionContext
    |
    +---- ExecutionEngine
    |
    +---- Scheduler
    |
    +---- EventRecorder
```

The runtime recorder observes events emitted through the runtime execution context.

This provides a lightweight observability foundation while keeping persistent monitoring infrastructure outside the core runtime.

---

# Agent Callbacks

BindAI also provides lightweight agent-level callback mechanisms where supported by the agent API.

For example:

```python
agent.on(
    "message",
    callback,
)
```

An application can emit an application-specific event where the API supports it:

```python
agent.emit(
    "message",
    "Hello",
)
```

These callbacks are intended for lightweight application-level behavior.

They are different from structured core `Event` objects and `EventBus` subscriptions.

For framework execution observability, prefer the core event infrastructure.

---

# EventBus vs Agent Callbacks

The two mechanisms have different purposes.

| Mechanism | Purpose |
| --- | --- |
| `agent.on()` | Lightweight agent-level callback |
| `agent.emit()` | Lightweight agent-level event emission |
| `EventBus` | Structured framework event communication |
| `EventRecorder` | In-memory recording of structured events |
| `EventTrigger` | Turn matching events into automation actions |

A useful rule is:

- Use agent callbacks for lightweight application-level behavior.
- Use `EventBus` for structured BindAI execution events.
- Use `EventRecorder` for lightweight in-memory execution inspection.
- Use `EventTrigger` when an event should initiate automation.
- Use workflows for explicit multi-step orchestration.

---

# Events and Automation

BindAI Automation provides `EventTrigger`, which can connect an event bus to an automation target.

Conceptually:

```text
BindAI Component
       |
       v
    EventBus
       |
       v
  EventTrigger
       |
       v
Automation Target
```

For example:

```python
from bindai_automation import EventTrigger


def handle_event(event):
    print(
        "Automation triggered:",
        event.payload,
    )


trigger = EventTrigger(
    bus=agent.events,
    event_name="my.event",
    target=handle_event,
)

trigger.attach()
```

Once attached, the trigger listens for the configured event.

When the matching event is published, the target is invoked.

This creates a separation between event production and automation behavior.

---

# Enabling Automation Triggers

An event trigger can be temporarily disabled:

```python
trigger.disable()
```

While disabled, matching events do not invoke the target.

It can later be enabled:

```python
trigger.enable()
```

This allows applications to temporarily suspend an automation without destroying the trigger configuration.

---

# Detaching Automation Triggers

A trigger can be detached from its event source:

```python
trigger.detach()
```

After detaching, the trigger no longer receives events from the event bus.

Applications should detach triggers when they are no longer needed.

---

# Event-Driven Architecture

Events can connect independent application components.

For example:

```text
              BindAI Agent
                   |
                   v
                EventBus
                   |
        +----------+----------+
        |          |          |
        v          v          v
     Logging    Metrics   EventTrigger
                             |
                             v
                         Automation
                             |
                    +--------+--------+
                    |        |        |
                    v        v        v
                 Workflow Service Notification
```

The important principle is that the component producing an event does not need to know which consumers will react to it.

This reduces coupling between:

- Agents
- Workflows
- Logging
- Observability
- Automation
- External services

# Events and Workflows

Events can be used as boundaries around larger application workflows.

For example:

```text
Agent
  |
  v
EventBus
  |
  v
EventTrigger
  |
  v
Workflow
  |
  +---- Condition
  |
  +---- Agent
  |
  +---- Human Task
  |
  v
Workflow Result
```

Events should generally initiate or notify workflows rather than contain complex orchestration logic.

For explicit multi-step orchestration, use BindAI workflows.

---

# Events and External Integrations

Events can connect BindAI execution to external application services.

For example:

```text
Agent
  |
  v
EventBus
  |
  +---- Logger
  |
  +---- Metrics
  |
  +---- Automation
  |
  +---- Connection
```

External service calls should generally be delegated to dedicated application components or BindAI Connections rather than implementing large amounts of business logic directly inside event handlers.

---

# Keeping Event Handlers Lightweight

Event handlers should generally perform small, focused operations.

Good event-handler responsibilities include:

- Logging
- Updating counters
- Recording metrics
- Creating audit records
- Triggering lightweight notifications
- Scheduling background work
- Passing work to another component

Avoid placing large amounts of business logic directly inside event handlers.

For complex processing, use the event as the boundary and delegate the work to another component.

---

# Error Handling in Event Handlers

Event handlers are application code and can introduce their own errors.

`EventBus` protects the publisher from handler failures by logging handler exceptions and continuing with other handlers.

Applications should still implement appropriate error handling when an event operation is important.

For example:

```python
def handle_event(event):
    try:
        process_event(event)
    except Exception:
        logger.exception(
            "Event processing failed",
        )
```

Important event-processing failures should be monitored appropriately.

---

# Event Naming

Use descriptive and stable event names.

Application-specific names might include:

```text
task_completed
execution_started
execution_failed
status_changed
```

Framework event names should come from the corresponding BindAI event type.

Avoid relying on undocumented names.

When consuming framework events, prefer the event classes exported by BindAI rather than manually reproducing event-name strings wherever possible.

---

# Hooks and Lifecycle Callbacks

Events are not the only extension mechanism available in BindAI.

Agents and execution components can also expose hooks or lifecycle callbacks.

These mechanisms are different from the core event system.

A useful distinction is:

```text
Hooks
  |
  v
Execution-related customization


Lifecycle callbacks
  |
  v
Direct execution lifecycle behavior


EventBus
  |
  v
Decoupled structured event communication
```

Use the mechanism appropriate for the required behavior.

Do not assume that a lifecycle callback and a framework event have identical timing or payload contracts.

---

# Events vs Hooks

| Mechanism | Primary purpose |
| --- | --- |
| `Agent.on()` | Lightweight agent-level callback |
| `Agent.emit()` | Agent-level event emission |
| `EventBus` | Structured event communication |
| `EventRecorder` | In-memory execution event recording |
| `EventTrigger` | Convert an event into an automation action |
| Hooks | Reusable execution-related behavior |
| Lifecycle callbacks | Direct lifecycle-specific behavior |
| Workflows | Explicit multi-step orchestration |

A simple rule is:

- Use agent callbacks for lightweight local behavior.
- Use core events for structured communication.
- Use `EventRecorder` for lightweight event inspection.
- Use automation triggers when events should initiate actions.
- Use hooks for reusable execution-related behavior.
- Use lifecycle callbacks for lifecycle-specific behavior.
- Use workflows for complex orchestration.

# Testing Events

Event behavior should be tested independently from external services.

A basic `EventBus` test can verify subscription and publication:

```python
received = []


def callback(event):
    received.append(event)


bus.subscribe(
    "my.event",
    callback,
)

bus.publish(
    MyEvent(
        payload={
            "message": "hello",
        },
    )
)

assert len(received) == 1
assert received[0].payload["message"] == "hello"
```

Tests should cover important event behavior such as:

- Event registration
- Event publication
- Event payloads
- Multiple subscribers
- Wildcard subscriptions
- Handler isolation
- Unsubscription
- Event-trigger attachment
- Event-trigger detachment
- Trigger enable/disable behavior
- Event recording
- Execution ID filtering

Avoid requiring external services when testing the core event mechanism.

---

# Testing EventRecorder

The `EventRecorder` can be tested using an existing `EventBus`.

For example:

```python
from bindai_core.events import EventBus
from bindai_runtime.event_recorder import EventRecorder


bus = EventBus()
recorder = EventRecorder(bus)

bus.publish(
    MyEvent(
        payload={
            "execution_id": "execution-123",
            "message": "hello",
        },
    )
)

assert len(recorder.all()) == 1
assert len(recorder.for_execution("execution-123")) == 1

recorder.close()
```

Tests should also verify that clearing the recorder removes its in-memory state.

# Events and Observability

Events provide the foundation for BindAI's current observability capabilities.

They can be connected to:

- Logging
- Metrics
- Tracing
- Auditing
- Error monitoring
- Execution inspection
- Automation

However, the event system itself is **not a complete observability platform**.

Production observability may require additional infrastructure for:

- Persistent event storage
- Distributed tracing
- Metrics aggregation
- Dashboards
- Alerting
- Log aggregation
- Long-term execution history

BindAI v0.1 provides the event infrastructure and lightweight in-memory recording foundation.

Applications can build additional observability integrations on top of it.

---

# Current Event Architecture

The current BindAI event architecture can be summarized as:

```text
ExecutionContext
      |
      v
   EventBus
      |
      +---- Framework Events
      |
      +---- EventRecorder
      |
      +---- EventTrigger
      |
      +---- Custom Event Handlers
```

Framework components publish structured events.

Consumers subscribe to those events.

The `EventRecorder` provides lightweight in-memory recording.

`EventTrigger` connects events to automation.

External observability systems can subscribe and forward events to their own infrastructure.

---

# Best Practices

- Use descriptive event names.
- Prefer framework event types when consuming BindAI events.
- Treat event payloads as structured contracts.
- Use execution IDs to correlate related execution events.
- Keep event handlers small and focused.
- Keep heavy business logic outside event handlers.
- Handle important handler failures appropriately.
- Use `EventRecorder` for lightweight development and execution inspection.
- Use `EventTrigger` when events should initiate automation.
- Detach triggers when they are no longer needed.
- Use workflows for explicit multi-step orchestration.
- Avoid logging sensitive memory or credential data.
- Test event mechanisms independently from external services.
- Do not assume undocumented event names or payload fields.
- Do not treat the event system as a complete observability platform.
- Remember that `EventRecorder` storage is process-local and in-memory in v0.1.

BindAI provides a structured event system for observing execution and connecting components.

The core architecture is:

```text
Execution
    |
    v
ExecutionContext
    |
    v
EventBus
    |
    +---- Framework Events
    |
    +---- EventRecorder
    |
    +---- EventTrigger
    |
    +---- Custom Integrations
```

Framework events cover important execution activities such as:

- Agent execution
- Workflow execution
- Node execution
- Model requests and responses
- Tool execution
- Memory operations
- Human tasks
- MCP connection lifecycle

`EventRecorder` provides lightweight in-memory recording of events and supports filtering events by execution ID.

The key principle is to use the appropriate layer for the job:

- **Agent callbacks** for lightweight local application behavior.
- **EventBus** for structured BindAI event communication.
- **EventRecorder** for lightweight in-memory execution inspection.
- **EventTrigger** for event-driven automation.
- **Workflows** for explicit multi-step orchestration.

BindAI v0.1 provides the event and observability foundation while leaving persistent tracing, metrics, dashboards, and distributed observability infrastructure to future integrations and deployment environments.

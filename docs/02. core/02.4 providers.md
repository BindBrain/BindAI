# Providers

Providers connect BindAI agents to language models.

BindAI separates agent configuration from the underlying model provider so applications can select different model providers without changing the overall agent architecture.

The provider layer handles provider-specific model integration while the agent layer provides a consistent application-facing interface.

---

# Provider Architecture

The relationship between an application, agent, provider, and model can be represented as:

```text
Application
    |
    v
  Agent
    |
    v
 Provider
    |
    v
Language Model
```

The provider is responsible for communicating with the underlying model service.

The exact capabilities available during execution depend on the provider and model being used.

---

# Supported Providers

The current BindAI provider ecosystem includes:

* OpenAI
* Anthropic
* Google Gemini
* Groq
* Ollama
* OpenRouter

Provider integrations are registered with the BindAI provider registry.

The registry provides a common interface for discovering and creating supported provider implementations.

---

# Configuring a Model

The recommended way to select a model is through `Agent.builder()`.

```python id="7k3m2x"
from bindai import Agent

agent = (
    Agent.builder()
    .name("assistant")
    .model("openai:gpt-4.1-mini")
    .instructions("You are a helpful assistant.")
    .build()
)
```

The model string uses the following format:

```text id="9x4p1v"
provider:model
```

For example:

```text id="m7q2c8"
openai:gpt-4.1-mini
```

The provider prefix identifies the provider, while the remaining value identifies the model.

---

# Environment Variables

Provider credentials should not be hardcoded into application source code.

For example:

```text id="r2m6x9"
OPENAI_API_KEY=your_api_key_here
```

The current BindAI development environment supports provider credentials such as:

```text id="c8v3q1"
OPENAI_API_KEY=your_api_key_here
ANTHROPIC_API_KEY=your_api_key_here
GEMINI_API_KEY=your_api_key_here
GROQ_API_KEY=your_api_key_here
OPENROUTER_API_KEY=your_api_key_here
```

Ollama generally runs locally and does not require a hosted-provider API key.

Store sensitive configuration in environment variables or an appropriate secret-management system.

Never commit API keys or other credentials to source control.

Conceptually:


# Provider and Agent Configuration

Provider configuration and agent behavior are separate concerns.

For example:

```python id="n6q3w8"
agent = (
    Agent.builder()
    .name("researcher")
    .model("openai:gpt-4.1-mini")
    .instructions(
        """
        You are a research assistant.

        Provide concise, factual answers.
        """
    )
    .build()
)
```

Here:

* `model()` selects the provider and model.
* `instructions()` defines agent behavior.
* `build()` creates the configured agent.

This separation makes it possible to change the model configuration without rewriting the agent's behavioral instructions.

---

# Switching Providers

Because the model is configured through the agent builder, changing providers can often be as simple as changing the model string.

For example:

```python id="s1x5k7"
.model("openai:gpt-4.1-mini")
```

can be changed to:

```python id="j8p4m2"
.model("anthropic:claude-sonnet-4")
```

or:

```python id="v3n6q9"
.model("ollama:llama3")
```

The rest of the agent configuration can remain conceptually unchanged.

However, provider portability does not guarantee identical behavior between models.

# Provider and Tools

Providers work together with BindAI's tool system.

For example:

```python id="x7m2c5"
agent = (
    Agent.builder()
    .name("assistant")
    .model("openai:gpt-4.1-mini")
    .tools(search_tool, calculator_tool)
    .build()
)
```

The agent can then make use of registered tools during execution when supported by the underlying model and provider.

Provider and model capabilities determine which tool-calling features are available.

Applications should verify the capabilities of the selected model before depending on tool calling.

# Provider and Structured Output

BindAI agents can request structured output through `run()`.

For example:

```python id="p8r4v1"
from pydantic import BaseModel


class User(BaseModel):
    name: str
    age: int


result = agent.run(
    "Generate a fictional user.",
    output=User,
)

print(result.output)
```

The actual structured-output behavior depends on the capabilities and implementation of the configured provider and model.

Applications should test structured-output behavior with the provider/model combinations they intend to support.

---

# Provider and Streaming

BindAI exposes streaming APIs for agent execution.

For conversational streaming:

```python id="m5x9q2"
for chunk in agent.stream_chat(
    "Explain transformers."
):
    print(chunk)
```

The exact streaming behavior depends on the execution API and provider implementation.

Streaming is particularly useful for:

* Chat interfaces
* Interactive applications
* Long responses
* Real-time user experiences

# Provider and Memory

Memory is implemented at the BindAI agent/application layer rather than being tied to a particular model provider.

For example:

```python id="c7n3w5"
agent = (
    Agent.builder()
    .name("assistant")
    .model("openai:gpt-4.1-mini")
    .memory(memory)
    .build()
)
```

The same general memory configuration can be used while changing the model provider.

This separation allows model selection and application state management to evolve independently.

# Custom Providers

# Provider Independence

Provider independence means that the application-level agent interface is separated from provider-specific model communication.

For example, the application can construct an agent using:

```python id="f4m8q2"
agent = (
    Agent.builder()
    .name("assistant")
    .model("openai:gpt-4.1-mini")
    .instructions("You are a helpful assistant.")
    .build()
)
```

The model can later be changed:

```python id="j7x3n9"
.model("ollama:llama3")
```

without requiring the rest of the application to be rewritten around a provider-specific SDK.

This is one of the primary benefits of the provider abstraction.

# Choosing a Provider

The appropriate provider depends on the application's requirements.

Consider:

* Model capabilities
* Hosting requirements
* Privacy requirements
* Latency
* Cost
* Tool-calling support
* Structured-output support
* Streaming support
* Deployment environment
* Local versus hosted inference

For local development or local inference, Ollama can be useful.

For hosted applications, a managed provider or routing service may be more appropriate.

The best provider is therefore determined by the requirements of the application rather than by provider popularity alone.

---

# Provider Errors

Provider execution can fail for reasons such as:

* Invalid credentials
* Missing credentials
* Unsupported model
* Provider service errors
* Network failures
* Rate limits
* Invalid requests
* Insufficient provider account credits

Applications should use the `AgentResult` returned by agent execution to determine whether an execution succeeded.

For example:

```python id="m9v3x6"
result = agent.run(
    "Explain what BindAI is."
)

if result.success:
    print(result.output)
else:
    print(result.error)
```

Provider-specific failures should not require the application to replace the overall agent abstraction.

# Best Practices

* Keep provider credentials out of source code.
* Use environment variables or an appropriate secret-management system for credentials.
* Use the `provider:model` format when selecting a model.
* Prefer `Agent.builder()` for agent configuration.
* Keep provider-specific logic out of application-level business logic where practical.
* Verify model capabilities before relying on tool calling or structured output.
* Test provider/model combinations used by the application.
* Use local providers when local inference is appropriate.
* Choose models based on the actual requirements of the task.
* Keep provider configuration separate from agent instructions whenever possible.
* Do not assume that different providers will produce identical behavior.
* Keep provider integrations modular so additional providers can be added without changing the core agent abstraction.

BindAI's provider architecture gives applications a consistent agent interface while allowing the underlying model provider to change as requirements evolve.

# Providers

Providers connect BindAI agents to language models.

BindAI separates agent configuration from the underlying model provider so applications can select different models without changing the rest of the agent architecture.

A provider configuration can be supplied directly through `AgentBuilder` or loaded from the project configuration.

---

# Provider Architecture

The relationship between an application, agent, provider, and model can be represented as:

```text
Application
    │
    ▼
  Agent
    │
    ▼
 Provider
    │
    ▼
Language Model
```

The provider is responsible for communicating with the underlying model service.

The exact capabilities available during execution depend on the provider and model being used.

---

# Configuring a Model

The simplest way to select a model with `AgentBuilder` is the `model()` method.

```python
from bindai import AgentBuilder

agent = (
    AgentBuilder()
    .name("assistant")
    .model("openai:gpt-4.1-mini")
    .instructions("You are a helpful assistant.")
    .build()
)
```

The model string uses the following format:

```text
provider:model
```

For example:

```text
openai:gpt-4.1-mini
```

The provider prefix identifies the provider, while the remaining value identifies the model.

---

# Configuring a Provider Explicitly

`AgentBuilder` also provides a dedicated `provider()` method.

```python
from bindai import AgentBuilder

agent = (
    AgentBuilder()
    .provider("openai")
    .model("gpt-4.1-mini")
    .instructions("You are a helpful assistant.")
    .build()
)
```

The provider method also supports provider configuration options.

```python
AgentBuilder().provider(
    "openai",
    api_key="your_api_key",
    endpoint="https://api.openai.com/v1",
)
```

The exact options depend on the provider implementation.

---

# Project Configuration

For applications using a BindAI project, provider configuration can be loaded through `from_project()`.

```python
from bindai import AgentBuilder

agent = (
    AgentBuilder()
    .from_project()
    .build()
)
```

This keeps provider configuration outside the application code.

A project can therefore define its default model and related configuration while individual agents focus on their behavior.

---

# Environment Variables

Provider credentials should not be hardcoded into application source code.

For example:

```text
OPENAI_API_KEY=your_api_key_here
```

Store sensitive configuration in environment variables or another appropriate secret-management system.

The exact environment variables required depend on the provider being used.

# Switching Models

Because the model is configured through the builder, changing models can be as simple as changing one value.

For example:

```python
.model("openai:gpt-4.1-mini")
```

can be changed to:

```python
.model("ollama:llama3")
```

or:

```python
.model("lmstudio:qwen3")
```

The rest of the agent configuration can remain unchanged.

---

# Provider Configuration and Agent Configuration

Provider configuration and agent behavior are separate concerns.

For example:

```python
agent = (
    AgentBuilder()
    .name("researcher")
    .model("openai:gpt-4.1-mini")
    .instructions("""
You are a research assistant.

Provide concise, factual answers.
""")
    .temperature(0.2)
    .build()
)
```

Here:

* `model()` selects the model provider and model.
* `instructions()` defines agent behavior.
* `temperature()` configures model-generation behavior.
* `build()` creates the configured agent.

This separation makes model configuration easier to change without rewriting agent instructions.

---

# Provider and Tools

Providers work together with BindAI's tool system.

For example:

```python
agent = (
    AgentBuilder()
    .name("assistant")
    .model("openai:gpt-4.1-mini")
    .tools(search_tool, calculator_tool)
    .build()
)
```

The agent can then use the registered tools during execution when supported by the underlying model/provider.

Provider and model capabilities determine which features are available.

---

# Provider and Structured Output

BindAI agents can request structured output through `run()`:

```python
from pydantic import BaseModel


class User(BaseModel):
    name: str
    age: int


result = agent.run(
    "Generate a fictional user.",
    output=User,
)

print(result.output)
```

The actual structured-output behavior depends on the capabilities of the configured provider and model.

---

# Provider and Streaming

BindAI exposes streaming APIs for agent execution.

For conversational streaming:

```python
for chunk in agent.stream_chat(
    "Explain transformers."
):
    print(chunk)
```

The exact streaming behavior depends on the execution API and provider implementation.

Streaming is particularly useful for:

* Chat interfaces
* Interactive applications
* Long responses
* Real-time user experiences

# Local Models

One advantage of the provider abstraction is that applications can use local inference services.

For example:

```python
.model("ollama:llama3")
```

or:

```python
.model("lmstudio:qwen3")
```

The rest of the agent can retain the same general structure:

```python
agent = (
    AgentBuilder()
    .name("assistant")
    .model("ollama:llama3")
    .instructions("You are a helpful assistant.")
    .build()
)
```

This makes it possible to experiment with local models without restructuring the application around a provider-specific SDK.

# Custom Providers

BindAI exposes provider abstractions that allow additional provider implementations to be integrated into the framework.

The public provider API includes the `LLMProvider` type:

```python
from bindai import LLMProvider
```

Custom provider implementations should follow the provider interfaces exposed by the BindAI version being used.

Because provider APIs can evolve independently, consult the provider implementation and API reference when building a custom integration.

---

# Choosing a Provider

The appropriate provider depends on the application's requirements.

Consider:

* Model capabilities
* Hosting requirements
* Privacy requirements
* Latency
* Cost
* Tool-calling support
* Structured-output support
* Streaming support
* Deployment environment

For local development, providers such as Ollama or LM Studio can be useful when local inference is preferred.

For hosted applications, a managed model provider may be more appropriate.

---

# Provider Portability

BindAI's provider-prefixed model format allows the same general agent architecture to be used with different model providers.

For example:

```python
.model("openai:gpt-4.1-mini")
```

```python
.model("ollama:llama3")
```

```python
.model("lmstudio:qwen3")
```

The agent's tools, instructions, memory, knowledge, and workflow integration can remain conceptually separate from the provider selection.

However, provider portability does **not** mean that every model supports every capability. Always verify the capabilities of the selected model before relying on features such as tool calling or structured output.

---

# Best Practices

* Keep provider credentials out of source code.
* Use environment variables or an appropriate secret-management system for credentials.
* Prefer `AgentBuilder().from_project().build()` when working with project-level configuration.
* Use the `provider:model` format when selecting a model directly.
* Keep provider-specific logic out of application-level business logic where practical.
* Verify model capabilities before relying on tool calling or structured output.
* Use local providers when local inference is appropriate for the application.
* Choose models based on the actual requirements of the task rather than provider popularity.
* Keep provider configuration separate from agent instructions whenever possible.

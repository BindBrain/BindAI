# Loops

Loop nodes allow a workflow to repeat execution while a predicate evaluates to **True**.

A loop evaluates its predicate against the current `WorkflowContext`. If the predicate returns `True`, execution continues to the loop body. If it returns `False`, execution follows the loop's exit path.

Loops are useful for iterative workflow logic such as processing collections, polling external systems, batch operations, and repeated validation.

---

# What is a Loop?

A loop creates a cycle in the workflow.

Conceptually:

```text
Loop
  │
  ▼
Evaluate Predicate
  │
  ├── True ──→ Loop Body
  │               │
  │               └────→ Loop
  │
  └── False ──→ Exit
```

The loop does not execute the body internally as a Python `while` statement. Instead, the loop node determines which workflow node should execute next.

Each iteration uses the current workflow context.

---

# Why Use Loops?

Loops are useful when the same workflow logic must execute repeatedly.

Common examples include:

* processing a collection of items
* polling an external service
* waiting for a background operation
* validating data until it reaches an expected state
* processing paginated results
* performing repeated calculations
* incremental synchronization

Without a loop, repeated workflow logic would need to be represented by duplicated nodes or branches.

---

# Loop Execution Flow

During execution, the loop evaluates its predicate using the current workflow context.

```text
Evaluate Predicate
        │
   ┌────┴────┐
 True       False
   │           │
   ▼           ▼
 Body         Exit
   │
   ▼
 Loop
```

When the predicate returns `True`, execution continues through the loop body.

When it returns `False`, execution follows the loop's exit path.

---

# Creating a Loop

The workflow builder exposes a `loop()` method that accepts a predicate.

```python
builder.loop(
    predicate=lambda context: ...,
)
```

The predicate receives the current workflow context and must return a boolean value.

For example:

```python
builder.loop(
    predicate=lambda context: context.variables["counter"] < 5,
)
```

The predicate is evaluated during workflow execution.

> **Note:** The public builder API calls this argument `predicate`, not `condition`.

---

# Loop Predicates

A predicate determines whether another iteration should execute.

For example:

```python
lambda context: context.variables["counter"] < 5
```

The predicate evaluates the current workflow state:

```text
counter = 0 → True
counter = 1 → True
counter = 2 → True
counter = 3 → True
counter = 4 → True
counter = 5 → False
```

When the predicate becomes `False`, the loop exits.

Predicates should therefore be based on state that changes during workflow execution.

---

# Working with Workflow Variables

Loop predicates commonly use values stored in the workflow context.

For example:

```text
counter = 0
     │
     ▼
Evaluate Predicate
     │
   True
     │
     ▼
Execute Body
     │
     ▼
Update counter
     │
     ▼
Evaluate Predicate
     │
   ...
     │
counter = 5
     │
     ▼
   False
     │
     ▼
   Exit
```

Because each iteration operates on the workflow context, changes made during one iteration can be observed by later iterations.

---

# Loop Body and Exit

A `LoopNode` uses two outgoing paths:

```text
next_nodes[0] → loop body
next_nodes[1] → loop exit
```

The predicate selects between these paths.

Conceptually:

```text
                 Loop
                   │
             Evaluate Predicate
              ┌────┴────┐
           True        False
             │            │
             ▼            ▼
          Body           Exit
             │
             └────────→ Loop
```

The loop body must eventually route execution back to the loop node when another iteration should be evaluated.

This creates the workflow cycle.

---

# Shared Workflow Context

Each iteration operates on the same `WorkflowContext`.

```text
Iteration 1
     │
     ▼
Workflow Context
     │
     ▼
Iteration 2
     │
     ▼
Workflow Context
     │
     ▼
Iteration 3
```

Variables updated during an iteration remain available to subsequent nodes and iterations unless the workflow explicitly changes or resets them.

This makes loops useful for incremental processing.

---

# Example: Processing a Collection

A common loop pattern processes items one at a time.

```text
Initialize Items
       │
       ▼
     Loop
       │
       ▼
Process Current Item
       │
       ▼
Advance Position
       │
       ▼
     Loop
```

The predicate can determine whether more items remain.

Conceptually:

```python
lambda context: context.variables["index"] < len(
    context.variables["items"]
)
```

The workflow should update the index during each iteration.

---

# Example: Polling an External Service

Loops can repeatedly check the state of an asynchronous operation.

```text
Check Status
     │
     ▼
   Loop
     │
     ▼
Completed?
  ┌──┴──┐
 No    Yes
  │      │
  ▼      ▼
Wait    Exit
  │
  └────→ Loop
```

The predicate can inspect the current status stored in the workflow context.

When the operation reaches its completed state, the predicate returns `False` and the workflow exits the loop.

---

# Example: Batch Processing

Loops can process records in batches.

```text
Load Batch
     │
     ▼
   Loop
     │
     ▼
Process Batch
     │
     ▼
Load Next Batch
     │
     ▼
   Loop
```

The predicate determines whether additional records remain.

This allows a workflow to process large collections incrementally instead of attempting to process everything in a single operation.

---

# Loops vs Retry

Loops and retries both involve repeated execution, but they solve different problems.

| Loop                               | Retry                           |
| ---------------------------------- | ------------------------------- |
| Repeats intentional workflow logic | Repeats failed node execution   |
| Controlled by a predicate          | Controlled by retry policy      |
| Uses workflow state                | Triggered by an execution error |
| Part of normal workflow design     | Reliability mechanism           |
| May continue for many iterations   | Limited by retry attempts       |

Use a **loop** when repetition is part of the business or workflow logic.

Use **retry** when an operation fails and should be attempted again according to a reliability policy.

---

# Nested Loops

Loops can be combined with other workflow structures, including nested iterative logic.

Conceptually:

```text
Outer Loop
    │
    ▼
Inner Loop
    │
    ▼
Process
    │
    ▼
Continue
```

Nested loops can be useful when processing hierarchical data, but excessive nesting can make workflows difficult to understand and maintain.

Keep loop bodies focused and avoid unnecessary nesting.

---

# Exiting a Loop

Every loop should have a clear terminating condition.

```text
Predicate
   │
   ├── True  → Body → Loop
   │
   └── False → Exit
```

The predicate should eventually become `False` under normal execution.

A loop without a reachable exit can cause the workflow to continue indefinitely.

---

# Avoiding Infinite Loops

The loop body should normally update the state used by the predicate.

For example:

```text
counter += 1
     │
     ▼
Evaluate Predicate
     │
     ▼
counter < 5
```

If `counter` never changes, a predicate such as:

```python
lambda context: context.variables["counter"] < 5
```

may remain `True` indefinitely.

Good loop design therefore requires:

1. a clearly defined exit condition
2. state that changes during execution
3. a loop body that makes progress toward termination

---

# Combining Loops with Other Nodes

Loops can be combined with other workflow nodes.

For example:

```text
Loop
  │
  ▼
Agent
  │
  ▼
Tool
  │
  ▼
Update Context
  │
  └────→ Loop
```

Each iteration can perform multiple workflow operations before returning to the loop.

This makes loops useful for multi-step iterative processes.

# Common Use Cases

Loop nodes are useful for:

* collection processing
* batch processing
* pagination
* polling external services
* repeated validation
* incremental synchronization
* waiting for state changes
* iterative business processes

---

# Best Practices

* Define a clear exit condition.
* Make sure the predicate can eventually become `False`.
* Update the state used by the predicate.
* Keep loop bodies focused on a specific responsibility.
* Avoid unnecessary nested loops.
* Use retry policies for transient execution failures.
* Monitor long-running workflows that contain loops.
* Keep loop state in the workflow context when it must persist between iterations.

---

# Summary

Loop nodes allow BindAI workflows to repeat execution while a predicate evaluates to `True`.

The predicate receives the current `WorkflowContext` and determines whether execution should continue through the loop body or follow the exit path.

Loops are useful for collection processing, polling, batch operations, repeated validation, and other intentional iterative workflows.

For transient execution failures, use retry policies instead of loops.

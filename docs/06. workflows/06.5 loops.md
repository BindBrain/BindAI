# Loops

Loop nodes allow a workflow to repeat execution while a predicate evaluates to **True**.

A loop evaluates its predicate against the current `WorkflowContext`. If the predicate returns `True`, execution enters the loop body. When the predicate returns `False`, execution follows the loop's exit path.

Unlike a Python `while` statement, a workflow loop is represented explicitly as a node in the workflow graph.

---

# What is a Loop?

A loop creates a cycle in the workflow.

Conceptually:

```text
Loop
  │
  ▼
Evaluate Predicate
  │
  ├── True ──→ Loop Body
  │               │
  │               └────→ Loop
  │
  └── False ──→ Exit
```

The loop node decides whether another iteration should execute.

Each iteration evaluates the predicate against the current workflow context.

---

# Why Use Loops?

Loops are useful when the same workflow logic must execute repeatedly.

Common examples include:

* processing collections
* processing batches
* polling external systems
* waiting for background operations
* validating data repeatedly
* processing paginated results
* performing repeated calculations
* incremental synchronization

Without loops, repeated workflow logic would need to be represented by duplicated nodes or manually constructed graph cycles.

---

# Loop Execution Flow

During execution, the loop evaluates its predicate.

```text
Evaluate Predicate
        │
   ┌────┴────┐
 True       False
   │           │
   ▼           ▼
 Body         Exit
   │
   ▼
 Loop
```

When the predicate returns `True`, execution enters the loop body.

After the body completes, execution returns to the loop node and the predicate is evaluated again.

When the predicate returns `False`, execution leaves the loop.

---

# Creating a Loop

The workflow builder exposes a `loop()` method that accepts a predicate.

```python
builder.loop(
    predicate=lambda context: ...,
)
```

The predicate receives the current workflow context and must return a Boolean value.

For example:

```python
builder.loop(
    predicate=lambda context: context.variables["counter"] < 5,
)
```

The predicate is evaluated during workflow execution rather than when the workflow is constructed.

> **Important:** The loop argument is called `predicate`. It is distinct from the `condition()` API used for conditional branching.

---

# Loop Predicates

The predicate determines whether another iteration should execute.

For example:

```python
lambda context: context.variables["counter"] < 5
```

The predicate may produce:

```text
counter = 0 → True
counter = 1 → True
counter = 2 → True
counter = 3 → True
counter = 4 → True
counter = 5 → False
```

The loop continues while the predicate is `True`.

Once the predicate becomes `False`, execution follows the loop's exit path.

---

# Workflow Context

Loop predicates operate on the current `WorkflowContext`.

Conceptually:

```text
Workflow Context

├── Variables
├── Agent Results
├── Tool Results
└── Execution State
```

The predicate reads the state required to determine whether another iteration should occur.

Because the same workflow context is used throughout execution, updates made during one iteration can be observed by later iterations.

---

# Loop State

A loop normally depends on state that changes as execution progresses.

For example:

```text
counter = 0

↓

Evaluate Predicate

↓

counter < 5

↓

True

↓

Loop Body

↓

counter += 1

↓

Evaluate Predicate
```

The body must make progress toward the terminating state.

If the state used by the predicate never changes, the workflow may continue indefinitely.

---

# Loop Body and Exit

A loop has two logical execution paths:

```text
Loop
 │
 ├── True  → Loop Body
 │
 └── False → Exit
```

The loop body performs the work for one iteration.

After the body completes, execution must eventually return to the loop node so that the predicate can be evaluated again.

Conceptually:

```text
                 Loop
                   │
             Evaluate Predicate
              ┌────┴────┐
           True        False
             │            │
             ▼            ▼
          Body           Exit
             │
             └────────→ Loop
```

This cycle is what makes the workflow iterative.

---

# Shared Workflow Context

Each iteration operates on the workflow's current context.

```text
Iteration 1
     │
     ▼
Workflow Context
     │
     ▼
Iteration 2
     │
     ▼
Workflow Context
     │
     ▼
Iteration 3
```

Values updated during an iteration remain available to subsequent nodes and iterations unless they are explicitly changed or removed.

This makes loops suitable for incremental processing.

---

# Example: Processing a Collection

A common loop pattern processes items one at a time.

```text
Initialize Items
       │
       ▼
     Loop
       │
       ▼
Process Current Item
       │
       ▼
Advance Position
       │
       ▼
     Loop
```

The predicate can determine whether additional items remain.

Conceptually:

```python
lambda context: (
    context.variables["index"]
    < len(context.variables["items"])
)
```

The loop body should update the index after processing the current item.

For example:

```text
index = 0
    ↓
Process items[0]
    ↓
index = 1
    ↓
Process items[1]
    ↓
...
```

---

# Example: Polling an External Service

A loop can repeatedly check the state of an asynchronous operation.

```text
Check Status
     │
     ▼
   Loop
     │
     ▼
Completed?
  ┌──┴──┐
 No    Yes
  │      │
  ▼      ▼
Wait    Exit
  │
  └────→ Loop
```

The workflow context can store the current operation status.

The predicate evaluates that status.

When the operation is complete, the predicate returns `False` and the workflow exits the loop.

For production polling workflows, a delay or backoff mechanism should normally be included so that the workflow does not repeatedly query the external service without pause.

---

# Example: Batch Processing

Loops can process records incrementally.

```text
Load Batch
     │
     ▼
   Loop
     │
     ▼
Process Batch
     │
     ▼
Load Next Batch
     │
     ▼
   Loop
```

The predicate determines whether additional batches remain.

This approach avoids processing a large collection in a single workflow step.

---

# Example: Repeated Validation

A workflow may repeat validation until a desired state is reached.

```text
Prepare Data
     │
     ▼
   Loop
     │
     ▼
Validate
     │
     ▼
Update Data
     │
     └────→ Loop
```

The predicate evaluates the current validation state.

```text
Valid?

├── True  → Exit
└── False → Continue Iteration
```

The loop should have a defined maximum or another reliable termination mechanism when external or unpredictable state is involved.

---

# Loops vs Retry

Loops and retries both involve repeated execution, but they solve different problems.

| Loop                               | Retry                            |
| ---------------------------------- | -------------------------------- |
| Repeats intentional workflow logic | Repeats failed node execution    |
| Controlled by a predicate          | Controlled by retry policy       |
| Uses workflow state                | Triggered by execution failure   |
| Part of normal workflow design     | Reliability mechanism            |
| May execute many iterations        | Usually limited by attempt count |

Use a **loop** when repetition is part of the workflow's intended business logic.

Use **retry** when an operation fails and should be attempted again according to a reliability policy.

A retry should not normally be implemented by wrapping the failed operation in a general-purpose loop.

---

# Nested Loops

Loops can be combined with other workflow structures, including nested loops.

Conceptually:

```text
Outer Loop
    │
    ▼
Inner Loop
    │
    ▼
Process
    │
    ▼
Continue
```

Nested loops can be useful for hierarchical data.

For example:

```text
For each customer
    ↓
    For each order
        ↓
        Process Order
```

However, excessive nesting can make workflows difficult to understand and debug.

Prefer smaller workflow stages when nested iteration becomes complicated.

---

# Exiting a Loop

Every loop should have a clear termination condition.

```text
Predicate
   │
   ├── True  → Body → Loop
   │
   └── False → Exit
```

The predicate should eventually become `False` under normal execution.

A loop without a reachable exit can cause the workflow to execute indefinitely.

---

# Avoiding Infinite Loops

The loop body should normally update the state used by the predicate.

For example:

```text
counter += 1
     │
     ▼
Evaluate Predicate
     │
     ▼
counter < 5
```

With:

```python
lambda context: context.variables["counter"] < 5
```

the workflow eventually reaches:

```text
counter = 5

↓

predicate = False

↓

Exit
```

If `counter` never changes, the predicate may remain `True` indefinitely.

Good loop design therefore requires:

1. a clearly defined exit condition
2. state that changes during execution
3. progress toward termination
4. appropriate safeguards for long-running operations

---

# Maximum Iterations

For loops that depend on external systems or unpredictable data, a maximum iteration limit can provide an additional safety mechanism.

Conceptually:

```text
Loop

├── Predicate
│
└── Iteration Count
        │
        ├── Limit reached → Exit/Error
        └── Limit not reached → Continue
```

This prevents an unexpected state from causing an unbounded workflow execution.

The exact maximum-iteration configuration should follow the implemented BindAI workflow API.

---

# Combining Loops with Other Nodes

Loops can contain multiple workflow nodes.

For example:

```text
Loop
  │
  ▼
Agent
  │
  ▼
Tool
  │
  ▼
Update Context
  │
  └────→ Loop
```

Each iteration can therefore perform several operations before returning to the loop.

This is useful for workflows where each iteration requires reasoning, deterministic processing, and state updates.

---

# Loops with Conditions

Conditions can also be used inside a loop.

```text
Loop
  │
  ▼
Agent
  │
  ▼
Condition
  │
  ├── Continue Processing
  │        │
  │        └────→ Loop
  │
  └── Stop Processing
           │
           └────→ Exit
```

This allows the workflow to make decisions during each iteration.

The loop controls repetition, while the condition controls decisions within the iteration.

---

# Common Use Cases

Loop nodes are useful for:

* collection processing
* batch processing
* pagination
* polling external services
* repeated validation
* incremental synchronization
* waiting for state changes
* iterative business processes
* multi-step processing of records

---

# Error Handling

A failure inside a loop body should follow the workflow's configured error-handling behavior.

Possible strategies include:

```text
Loop Body Error

├── Stop Workflow
├── Retry Failed Node
├── Error Branch
└── Continue
```

The exact behavior depends on the node and workflow execution configuration.

Use retry policies for transient failures rather than relying on loop iteration as a retry mechanism.

---

# Testing Loops

Loop behavior should be tested with several scenarios.

### Zero iterations

The predicate is initially `False`.

```text
Loop

↓

False

↓

Exit
```

The body should not execute.

### One iteration

The predicate is initially `True`, but becomes `False` after one body execution.

```text
Loop

↓

True

↓

Body

↓

Loop

↓

False

↓

Exit
```

### Multiple iterations

The predicate remains `True` for several iterations before becoming `False.

### Non-terminating state

The predicate never becomes `False`.

The workflow should have an appropriate safeguard such as a maximum iteration limit, timeout, or cancellation mechanism.

---

# Best Practices

* Define a clear exit condition.
* Make sure the predicate can eventually become `False`.
* Update the state used by the predicate.
* Keep loop bodies focused.
* Avoid unnecessary nested loops.
* Use retry policies for transient execution failures.
* Consider maximum iteration limits for untrusted or external state.
* Use delays or backoff when polling external services.
* Keep loop state in the workflow context when it must persist between iterations.
* Test zero, one, multiple, and non-terminating iteration scenarios.
* Monitor long-running workflows containing loops.

---

# Loop Design Pattern

A reliable loop generally follows this pattern:

```text
Initialize State

↓

Loop

↓

Evaluate Predicate

├── False → Exit
│
└── True
      ↓
   Execute Body
      ↓
   Update State
      ↓
   Loop
```

The important property is that the loop body changes the state used by the predicate.

That creates measurable progress toward termination.

# Summary

Loop nodes allow BindAI workflows to repeat execution while a predicate evaluates to `True`.

The predicate receives the current `WorkflowContext` and determines whether execution enters the loop body or follows the exit path.

Each iteration operates on the current workflow state, allowing the loop body to update variables and make progress toward termination.

Loops are useful for collection processing, batch operations, pagination, polling, repeated validation, and other intentional iterative workflows.

For transient execution failures, use retry policies rather than loops.

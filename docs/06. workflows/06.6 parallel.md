# Parallel Execution

Parallel execution allows a BindAI workflow to execute multiple independent branches and then continue through a Join point.

In BindAI V1, parallel execution is represented by **Parallel** and **Join** workflow nodes.

The implemented pattern is:

```text
             +--> Branch A --+
             |               |
Start --> Parallel           +--> Join --> Continue
             |               |
             +--> Branch B --+
```

Parallel branches are executed as part of the same workflow instance.

---

# What Is Parallel Execution?

Parallel execution splits workflow execution into multiple branches.

For example:

```text
Start
  |
  v
Parallel
 /      \
A        B
 \      /
  \    /
   Join
    |
    v
   End
```

The Parallel node starts the configured branches.

The Join node provides the synchronization point where the workflow waits for the required branches before continuing.

---

# Parallel and Join Nodes

BindAI V1 provides two separate workflow operations for this pattern:

* **Parallel** — creates parallel execution branches.
* **Join** — synchronizes the branches before downstream execution continues.

Conceptually:

```text
Parallel
 /     \
A       B
 \     /
  Join
```

This separation keeps branch execution and synchronization as two distinct parts of the workflow graph.

---

# Basic Parallel Workflow

A simple workflow can contain two independent branches:

```text
Start
  |
  v
Parallel
 /      \
Agent   Tool
 \      /
  Join
   |
   v
 End
```

The branches can perform different operations.

After the branches reach the Join node, execution continues to the next connected operation.

---

# Multiple Parallel Branches

Parallel execution can contain more than two branches.

For example:

```text
             +--> Agent A --+
             |              |
Start --> Parallel --> Agent B --> Join --> End
             |              |
             +--> Agent C --+
```

Each branch is part of the same workflow execution.

The Join node provides the point at which the branches converge again.

---

# Independent Work

Parallel execution is intended for operations that can execute independently.

For example:

```text
             +--> Agent A
             |
Start --> Parallel --> Agent B
             |
             +--> Tool
```

These operations can perform separate work before their results are needed by a later stage.

A dependent operation should remain sequential.

For example:

```text
Agent A
  |
  v
Agent B
```

If Agent B requires the output of Agent A, there is no reason to place those operations in independent parallel branches.

---

# Parallel Agent Execution

Agent nodes can be placed on separate parallel branches.

For example:

```text
             +--> Research Agent --+
             |                     |
Start --> Parallel                  +--> Join
             |                     |
             +--> Analysis Agent --+
```

The agents execute as independent branches of the workflow.

A later node can continue after the Join.

---

# Parallel Tool Execution

Tool nodes can also participate in parallel branches.

For example:

```text
             +--> Tool A --+
             |             |
Start --> Parallel         +--> Join --> End
             |             |
             +--> Tool B --+
```

This is useful when the tools perform independent operations.

Each branch can produce its own workflow result.

---

# Combining Agents and Tools

Parallel branches can contain different node types.

For example:

```text
                 +--> Agent --+
                 |            |
Start --> Parallel             +--> Join --> End
                 |            |
                 +--> Tool ---+
```

A more complex workflow can contain several operations inside each branch:

```text
                 +--> Agent --> Tool --+
                 |                     |
Start --> Parallel                      +--> Join --> End
                 |                     |
                 +--> Agent --> Tool --+
```

The branches remain independent until they reach the Join.

---

# Join Behavior

The Join node is the synchronization point for parallel branches.

Conceptually:

```text
Branch A -------+
                |
Branch B -------+----> Join ----> Next Node
                |
Branch C -------+
```

The workflow does not proceed beyond the Join until the required parallel branches have completed their execution path.

This allows downstream nodes to depend on the completed parallel stage.

---

# Parallel Branch Results

Each branch can produce its own workflow values.

For example:

```text
Parallel
 /      \
Agent A  Agent B
 |        |
 v        v
result_a result_b
 \        /
  \      /
    Join
```

The branch results remain available as workflow state.

A downstream node can then use the values produced by the branches.

For example:

```text
result_a
   |
   +------+
          |
result_b -+--> Agent --> final_result
```

The workflow can therefore use Parallel and Join to prepare information for a later operation.

---

# Workflow State

Parallel branches execute within the same workflow instance.

Workflow state is therefore available to the branches.

For example:

```text
                 Workflow State
                  /          \
                 v            v
             Branch A      Branch B
                 |            |
                 +-----+------+
                       |
                      Join
```

Branches should use distinct output variables when they produce independent results.

For example:

```text
agent_result
tool_result
```

This makes the values available to later workflow operations without relying on branch execution order.

---

# Parallel Branch Ordering

Parallel branches should not be treated as a sequential list.

For example:

```text
Parallel
 /   |   \
 A   B   C
```

The workflow should not rely on:

```text
A finishes first
B finishes second
C finishes third
```

The Join provides the synchronization boundary instead.

This is important when designing workflows that consume results from multiple branches.

---

# Sequential vs Parallel

Use sequential execution when one operation depends on another:

```text
A
|
v
B
|
v
C
```

Use parallel execution when operations are independent:

```text
     +--> A --+
     |       |
     +--> B -+--> Join
     |       |
     +--> C -+
```

The distinction is based on data and execution dependencies.

---

# Parallel with Conditions

A parallel branch can contain a Condition node.

For example:

```text
                 +--> Agent --> Condition --+
                 |                          |
Start --> Parallel                           +--> Join
                 |                          |
                 +--> Tool -----------------+
```

The condition controls execution inside that branch.

The Join remains responsible for synchronization between the parallel branches.

---

# Parallel with Loops

A branch can also contain loop execution.

For example:

```text
                 +--> Loop --> Tool --+
                 |                    |
Start --> Parallel                     +--> Join --> End
                 |                    |
                 +--> Agent ----------+
```

The Join waits for the configured branches to reach the synchronization point.

This allows more complex workflow structures while keeping the parallel branches independent.

---

# Parallel with Human Tasks

A parallel branch can contain a Human Task.

For example:

```text
                 +--> Agent -----------+
                 |                     |
Start --> Parallel                      +--> Join --> End
                 |                     |
                 +--> Human Task ------+
```

The workflow branch containing the Human Task can wait for the human action.

The parallel stage therefore remains active until the required branches can reach the Join.

---

# Parallel Execution and Connections

Connection-backed tools can be used inside parallel branches.

For example:

```text
                 +--> Webhook Tool --+
                 |                   |
Start --> Parallel                    +--> Join --> End
                 |                   |
                 +--> Agent ---------+
```

In BindAI V1, the implemented external connection available through Studio is the Webhook connection.

The Webhook connection is exposed to workflows through a connection-backed tool.

---

# Parallel Execution and Memory

Agents running in parallel branches can use configured Memory.

Conceptually:

```text
                 +--> Agent --> Memory
                 |
Start --> Parallel
                 |
                 +--> Agent --> Memory
```

Memory is associated with agent execution.

Parallel execution itself is responsible for coordinating the workflow branches.

---

# Parallel Execution and Knowledge

Agents running in parallel branches can also use configured Knowledge.

For example:

```text
                 +--> Agent --> Knowledge
                 |
Start --> Parallel
                 |
                 +--> Agent --> Knowledge
```

Knowledge remains part of agent execution.

The Parallel and Join nodes coordinate the workflow structure around those agents.

---

# Error Behavior

Parallel execution can contain branches that produce failed results.

The workflow execution result records the execution state and errors produced during workflow processing.

A workflow should therefore be designed so that downstream operations handle the results produced by its branches appropriately.

For example:

```text
             +--> Branch A --+
             |               |
Start --> Parallel           +--> Join --> Next
             |               |
             +--> Branch B --+
```

The exact failure path should follow the implemented workflow execution behavior rather than assuming a separate parallel-specific retry or recovery mechanism.

---

# Parallel Execution and Tool Results

Tool nodes produce `ToolResult` values.

For example:

```text
             +--> Tool A --> result_a --+
             |                          |
Start --> Parallel                       +--> Join
             |                          |
             +--> Tool B --> result_b --+
```

The workflow can preserve the branch results in workflow state.

The Studio API converts runtime `ToolResult` values into JSON-safe responses at the API boundary.

This keeps the runtime result model separate from the HTTP representation.

---

# Parallel Execution and Workflow Persistence

BindAI Studio persists workflow instances.

This includes workflow state associated with an executing workflow instance.

A parallel workflow therefore remains part of the same persisted workflow execution:

```text
Workflow Instance
       |
       v
   Parallel
    /    \
 Branch A Branch B
    \    /
      Join
       |
       v
    Continue
```

Persistence is handled by the workflow store used by the Studio runtime.

---

# Visual Studio Workflow

BindAI Studio represents Parallel and Join as workflow nodes in the visual workflow editor.

A typical graph can therefore be constructed visually as:

```text
Start
  |
  v
Parallel
 /      \
Agent   Tool
 \      /
  Join
   |
   v
 End
```

The saved workflow definition contains the nodes and their connections.

The Studio runtime then loads the definition and executes it.

# Parallel Workflow Example

A complete V1 workflow can combine several implemented capabilities:

```text
                    +--> Agent --------+
                    |                  |
Start --> Parallel -+--> Tool ---------+--> Join --> Human Task --> End
                    |                  |
                    +--> Agent --------+
```

For example:

1. The workflow starts.
2. Parallel creates independent branches.
3. Each branch performs its configured operation.
4. The branches reach Join.
5. Execution continues after synchronization.
6. A Human Task can pause the workflow if required.
7. The workflow resumes after the human action.
8. The workflow reaches End.

This combines Parallel/Join with other implemented V1 workflow capabilities.

# Testing Parallel Workflows

Parallel execution should be tested as an actual workflow rather than only as a graph structure.

Important V1 cases include:

* Two parallel branches
* Multiple parallel branches
* Agent branches
* Tool branches
* Mixed Agent and Tool branches
* Branches producing separate output variables
* Join after all required branches
* Parallel branches containing Conditions
* Parallel branches containing Loops
* Parallel branches containing Human Tasks
* Connection-backed tools inside a branch
* Persisted workflow instances

The important verification is that the workflow reaches the Join correctly and continues with the expected workflow state.

---

# Deterministic Join Behavior

The Join node provides a deterministic synchronization point for the workflow.

For example:

```text
Branch A ----+
             |
Branch B ----+--> Join --> Next
             |
Branch C ----+
```

The purpose of Join is not to impose an ordering on the branches.

Instead, it establishes the point at which the workflow can continue after the required branches have completed.

# API Accuracy

The workflow documentation describes the implemented **Parallel** and **Join** workflow capabilities.

It intentionally does not invent a separate public API such as:

```python
ParallelNode(...)
JoinNode(...)
```

or builder methods such as:

```python
parallel(...)
join(...)
```

unless those exact APIs are exposed by the installed BindAI release.

The supported workflow behavior is represented by the workflow definition and runtime used by BindAI Studio.

# Summary

Parallel execution allows BindAI workflows to execute independent branches and synchronize them before continuing.

The core V1 pattern is:

```text
             +--> Branch A --+
             |               |
Start --> Parallel           +--> Join --> Continue
             |               |
             +--> Branch B --+
```

Parallel is responsible for creating the independent execution branches.

Join provides the synchronization point.

Parallel workflows can contain the other implemented V1 workflow capabilities, including Agents, Tools, Conditions, Loops, Human Tasks, and connection-backed tools.

The key design rule is:

> **Use Parallel for independent work and Join when downstream execution depends on the completed branches.**

# Parallel Execution

Parallel execution allows a workflow to schedule multiple outgoing workflow branches from the same node.

In BindAI, a `ParallelNode` acts as a branching point. The node itself does not execute the branches. Instead, the workflow executor schedules every node listed in the Parallel node's `next_nodes`.

Parallel execution is useful when multiple workflow paths can progress independently.

---

# What is Parallel Execution?

A Parallel node represents a point where workflow execution branches into multiple paths.

Conceptually:

```text
             Parallel
          ┌────┼────┐
          │    │    │
          ▼    ▼    ▼
      Branch A Branch B Branch C
```

The Parallel node does not contain branch execution logic itself. It simply allows the executor to schedule its outgoing nodes.

---

# Why Use Parallel Execution?

Parallel branches are useful when a workflow needs to perform independent operations.

Common examples include:

* running multiple agents
* querying different services
* processing independent documents
* retrieving information from multiple sources
* performing separate validation tasks
* generating independent results

Branches can then converge later using a Join node.

---

# Parallel Workflow

A typical workflow can be structured like this:

```text
Start

↓

Parallel

↙          ↘

Branch A    Branch B

↓           ↓

Join

↓

End
```

The Parallel node provides the branching point.

The Join node can then synchronize the branches before execution continues.

---

# Creating Parallel Branches

A Parallel node can have multiple outgoing connections.

For example:

```text
Parallel

↙      ↓      ↘

Branch 1

Branch 2

Branch 3
```

The executor schedules the nodes contained in `next_nodes`.

The Parallel node itself does not create threads, tasks, or separate workflow contexts.

---

# ParallelNode

The Parallel node is intentionally simple.

Conceptually, its execution is:

```python
def execute(context):
    return context
```

The executor is responsible for scheduling the node's outgoing connections.

This means that parallel behavior is part of workflow execution rather than logic contained inside the Parallel node.

---

# Join Node

A Join node provides synchronization for parallel branches.

A Join node is created with an expected number of branch arrivals:

```python
JoinNode(
    node_id="join",
    expected=2,
)
```

The `expected` value determines how many arrivals are required before the Join allows execution to continue.

Conceptually:

```text
Branch A
   ↓
   Join ──→ Continue
   ↑
Branch B
```

---

# Join Synchronization

The Join node maintains arrival state in the workflow context.

Each time a branch reaches the Join:

```text
current arrivals += 1
```

If the expected number of branches has not arrived, the Join sets the workflow context to waiting.

For example, with:

```python
expected=3
```

the execution behaves conceptually like:

```text
Branch A → Join → 1 / 3 → Wait

Branch B → Join → 2 / 3 → Wait

Branch C → Join → 3 / 3 → Continue
```

Once all expected branches arrive, the Join clears its state and allows execution to continue.

---

# Join State

Join progress is stored in the shared workflow context.

Conceptually:

```text
context.join_state

join_1 → 1
```

After another branch arrives:

```text
context.join_state

join_1 → 2
```

When the expected number of branches has arrived, the Join removes its entry from `join_state`.

This allows the same Join node to be used again during future workflow execution.

---

# Waiting Behavior

When a Join has not received all expected branches, it sets:

```python
context.waiting = True
```

The executor recognizes this state and pauses the workflow's normal progression.

Once the expected number of branches has arrived, the Join sets:

```python
context.waiting = False
```

Execution can then continue.

---

# Shared Workflow Context

Parallel branches use the workflow's shared execution context.

This means branches do not automatically receive isolated copies of:

* workflow variables
* events
* join state
* execution state

For example:

```text
Workflow Context
       │
   ┌───┴───┐
   ↓       ↓
Branch A  Branch B
```

Because the context is shared, branches should avoid conflicting updates to the same variables.

Prefer separate variables when independent branches produce separate results:

```text
result_a

result_b
```

A later node can use those variables after synchronization.

---

# Result Handling

The Join node does not merge branch results itself.

It only tracks how many branches have reached the Join.

For example:

```text
Branch A → result_a
                  \
                   → Join → Next Node
                  /
Branch B → result_b
```

The variables remain part of the shared workflow context.

Any downstream node that needs to combine or interpret those values is responsible for doing so.

---

# Parallel vs Sequential

| Sequential                               | Parallel                                                     |
| ---------------------------------------- | ------------------------------------------------------------ |
| One workflow path continues at a time    | Multiple outgoing paths are scheduled                        |
| Simple control flow                      | Multiple branches require synchronization when they converge |
| No Join required for ordinary sequencing | Join can be used to wait for expected branches               |
| Suitable for dependent operations        | Suitable for independent operations                          |

Use sequential execution when one operation depends directly on another.

Use parallel branching when independent paths can be scheduled separately.

---

# Independent Branches

Good candidates for parallel branches include:

* independent agent operations
* separate API calls
* independent document processing
* separate retrieval operations
* independent validation tasks

For example:

```text
Parallel

↙          ↘

Search     Analyze

↓          ↓

Join

↓

Continue
```

The branches do not need each other's output before they reach the Join.

---

# Dependent Operations

Parallel branches should not be used when one branch requires the output of another branch.

For example:

```text
Branch A
   ↓
result_a
   ↓
Branch B requires result_a
```

This is better represented as sequential execution:

```text
Branch A

↓

Branch B
```

Keeping dependencies explicit makes workflow behavior easier to understand.

---

# Error Handling

Parallel nodes do not define a separate branch-failure policy.

Node failures are handled by the workflow executor.

The executor can apply the configured retry policy when a node raises an exception. If no retry policy is available, the workflow fails through the executor's normal failure handling.

Therefore, Parallel execution should not be interpreted as automatically providing:

* partial-result continuation
* branch-specific error handlers
* automatic failure isolation
* automatic result merging

Those behaviors require additional workflow design or executor functionality.

---

# Execution Model

The current execution model can be summarized as:

```text
Parallel Node
      ↓
Executor schedules next_nodes
      ↓
┌─────┼─────┐
↓     ↓     ↓
A     B     C
└─────┼─────┘
      ↓
    Join
      ↓
Count arrivals
      ↓
Expected reached?
   ↙          ↘
 No            Yes
 ↓              ↓
Wait          Continue
```

The Parallel node is therefore a scheduling point, while the Join node is a synchronization point.

---

# Typical Use Cases

Parallel branching is useful for:

* multi-agent workflows
* independent API operations
* separate document processing
* independent retrieval tasks
* parallel validation
* independent data preparation
* workflows that need multiple paths to converge later

---

# Best Practices

* Use parallel branches for independent operations.
* Use a Join when multiple branches must synchronize.
* Set the Join `expected` count to match the number of required arrivals.
* Give independent branches separate output variables when possible.
* Avoid conflicting writes to shared workflow variables.
* Keep dependencies explicit.
* Do not assume that the Parallel node itself creates threads or asynchronous tasks.
* Use the executor's retry configuration for transient node failures.
* Keep branch structures easy to understand and maintain.

---

# Summary

A `ParallelNode` provides a branching point in a BindAI workflow.

The node itself does not execute branches concurrently. Instead, the workflow executor schedules the nodes listed in `next_nodes`.

A `JoinNode` can synchronize those branches by counting arrivals against its configured `expected` value. Until all expected branches arrive, the Join places the workflow in a waiting state.

Because branches use the shared workflow context, workflows should manage variables carefully and avoid conflicting updates.

Together, Parallel and Join nodes provide a simple mechanism for branching and synchronization within BindAI workflows.

# Conditions

Condition nodes allow a workflow to make decisions during execution.

Instead of always following a fixed sequence, a condition evaluates the current workflow state and routes execution to different branches based on the result.

Conditions make workflows dynamic, predictable, and easy to maintain.

---

# What is a Condition?

A condition evaluates a Boolean expression.

If the result is `True`, one branch executes.

If the result is `False`, a different branch executes.

```text
Workflow Context

↓

Condition

↙         ↘

True      False
```

Only the selected branch continues execution.

---

# Why Use Conditions?

Without conditions, workflows always execute the same sequence of steps.

Conditions allow workflows to:

- make business decisions
- validate input
- choose different agents
- skip unnecessary work
- handle success and failure differently
- implement approval flows
- route requests dynamically

---

# Creating a Condition

A condition is created by supplying a predicate function.

```python
builder.condition(
    lambda context: context.variables.get("approved"),
)
```

The predicate receives the workflow execution context and returns either `True` or `False`.

---

# Using Workflow Variables

Conditions usually evaluate values created by previous workflow nodes.

Example:

```text
approved = True

↓

Condition

↓

Approved Branch
```

Variables are commonly produced by:

- agents
- tools
- human tasks
- previous workflow steps

---

# Example

Suppose an agent reviews a purchase request.

```text
Review Agent

↓

approved = True

↓

Condition

↓

Continue Purchase
```

If approval fails:

```text
Review Agent

↓

approved = False

↓

Condition

↓

Reject Purchase
```

---

# Branching Logic

A condition creates two execution paths.

```text
Agent

↓

Condition

↙            ↘

Approved     Rejected
```

Each branch may contain completely different workflow logic.

---

# Multiple Conditions

Workflows often contain more than one decision.

```text
Start

↓

Condition

↓

Agent

↓

Condition

↓

Tool

↓

End
```

Each condition influences the remaining execution path.

---

# Chaining Conditions

Conditions can be chained together to create more advanced decision trees.

```text
Condition A

↓

Condition B

↓

Condition C
```

This allows workflows to represent increasingly sophisticated business processes.

---

# Nested Decisions

Conditions may also appear inside branches.

```text
Condition

↙          ↘

True      False

↓

Condition

↓

Continue
```

Nested conditions make it possible to model complex workflows while keeping each individual decision simple.

---

# Common Use Cases

Condition nodes are commonly used for:

- approval workflows
- confidence thresholds
- validation checks
- payment status
- inventory availability
- customer type
- user permissions
- feature flags
- workflow routing

---

# Condition vs Prompt Logic

Business decisions should usually be implemented as workflow conditions rather than hidden inside prompts.

| Prompt Logic | Condition Node |
|--------------|----------------|
| Hidden inside instructions | Explicit workflow step |
| Difficult to debug | Easy to inspect |
| Hard to reuse | Reusable |
| Mixed responsibilities | Clear separation |

Keeping orchestration outside prompts results in more predictable workflows.

---

# Accessing the Execution Context

Condition predicates receive the workflow execution context.

Example:

```python
builder.condition(
    lambda context: context.variables.get("score", 0) >= 80,
)
```

The context may contain:

- workflow variables
- tool outputs
- agent results
- metadata
- execution state

---

# Combining Conditions

Predicates can combine multiple values.

Example:

```python
builder.condition(
    lambda context: context.variables.get("approved") and context.variables.get("payment_received"),
)
```

Complex logic is possible, although simpler predicates are usually easier to maintain.

---

# Error Handling

Conditions should evaluate predictable values.

If required variables may not exist:

- provide default values
- validate inputs earlier
- handle missing values explicitly

Example:

```python
builder.condition(
    lambda context: context.variables.get("approved", False),
)
```

---

# Best Practices

- Keep predicates short and readable.
- Base decisions on workflow variables instead of prompt text.
- Keep business logic outside language model prompts.
- Use descriptive variable names.
- Prefer several simple conditions over one large expression.
- Keep both branches easy to understand.
- Validate required data before evaluating conditions.

---

# Summary

Condition nodes give BindAI workflows the ability to make runtime decisions.

By evaluating the execution context and selecting the appropriate branch, conditions enable workflows to adapt dynamically while keeping orchestration clear, reusable, and separate from language model reasoning.

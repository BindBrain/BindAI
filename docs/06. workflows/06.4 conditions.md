# Conditions

Conditions allow a workflow to make decisions during execution.

Instead of always following a fixed sequence, a workflow can evaluate runtime information and select different execution paths.

Conceptually:

```text
Workflow State

↓

Condition

↙        ↘

True     False
```

Only the selected path continues execution.

> **Current status:** The condition model described here represents the workflow architecture. The concrete condition API should only be documented as available after it has been implemented and verified in BindAI.

---

# What is a Condition?

A condition evaluates a Boolean expression or predicate.

The result determines which execution path should be selected.

```text
Input State

↓

Evaluate Predicate

├── True  → Branch A
└── False → Branch B
```

A condition therefore acts as a decision point within the workflow graph.

---

# Why Use Conditions?

Without conditions, a workflow generally follows the same execution path for every input.

Conditions allow workflows to:

* make business decisions
* validate input
* select different agents
* skip unnecessary work
* handle success and failure differently
* implement approval flows
* route requests dynamically

---

# Condition Lifecycle

A typical condition follows this lifecycle:

```text
Receive Workflow Context

↓

Evaluate Predicate

↓

Boolean Result

↓

Select Branch

↓

Continue Execution
```

The condition itself should normally remain focused on making the decision. The nodes on each branch perform the resulting work.

---

# Using Workflow State

Conditions usually make decisions using values produced by previous workflow steps.

For example:

```text
Review Agent

↓

approved = True

↓

Condition

↓

Approved Branch
```

If the value is false:

```text
Review Agent

↓

approved = False

↓

Condition

↓

Rejected Branch
```

The workflow state therefore provides the input used by the decision.

---

# Predicate Functions

A predicate is a function that evaluates workflow state and returns a Boolean value.

Conceptually:

```python
def is_approved(context):
    return context.variables.get("approved", False)
```

A builder API could then use that predicate:

```python
builder.condition(
    is_approved,
)
```

The exact BindAI method name and context interface should be verified against the current workflow implementation.

---

# Example

Consider a purchase approval workflow:

```text
Start

↓

Review

↓

Condition

↙              ↘

Approved       Rejected

↓              ↓

Process        Reject

↘              ↙

End
```

The review step produces the information required by the condition.

The condition determines which branch should execute.

---

# Branching Logic

A condition normally creates two logical paths:

```text
Agent

↓

Condition

↙            ↘

Approved     Rejected
```

Each branch can contain completely different workflow operations.

For example:

```text
Condition

├── Approved
│   └── Payment Tool
│
└── Rejected
    └── Notification Tool
```

---

# Multiple Conditions

A workflow can contain multiple decision points.

```text
Start

↓

Condition A

↓

Agent

↓

Condition B

↓

Tool

↓

End
```

Each condition evaluates the state available at that point in execution.

This allows the workflow to make decisions progressively rather than evaluating every possible decision at the beginning.

---

# Chained Conditions

Conditions can form decision trees.

```text
Condition A

├── True
│   └── Condition B
│
└── False
    └── Condition C
```

For example:

```text
Is Customer Active?

├── Yes
│   └── Is Payment Valid?
│       ├── Yes → Process Order
│       └── No  → Request Payment
│
└── No
    └── Reject Order
```

Keeping each decision separate makes the workflow easier to understand and test.

---

# Nested Decisions

A condition can lead to another condition.

```text
Condition

↙          ↘

True      False

↓

Condition

↓

Continue
```

Nested decisions are useful for complex business processes, but excessive nesting can make workflows difficult to maintain.

When decision trees become large, consider splitting them into smaller workflow stages.

---

# Common Use Cases

Condition nodes are useful for:

* approval workflows
* validation checks
* confidence thresholds
* payment status
* inventory availability
* customer classification
* user permissions
* feature flags
* workflow routing
* error handling

---

# Condition vs Prompt Logic

Business decisions should generally be represented explicitly in the workflow rather than hidden inside language-model instructions.

| Prompt Logic               | Condition                    |
| -------------------------- | ---------------------------- |
| Hidden inside instructions | Explicit workflow step       |
| Difficult to inspect       | Easy to inspect              |
| Harder to test             | Easier to test               |
| Depends on model behavior  | Deterministic predicate      |
| Mixed with reasoning       | Separate orchestration logic |

For example, instead of asking an agent:

```text
If the purchase is approved, continue.
Otherwise reject it.
```

the workflow can represent the decision explicitly:

```text
Review Agent

↓

Condition

├── Approved → Continue
└── Rejected → Stop
```

The agent performs reasoning; the workflow performs orchestration.

# Accessing Execution Context

A condition predicate needs access to the relevant workflow state.

A conceptual example is:

```python
def high_score(context):
    return context.variables.get("score", 0) >= 80
```

The execution context may contain information such as:

* workflow variables
* tool results
* agent results
* execution metadata
* runtime state

The exact structure of the BindAI execution context should follow the implemented workflow API.

---

# Combining Conditions

Predicates can combine multiple values.

For example:

```python
def can_continue(context):
    return (
        context.variables.get("approved", False)
        and context.variables.get("payment_received", False)
    )
```

This allows a branch to depend on multiple pieces of workflow state.

However, large Boolean expressions can become difficult to read.

Prefer several clearly named predicates when the decision becomes complex.

---

# Missing Values

Conditions should handle missing or invalid values predictably.

For example:

```python
def is_approved(context):
    return context.variables.get("approved", False)
```

Using a safe default prevents a missing value from unexpectedly causing the workflow to fail.

For required values, another option is to validate the data before reaching the condition:

```text
Input

↓

Validation

↓

Condition
```

This makes failures easier to diagnose.

---

# Condition Errors

A condition can fail if its predicate raises an exception or receives unexpected data.

A workflow engine should define how such failures are handled.

Possible strategies include:

```text
Condition Error

├── Stop Workflow
├── Retry
├── Error Branch
└── Fallback
```

The actual behavior depends on the workflow execution engine.

Applications should avoid relying on undocumented failure behavior.

---

# Testing Conditions

Conditions should be easy to test independently.

For a predicate such as:

```python
def is_approved(context):
    return context.variables.get("approved", False)
```

test at least:

```text
approved = True

→ True
```

```text
approved = False

→ False
```

```text
approved missing

→ False
```

This ensures the workflow behaves predictably for both expected and edge-case inputs.

---

# Condition Design

Good condition predicates should be:

* deterministic
* short
* readable
* independently testable
* based on explicit workflow state

Avoid putting large amounts of business logic directly inside a condition.

Instead:

```text
Prepare Data

↓

Evaluate Decision

↓

Condition

↓

Execute Branch
```

This keeps responsibilities separated.

---

# Best Practices

* Keep predicates short and readable.
* Base decisions on explicit workflow state.
* Keep deterministic business logic outside model prompts.
* Use descriptive variable names.
* Prefer several simple conditions over one large expression.
* Make both branches easy to understand.
* Validate required data before evaluating conditions.
* Handle missing values explicitly.
* Test true, false, and edge-case outcomes.
* Avoid deeply nested decision trees when possible.
* Document the implemented condition API rather than planned APIs.

# Summary

Conditions provide the decision-making layer of workflow orchestration.

They evaluate runtime workflow state and select the appropriate execution path without requiring business decisions to be hidden inside language-model prompts.

By keeping predicates small, deterministic, and testable, BindAI workflows can implement clear approval, validation, routing, and business-logic decisions while keeping AI reasoning separate from workflow orchestration.

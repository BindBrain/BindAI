# Timeout Policies

Timeout policies protect workflows from running indefinitely.

A timeout defines the maximum amount of time a workflow, node, or operation is allowed to execute before BindAI considers it to have exceeded its execution limit.

Timeouts improve reliability by preventing stalled or excessively long-running tasks from consuming resources forever.

---

# What is a Timeout?

A timeout specifies the maximum execution duration for an operation.

Conceptually:

```text
Start Task

↓

Execute

↓

Time Limit Reached?

      ↙        ↘

     No        Yes

     ↓          ↓

 Continue    Timeout
```

If execution exceeds the configured limit, the timeout policy is triggered.

---

# Why Use Timeouts?

Not every operation completes successfully.

Tasks may become stuck because of:

- unresponsive external services
- slow API responses
- infinite loops
- blocked network requests
- infrastructure failures
- unexpected system behavior

Timeouts prevent these situations from blocking the rest of the workflow.

---

# Execution Timeline

A timeout measures elapsed execution time.

```text
Start

↓

Running

↓

Running

↓

Time Limit

↓

Timeout
```

If the operation finishes before the limit, the workflow continues normally.

---

# Configuring a Timeout

BindAI provides a timeout policy object.

Example:

```python
TimeoutPolicy(
    seconds=30,
    fail_workflow=True,
)
```

A timeout policy typically defines:

- maximum execution duration
- what should happen when the limit is exceeded

---

# Successful Completion

If execution finishes within the configured duration:

```text
Start

↓

Execute

↓

Complete

↓

Continue Workflow
```

The timeout policy is never triggered.

---

# When a Timeout Occurs

If execution exceeds the configured limit:

```text
Start

↓

Execute

↓

Time Limit Reached

↓

Timeout
```

BindAI applies the configured timeout behavior.

---

# Failing the Workflow

Many workflows stop immediately after a timeout.

```text
Timeout

↓

Workflow Failed
```

This prevents downstream steps from executing with incomplete or invalid state.

---

# Continuing After a Timeout

Some workflows may continue after recording the timeout.

```text
Timeout

↓

Record Event

↓

Continue
```

This behavior depends on how the timeout policy has been configured.

---

# Timeouts and External Services

Timeouts are especially important when interacting with external systems.

Examples include:

- REST APIs
- databases
- cloud services
- AI model providers
- file storage systems

External dependencies often have unpredictable response times.

---

# Timeout vs Retry

Timeouts and retries solve different problems.

| Timeout | Retry |
| ------- | ----- |
| Limits execution time | Repeats failed operations |
| Prevents hanging tasks | Handles transient failures |
| Triggered by elapsed time | Triggered after failures |
| Stops stalled execution | Attempts recovery |

Both policies are commonly used together.

---

# Timeout and Retry Together

A common production workflow looks like this.

```text
Execute

↓

Timeout?

↓

Retry

↓

Timeout?

↓

Retry

↓

Failure Handler
```

Retries recover from temporary problems, while timeouts prevent endless waiting.

---

# Timeout vs Loop

Loops intentionally repeat work.

Timeouts prevent loops from running forever.

```text
Loop

↓

Loop

↓

Loop

↓

Timeout

↓

Exit
```

Timeouts provide a safety net when loop exit conditions are never satisfied.

---

# Typical Use Cases

Timeout policies are useful for:

- external API requests
- AI model inference
- document processing
- long-running workflows
- scheduled automation
- network communication
- data synchronization
- background jobs

Any operation with unpredictable execution time can benefit from a timeout.

---

# Monitoring Timeouts

Timeouts should be monitored in production.

Useful metrics include:

- execution duration
- timeout threshold
- workflow identifier
- node identifier
- retry count
- failure frequency

Tracking timeout events helps identify performance bottlenecks and unstable services.

---

# Choosing Timeout Values

Timeout values should match the expected duration of the operation.

Examples:

| Operation | Typical Timeout |
| ---------- | --------------: |
| Simple API request | 5–15 seconds |
| Database query | 10–30 seconds |
| AI model generation | 30–120 seconds |
| Large document processing | Several minutes |

Timeouts that are too short may interrupt valid work.

Timeouts that are too long reduce the benefit of having a timeout policy.

---

# Best Practices

- Choose realistic timeout values.
- Use shorter limits for external services.
- Combine timeouts with retry policies.
- Monitor timeout frequency in production.
- Avoid excessively large timeout values.
- Design workflows so interrupted operations can be restarted safely.
- Keep timeout behavior predictable across workflows.

---

# Summary

Timeout policies protect BindAI workflows from stalled or excessively long-running operations.

By limiting execution time, they improve system stability, prevent resource exhaustion, and provide predictable behavior when tasks fail to complete within an acceptable timeframe.

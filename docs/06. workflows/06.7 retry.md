# Retry Policies

Retry policies improve workflow reliability by automatically repeating failed operations.

Instead of immediately failing a workflow when a temporary error occurs, BindAI can retry the operation according to a configurable policy.

Retries are most effective for transient failures such as temporary network issues, rate limits, or unavailable services.

---

# What is a Retry Policy?

A retry policy defines how BindAI should respond when a task fails.

Conceptually:

```text
Execute Task

↓

Success?
      ↙       ↘

    Yes       No

              ↓

        Retry Policy

              ↓

       Execute Again
```

If a retry eventually succeeds, workflow execution continues normally.

---

# Why Use Retries?

Many failures are temporary rather than permanent.

Examples include:

- network timeouts
- temporary API outages
- HTTP 429 rate limits
- database connection interruptions
- cloud service availability issues
- AI provider transient failures

Automatically retrying these operations often prevents unnecessary workflow failures.

---

# Retry Lifecycle

A retry-enabled task follows a predictable pattern.

```text
Attempt 1

↓

Failure

↓

Wait

↓

Attempt 2

↓

Failure

↓

Wait

↓

Attempt 3

↓

Success
```

If all attempts fail, the workflow reports an error or follows the configured failure behavior.

---

# Configuring a Retry Policy

BindAI provides a retry policy object that controls retry behavior.

Typical configuration includes:

- maximum attempts
- delay between attempts
- exponential backoff
- retryable exception types

Example:

```python
RetryPolicy(
    max_attempts=3,
    delay_seconds=5,
    exponential_backoff=True,
)
```

---

# Maximum Attempts

A retry policy limits how many times an operation can be executed.

```text
Attempt 1

↓

Attempt 2

↓

Attempt 3

↓

Stop
```

After the configured limit is reached, BindAI stops retrying and reports the failure.

---

# Retry Delay

Retries normally wait before executing again.

```text
Failure

↓

5 Seconds

↓

Retry
```

Waiting briefly prevents repeatedly hammering a service that is already experiencing problems.

---

# Exponential Backoff

Exponential backoff increases the waiting period after each failed attempt.

Example:

```text
Attempt 1

↓

5 Seconds

↓

Attempt 2

↓

10 Seconds

↓

Attempt 3

↓

20 Seconds
```

This strategy:

- reduces load on external systems
- improves recovery chances
- avoids excessive retry traffic

---

# Success During Retry

If any retry succeeds, workflow execution continues normally.

```text
Attempt 1

↓

Failure

↓

Retry

↓

Success

↓

Continue Workflow
```

From the rest of the workflow's perspective, the task completed successfully.

---

# Permanent Failures

Retries cannot resolve permanent problems.

Examples include:

- invalid credentials
- incorrect configuration
- malformed requests
- missing resources
- validation failures

These issues should usually fail immediately rather than being retried.

---

# Retry vs Loop

Retries and loops solve different problems.

| Retry | Loop |
| ------ | ---- |
| Handles temporary failures | Repeats business logic |
| Automatic | Explicit workflow behavior |
| Triggered by exceptions | Triggered by conditions |
| Improves reliability | Implements process logic |

Retries recover from operational failures.

Loops intentionally repeat workflow steps.

---

# Common Retry Scenarios

Retry policies are commonly applied to:

- REST API requests
- AI model providers
- database operations
- cloud storage services
- message queues
- payment gateways
- external integrations

These systems may occasionally fail temporarily before recovering.

---

# Error Handling

If every retry attempt fails, workflows can:

- stop execution
- trigger an error handler
- notify administrators
- create a human approval task
- schedule another execution
- execute a fallback branch

Retries work best when combined with broader error-handling strategies.

---

# Monitoring Retries

Production systems often record retry activity.

Useful metrics include:

- total retry attempts
- successful retries
- failed retries
- average retry count
- retry latency

Monitoring helps identify unstable services before they become major issues.

---

# Best Practices

- Retry only transient failures.
- Keep the maximum number of attempts reasonable.
- Use exponential backoff for external services.
- Log retry attempts for troubleshooting.
- Do not retry validation or configuration errors.
- Combine retries with timeout policies.
- Monitor retry frequency in production.

---

# Summary

Retry policies improve workflow resilience by automatically repeating operations that fail due to temporary conditions.

When configured appropriately, retries reduce unnecessary failures, improve workflow reliability, and help production systems recover gracefully from transient infrastructure problems.

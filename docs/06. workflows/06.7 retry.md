# Retry Policies

Retry policies allow BindAI to automatically retry a workflow node when its execution raises an exception.

Retries are handled by the workflow executor. When a node fails and a `RetryPolicy` is configured, the executor attempts the same node again until it succeeds or the configured maximum number of attempts is reached.

Retries are useful for operations that may fail temporarily, such as external service calls or network-dependent operations.

---

# What is a Retry Policy?

A retry policy defines how many times the executor may attempt a failed node.

```text
Execute Node

↓

Success?
      ↙       ↘

    Yes        No
     ↓          ↓
 Continue    Retry Policy
                ↓
           Try Again
```

If a retry succeeds, normal workflow execution continues.

If the retry limit is reached, the workflow fails.

---

# Retry Policy Configuration

BindAI provides a `RetryPolicy` configuration object.

```python
from bindai_workflow.retry import RetryPolicy

policy = RetryPolicy(
    max_attempts=3,
    delay_seconds=5,
    exponential_backoff=True,
)
```

The policy currently contains three configuration fields:

| Field                 | Default | Purpose                                               |
| --------------------- | ------: | ----------------------------------------------------- |
| `max_attempts`        |     `3` | Maximum number of attempts allowed                    |
| `delay_seconds`       |     `5` | Configured delay value for retry behavior             |
| `exponential_backoff` |  `True` | Configures whether exponential backoff should be used |

The executor currently uses `max_attempts` to control retrying.

The `delay_seconds` and `exponential_backoff` fields are defined by the policy but are not yet applied by the executor.

---

# How Retries Work

Retry handling occurs when a workflow node raises an exception.

Conceptually:

```text
Execute Node

↓

Exception

↓

Retry Policy Available?

↙                 ↘

No                 Yes
↓                   ↓
Fail             Increment Attempt
                    ↓
              Attempts Exhausted?
                 ↙          ↘
               Yes           No
                ↓             ↓
              Fail         Execute Again
```

The executor performs this logic inside its node execution loop.

---

# Retry Attempts

The workflow context stores the current retry attempt:

```python
context.retry_attempt
```

Before each node starts, the executor resets this value:

```python
context.retry_attempt = 0
```

When the node raises an exception, the executor increments it:

```python
context.retry_attempt += 1
```

The executor then compares the attempt count with:

```python
context.retry_policy.max_attempts
```

---

# Maximum Attempts

`max_attempts` controls when retrying stops.

For example:

```python
RetryPolicy(
    max_attempts=3,
)
```

produces behavior conceptually equivalent to:

```text
Attempt

↓

Failure

↓

Retry Attempt

↓

Failure

↓

Retry Attempt

↓

Failure

↓

Retry Limit Reached

↓

Workflow Failure
```

The executor fails the workflow when:

```python
context.retry_attempt >= policy.max_attempts
```

The configured value therefore represents the maximum attempt count, including the initial execution.

---

# Successful Retry

If a node eventually executes successfully, the executor resets the retry counter:

```python
context.retry_attempt = 0
```

Normal workflow execution then continues with the node's next connection.

Conceptually:

```text
Attempt 1

↓

Failure

↓

Attempt 2

↓

Success

↓

Continue Workflow
```

A successful retry does not produce a separate workflow result. From the workflow's perspective, the node has completed successfully.

---

# Retry Without a Policy

If a node raises an exception and no retry policy is configured:

```python
context.retry_policy is None
```

the executor immediately fails the workflow.

Conceptually:

```text
Execute Node

↓

Exception

↓

No Retry Policy

↓

Workflow Failure
```

---

# Retry State in Workflow Context

Retry configuration belongs to the workflow execution context:

```python
context.retry_policy
```

The context also stores:

```python
context.retry_attempt
```

This allows the executor to track retry progress for the current node execution.

A new node starts with the retry counter reset.

---

# Delay and Backoff

`RetryPolicy` currently defines:

```python
delay_seconds: int = 5
exponential_backoff: bool = True
```

However, the current executor does not yet sleep between attempts or calculate an exponential delay.

The retry loop currently retries immediately.

The executor contains a future implementation section for:

* sleeping for the configured delay
* exponential backoff
* retry events

Therefore, these settings should currently be treated as **configuration fields reserved for retry-delay behavior**, rather than as active runtime behavior.

---

# Retryable Exceptions

The current retry implementation does not define a list of retryable exception types.

Any exception raised by `node.execute()` enters the executor's retry handling when a retry policy is configured.

There is currently no built-in configuration such as:

```python
retry_on=(TimeoutError, ConnectionError)
```

Therefore, applications should not assume that only transient exceptions are retried.

---

# Retry vs Loop

Retries and loops both involve repeated execution, but they serve different purposes.

| Retry                         | Loop                                    |
| ----------------------------- | --------------------------------------- |
| Triggered by an exception     | Triggered by a predicate                |
| Re-executes a failed node     | Repeats workflow logic                  |
| Controlled by `RetryPolicy`   | Controlled by `LoopNode`                |
| Intended for failure recovery | Intended for business/process iteration |
| Managed by the executor       | Represented as a workflow node          |

Use a retry when an operation failed.

Use a loop when repetition is part of the workflow's intended business logic.

---

# Retry and Timeout

Retry and timeout policies operate at different levels.

A retry determines what happens after a node raises an exception.

A timeout limits the overall workflow execution duration.

For example:

```text
Workflow
   │
   ├── Timeout Policy
   │
   └── Node
        │
        └── Retry Policy
```

A workflow can therefore have both policies configured.

---

# Failure After Retries

When the retry limit is reached, the executor calls its normal workflow failure handling.

The failure process:

1. records the error in `context.errors`
2. marks the workflow as completed
3. records the workflow failure event
4. persists the workflow instance
5. stores failed execution history
6. returns an unsuccessful `WorkflowResult`

Conceptually:

```text
Retry Limit Reached

↓

Workflow Failure

↓

Record Error

↓

Persist State

↓

Save History

↓

Return Failure Result
```

---

# Compensation

If the workflow has registered compensation callbacks, normal workflow failure handling also executes those compensations.

Compensations are separate from retry behavior.

They run when the workflow ultimately fails rather than after every individual failed attempt.

---

# Common Use Cases

Retries can be useful for nodes that interact with:

* external APIs
* AI providers
* databases
* network services
* cloud services
* external integrations

However, because the current implementation retries all node exceptions when a policy exists, retry policies should be configured carefully.

---

# Best Practices

* Set a reasonable `max_attempts`.
* Use retries for operations where repeating the operation is safe.
* Be aware that the current executor retries exceptions without filtering their type.
* Do not assume `delay_seconds` currently pauses execution.
* Do not assume `exponential_backoff` is currently active.
* Avoid retrying operations that are not safe to repeat.
* Combine retry policies with timeout policies when appropriate.
* Monitor failed executions and retry counts in production.
* Treat retry configuration as part of the workflow's reliability design.

---

# Summary

BindAI retry policies allow the workflow executor to retry failed node execution.

The current implementation tracks retry attempts using `context.retry_attempt` and limits execution using `RetryPolicy.max_attempts`.

If a node succeeds, execution continues normally. If the maximum number of attempts is reached, the executor invokes normal workflow failure handling.

`delay_seconds` and `exponential_backoff` are currently defined on `RetryPolicy` but are not yet applied by the executor. The current retry loop retries immediately, with no exception-type filtering or retry delay.

Retries are therefore currently a simple executor-level failure-recovery mechanism rather than a complete backoff system.

# Workflow Schedule Template

The **Workflow Schedule** template demonstrates how BindAI represents time-based workflow schedules and checks whether they are due.

A `WorkflowSchedule` stores:

* The workflow identifier
* The next scheduled execution time
* An optional recurring interval
* Whether the schedule is enabled

The `WorkflowScheduler` keeps schedules in memory, identifies enabled schedules that are due, and advances a schedule's next-run time by its configured interval.

Scheduling is separate from workflow execution. The scheduler determines **when a workflow is due**; application code is responsible for starting the workflow and managing the scheduling lifecycle.

The current implementation provides scheduling primitives, not a complete background scheduling service.

---

# Purpose

This template demonstrates how to:

* Create a workflow schedule
* Register schedules with a scheduler
* Check which schedules are due
* Configure recurring intervals
* Enable or disable schedules
* Advance recurring schedules after processing
* Understand the current limitations of in-memory scheduling

The current scheduler is intentionally lightweight and in-memory.

---

# Scheduling Architecture

The scheduling components provide timing state and due-checking:

```text
WorkflowSchedule
       |
       v
WorkflowScheduler
       |
       v
Check Due Schedules
       |
       v
Application Code
       |
       v
Workflow Execution
```

The scheduler does **not** execute workflows itself.

An application must call the scheduler's methods, decide how to process due schedules, and initiate the corresponding workflow executions.

---

# WorkflowSchedule

A `WorkflowSchedule` is a dataclass describing when a workflow should execute.

For example:

```python
from datetime import UTC, datetime

from bindai_workflow.schedule import WorkflowSchedule

schedule = WorkflowSchedule(
    workflow_id="daily-report",
    next_run=datetime(2026, 10, 11, 9, 0, tzinfo=UTC),
    interval_seconds=86400,
    enabled=True,
)
```

The example sets the next run to 09:00 UTC on 11 October 2026, with a 24-hour interval.

The current implementation contains four fields:

| Field              | Type          | Default  | Description                                             |
| ------------------ | ------------- | -------- | ------------------------------------------------------- |
| `workflow_id`      | `str`         | Required | Identifier of the workflow associated with the schedule |
| `next_run`         | `datetime`    | Required | Next scheduled execution time                           |
| `interval_seconds` | `int \| None` | `None`   | Optional recurring interval in seconds                  |
| `enabled`          | `bool`        | `True`   | Whether the schedule is considered by `due()`           |

There is no additional recurrence-rule object in the current implementation.

---

# Registering a Schedule

Create a `WorkflowScheduler` and add schedules with `add()`:

```python
from datetime import UTC, datetime

from bindai_workflow.schedule import WorkflowSchedule
from bindai_workflow.scheduler import WorkflowScheduler

scheduler = WorkflowScheduler()

schedule = WorkflowSchedule(
    workflow_id="daily-report",
    next_run=datetime(2026, 10, 11, 9, 0, tzinfo=UTC),
    interval_seconds=86400,
)

scheduler.add(schedule)
```

The scheduler stores the schedule in its internal list.

The current `add()` method does not return the schedule. Multiple schedules can be added to the same scheduler.

---

# In-Memory Scheduler

The current scheduler stores schedules in an in-memory list:

```python
self._schedules: list[WorkflowSchedule]
```

This means schedules are process-local and held in memory.

The current implementation does not provide:

* Database persistence
* File persistence
* Distributed scheduling
* Scheduler recovery after process restart
* A persistent schedule store
* A background scheduler thread
* A built-in scheduler service

If the process stops, the scheduler's in-memory schedules are lost unless application code persists and reconstructs them separately.

---

# Checking Due Schedules

The scheduler provides:

```python
scheduler.due()
```

to identify schedules that are currently due.

Conceptually:

```text
Current UTC Time
       |
       v
Compare next_run
       |
       +---- next_run <= now ----> Due
       |
       +---- next_run > now -----> Not Due
```

A schedule is returned when both conditions are true:

1. `schedule.enabled` is `True`.
2. `schedule.next_run <= datetime.now(UTC)`.

The scheduler evaluates the schedules currently registered in its in-memory list.

The comparison requires compatible datetime values. Use timezone-aware UTC timestamps for `next_run` so they can be compared with the scheduler's current UTC time.

Calling `due()` does not automatically mark schedules as processed, advance their timestamps, or execute their workflows.

---

# Due Schedule Example

Suppose the scheduler contains these schedules, with times expressed in UTC:

```text
Report     09:00
Backup     10:00
Sync       11:00
```

If the current UTC time is 10:30:

```text
Report     ✓ Due
Backup     ✓ Due
Sync       ✗ Not Due
```

Calling:

```python
due_schedules = scheduler.due()
```

returns the enabled schedules whose `next_run` is at or before the current UTC time.

This example assumes that the listed times fall on the same date and that the schedules have not been advanced or otherwise modified.

---

# Enabled Schedules

Schedules are enabled by default:

```python
schedule = WorkflowSchedule(
    workflow_id="report",
    next_run=scheduled_time,
)
```

Because `enabled` defaults to `True`, the schedule can be returned by:

```python
scheduler.due()
```

once its `next_run` time has arrived.

You can also explicitly enable a schedule:

```python
schedule.enabled = True
```

Changing this field affects subsequent due checks.

---

# Disabled Schedules

A schedule can be disabled:

```python
schedule = WorkflowSchedule(
    workflow_id="report",
    next_run=scheduled_time,
    enabled=False,
)
```

Disabled schedules remain in the scheduler's internal collection but are ignored by `due()`.

Even if:

```python
schedule.next_run <= datetime.now(UTC)
```

the schedule will not be returned while:

```python
schedule.enabled is False
```

This allows application code to temporarily disable a schedule without removing it from the in-memory scheduler.

---

# One-Time Schedules

A schedule with no recurring interval can represent a one-time execution:

```python
schedule = WorkflowSchedule(
    workflow_id="monthly-report",
    next_run=scheduled_time,
    interval_seconds=None,
)
```

When the schedule becomes due, `due()` returns it.

Calling:

```python
scheduler.reschedule(schedule)
```

does not change `next_run` because no interval is configured.

The scheduler does not automatically disable or remove a one-time schedule.

If application code calls `due()` again after the scheduled time has passed, the same enabled schedule can be returned again.

For one-time application behavior, application code should disable or otherwise manage the schedule after processing it:

```python
schedule.enabled = False
```

The application should also decide how to handle a failed workflow execution before treating the schedule as completed.

---

# Recurring Schedules

A recurring schedule specifies an interval:

```python
schedule = WorkflowSchedule(
    workflow_id="hourly-sync",
    next_run=scheduled_time,
    interval_seconds=3600,
)
```

The interval is expressed in seconds.

For example:

| Interval | Duration |
| -------: | -------- |
|     `60` | 1 minute |
|   `3600` | 1 hour   |
|  `86400` | 1 day    |
| `604800` | 1 week   |

The scheduler does not interpret calendar recurrence rules such as:

* Every Monday
* The first day of every month
* Weekdays at 09:00

It advances `next_run` by the configured number of seconds.

---

# Rescheduling

The scheduler provides:

```python
scheduler.reschedule(schedule)
```

to advance a recurring schedule.

Conceptually:

```text
Current next_run
       |
       + interval_seconds
       |
       v
Updated next_run
```

For example, if the schedule has:

```text
next_run = 09:00 UTC
interval_seconds = 3600
```

then calling:

```python
scheduler.reschedule(schedule)
```

advances the schedule to:

```text
next_run = 10:00 UTC
```

The implementation adds a `timedelta` to the existing timestamp:

```python
schedule.next_run += timedelta(
    seconds=schedule.interval_seconds,
)
```

This operation advances the stored schedule time. It does not start a workflow or verify that a workflow execution succeeded.

---

# Rescheduling Without an Interval

If:

```python
schedule.interval_seconds is None
```

the scheduler does not change `next_run`.

For example:

```python
schedule = WorkflowSchedule(
    workflow_id="one-time-report",
    next_run=scheduled_time,
    interval_seconds=None,
)

scheduler.reschedule(schedule)
```

leaves the scheduled time unchanged.

---

# Zero Interval

The current implementation checks the interval using truthiness:

```python
if schedule.interval_seconds:
```

Therefore:

```python
interval_seconds=0
```

does not advance the schedule.

A positive interval should be used for recurring schedules.

The scheduler does not validate the interval value when a schedule is created. Application code should validate its scheduling configuration.

---

# Missed Recurring Schedules

`reschedule()` advances `next_run` by **one interval only**.

For example:

```text
next_run = 09:00 UTC
interval = 1 hour
current time = 13:30 UTC
```

Calling:

```python
scheduler.reschedule(schedule)
```

changes:

```text
09:00 UTC -> 10:00 UTC
```

It does not automatically advance the schedule to 14:00 UTC or repeatedly catch up missed intervals.

Because 10:00 UTC is still in the past, another call to `due()` can return the schedule again.

Application code is responsible for deciding how missed executions should be handled. Possible strategies include processing each missed interval, skipping missed intervals, or advancing directly to the next future run time. Those strategies are not implemented by the scheduler itself.

---

# Scheduler Lifecycle

A typical application-level scheduling loop looks like:

```text
Register Schedules
       |
       v
Check Due Schedules
       |
       v
Start Due Workflows
       |
       v
Handle Workflow Results
       |
       v
Reschedule or Disable Schedules
       |
       v
Check Again
```

The current `WorkflowScheduler` provides these core operations:

```text
add()
  |
  v
due()
  |
  v
reschedule()
```

The surrounding application must determine:

* When to call `due()`
* How to execute due workflows
* When to call `reschedule()`
* How to handle workflow failures
* How to handle missed schedules
* How frequently to poll
* How to prevent duplicate or overlapping executions if required

There is no built-in scheduler loop.

---

# Scheduler Does Not Execute Workflows

`WorkflowScheduler` does not invoke `WorkflowExecutor`.

Its responsibility is to identify schedules that are due and update schedule timestamps when requested.

The separation is:

```text
WorkflowScheduler
       |
       v
due()
       |
       v
Due WorkflowSchedule
       |
       v
Application Code
       |
       v
Resolve Workflow
       |
       v
Workflow Execution
```

Application code must resolve `workflow_id` to the appropriate workflow and initiate execution.

This keeps scheduling state separate from workflow execution.

---

# Scheduler vs Workflow Executor

The two components have different responsibilities.

| Scheduler                                   | Workflow Executor                       |
| ------------------------------------------- | --------------------------------------- |
| Stores workflow schedules in memory         | Executes workflow instances             |
| Determines which schedules are due          | Runs workflow nodes                     |
| Tracks `next_run`                           | Manages execution state                 |
| Advances recurring intervals when requested | Handles workflow completion and failure |
| Does not execute workflow nodes             | Executes workflow nodes                 |

The scheduler answers:

> When is this workflow due?

The executor answers:

> How does this workflow execute?

Application code connects these responsibilities.

---

# Scheduler vs Workflow Loop

Scheduling and workflow loops both support repeated behavior, but at different levels.

| Scheduler                                                                                | Workflow Loop                                       |
| ---------------------------------------------------------------------------------------- | --------------------------------------------------- |
| Provides timing state for starting workflows                                             | Repeats work inside a workflow                      |
| Uses schedule timestamps                                                                 | Uses a loop's termination condition                 |
| Operates outside the workflow execution lifecycle                                        | Operates during workflow execution                  |
| Can be used to initiate multiple workflow executions when application code triggers them | Repeats logic within the current workflow execution |

A scheduler helps determine **when a workflow may start**.

A loop determines **how a running workflow repeats**.

# Example: Hourly Workflow

An application can register an hourly workflow schedule:

```python
from datetime import UTC, datetime

from bindai_workflow.schedule import WorkflowSchedule
from bindai_workflow.scheduler import WorkflowScheduler

scheduler = WorkflowScheduler()

schedule = WorkflowSchedule(
    workflow_id="hourly-report",
    next_run=datetime(2026, 10, 10, 13, 0, tzinfo=UTC),
    interval_seconds=3600,
)

scheduler.add(schedule)
```

The application can poll for due schedules:

```python
for schedule in scheduler.due():
    # Application code starts the corresponding workflow.
    # Handle the workflow result before deciding how to reschedule.
    scheduler.reschedule(schedule)
```

This is a simplified illustration of application-managed scheduling. In production code, workflow execution and error handling should be implemented before rescheduling the schedule.

The scheduler maintains the timing state. It does not resolve `workflow_id` to a workflow or execute it automatically.

---

# Multiple Schedules

A single scheduler can contain multiple schedules:

```text
WorkflowScheduler
├── Daily Report
├── Hourly Sync
├── Data Backup
└── Knowledge Refresh
```

Calling:

```python
scheduler.due()
```

evaluates all schedules currently stored in the scheduler.

Every enabled schedule whose `next_run` is at or before the current UTC time is included in the returned list.

The scheduler does not check whether multiple schedules refer to the same workflow or whether that workflow is already running.

---

# Current Time Handling

The current implementation uses:

```python
datetime.now(UTC)
```

inside `WorkflowScheduler.due()`.

Therefore, `due()` compares each schedule's `next_run` against a timezone-aware UTC datetime.

Applications should supply compatible timezone-aware `next_run` values.

Mixing naive and timezone-aware datetimes can cause Python datetime comparisons to raise an exception. Use consistent UTC timestamps to avoid this issue.

The scheduler does not currently provide:

* Timezone conversion
* Local-time scheduling rules
* Daylight-saving-time handling
* Calendar-based recurrence
* User timezone configuration

These concerns belong to additional application-level scheduling logic.

---

# Timezone Considerations

The scheduler uses UTC for its due-time comparison and advances the stored `next_run` by a duration.

For example:

```python
from datetime import UTC, datetime

scheduled_time = datetime(
    2026, 10, 11, 9, 0,
    tzinfo=UTC,
)
```

This represents 09:00 UTC.

The current scheduler does not convert local-time rules into UTC or handle daylight-saving transitions for recurring local schedules.

For example, a 24-hour interval is a duration of 86,400 seconds; it is not a guarantee that a workflow will run at the same local clock time every day across daylight-saving transitions.

Applications that require named-timezone or local-calendar behavior must calculate the next scheduled timestamp themselves or use a scheduling system that supports those requirements.

---

# Recurring Execution

Recurring schedules use a fixed interval.

For example:

```python
interval_seconds=86400
```

represents a duration of 24 hours.

The scheduler calculates the next execution time by adding that duration:

```text
09:00 UTC
    |
    + 24 hours
    v
09:00 UTC next day
```

This is duration-based recurrence rather than calendar-based recurrence.

The scheduler does not guarantee that the workflow actually executes at the calculated time. Application code must poll for due schedules and initiate execution.

---

# Schedule State

A schedule contains four pieces of state:

```text
workflow_id
     +
next_run
     +
interval_seconds
     +
enabled
```

For example:

```python
WorkflowSchedule(
    workflow_id="knowledge-refresh",
    next_run=scheduled_time,
    interval_seconds=86400,
    enabled=True,
)
```

The scheduler does not maintain additional execution metadata for the schedule.

There is no built-in:

* Last-run timestamp
* Run count
* Failure count
* Execution result
* Retry state
* Schedule history

Applications that need these features must manage them separately.

---

# No Duplicate Detection

The scheduler does not check whether a workflow is already registered.

For example, application code can add multiple schedules with the same `workflow_id`:

```python
scheduler.add(schedule_a)
scheduler.add(schedule_b)
```

Both schedules remain in the internal list.

`due()` evaluates them independently.

Applications should avoid registering duplicate schedules unintentionally and should implement deduplication if their use case requires it.

---

# No Automatic Execution

The scheduler does not start a background thread or process.

An application must actively call:

```python
scheduler.due()
```

for due schedules to be detected.

A typical application might use its own timer, worker, service loop, or deployment infrastructure to call the scheduler periodically.

Without that orchestration, schedules do not trigger workflows automatically.

The scheduler only manages timing state. Workflow execution remains the responsibility of the surrounding application.

# Scheduling and Workflow Execution

A complete application-level flow can look like:

```text
WorkflowSchedule
       |
       v
WorkflowScheduler.due()
       |
       v
Due Workflow ID
       |
       v
Application Resolves Workflow
       |
       v
Workflow Execution
       |
       v
Application Handles Result
       |
       v
WorkflowScheduler.reschedule()
```

The scheduler intentionally does not contain workflow registry or execution logic.

This allows applications to choose how workflows are resolved, executed, monitored, and rescheduled.

---

# Error Handling

The current scheduler does not execute workflows, so it does not manage workflow execution errors.

If application code starts a workflow and that workflow fails, the application is responsible for deciding whether and when to reschedule the associated schedule.

The scheduler does not implement:

* Retry policies for workflow executions
* Backoff
* Workflow failure handling
* Dead-letter behavior
* Execution cancellation
* Automatic rescheduling after failure

Those concerns belong to the workflow execution or application infrastructure.

---

# Persistence and Recovery

Schedules are stored only in memory:

```python
self._schedules: list[WorkflowSchedule]
```

There is no persistent scheduler store in the current implementation.

If the process exits, the schedules held in that scheduler instance disappear.

Applications requiring durable scheduling should persist schedule definitions externally and reconstruct the scheduler after startup.

Schedule persistence is separate from workflow execution persistence and history.

---

# Best Practices

* Use timezone-aware UTC values for `next_run`.
* Prefer positive `interval_seconds` values for recurring schedules.
* Explicitly disable one-time schedules after processing if they should not run again.
* Decide whether to reschedule recurring schedules after success, failure, or both.
* Define how missed intervals should be handled.
* Keep scheduling separate from workflow execution.
* Avoid registering duplicate schedules unintentionally.
* Do not assume the scheduler persists schedules.
* Do not assume the scheduler executes workflows automatically.
* Handle workflow failures separately from schedule management.
* Use application-level infrastructure for polling or background scheduling.
* Design recurring workflows so repeated execution is safe.
* Add locking or deduplication if multiple application workers might process the same schedule.

# Current Limitations

The current `WorkflowScheduler` is intentionally simple.

It does not currently provide:

* Persistent schedules
* Background polling
* Distributed scheduling
* Scheduler workers
* Timezone conversion or local-time recurrence
* Calendar recurrence rules
* Automatic workflow execution
* Automatic retries
* Missed-run recovery
* Schedule history
* Duplicate detection
* Scheduler locking
* Distributed coordination

These capabilities require additional application or infrastructure layers.

# Summary

The **Workflow Schedule** template demonstrates how BindAI represents and checks time-based workflow schedules.

`WorkflowSchedule` stores:

```text
workflow_id
next_run
interval_seconds
enabled
```

`WorkflowScheduler` provides three core operations:

```text
add()
  |
  v
due()
  |
  v
reschedule()
```

* `add()` stores schedules in memory.
* `due()` returns enabled schedules whose `next_run` is at or before the current UTC time.
* `reschedule()` advances a schedule by one configured interval when `interval_seconds` is truthy.

The scheduler does not execute workflows, persist schedules, run a background polling loop, or provide timezone-aware calendar recurrence.

It is best understood as a lightweight scheduling-state and due-checking component that application code can combine with BindAI workflow execution.

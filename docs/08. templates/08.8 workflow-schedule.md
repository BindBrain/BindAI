# Workflow Schedule Template

The **Workflow Schedule** template demonstrates how BindAI represents and checks time-based workflow schedules.

A `WorkflowSchedule` stores:

- the workflow identifier
- the next scheduled execution time
- an optional recurring interval
- whether the schedule is enabled

The `WorkflowScheduler` keeps schedules in memory, identifies schedules that are currently due, and advances recurring schedules.

Scheduling is separate from workflow execution. The scheduler determines **when a workflow is due**; application code is responsible for actually executing the workflow.

---

# Purpose

This template demonstrates how to:

- Create a workflow schedule
- Register schedules with a scheduler
- Check which schedules are due
- Configure recurring execution intervals
- Enable or disable schedules
- Advance recurring schedules after processing

The current scheduler is intentionally lightweight and in-memory.

---

# Scheduling Architecture

The scheduling components provide timing state and due-checking:

```text
WorkflowSchedule
      |
      v
WorkflowScheduler
      |
      v
Check Due Schedules
      |
      v
Application Code
      |
      v
Workflow Execution
```

The scheduler does **not** execute workflows itself.

---

# WorkflowSchedule

A `WorkflowSchedule` is a dataclass describing when a workflow should execute.

```python
from datetime import datetime

from bindai_workflow.schedule import WorkflowSchedule

schedule = WorkflowSchedule(
    workflow_id="daily-report",
    next_run=datetime(...),
    interval_seconds=3600,
    enabled=True,
)
```

The current implementation contains four fields:

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| `workflow_id` | `str` | Required | Identifier of the workflow associated with the schedule |
| `next_run` | `datetime` | Required | Next scheduled execution time |
| `interval_seconds` | `int \| None` | `None` | Optional recurring interval in seconds |
| `enabled` | `bool` | `True` | Whether the schedule is considered by `due()` |

There is no additional recurrence-rule object in the current implementation.

---

# Registering a Schedule

Create a `WorkflowScheduler` and add schedules with `add()`:

```python
from datetime import datetime

from bindai_workflow.schedule import WorkflowSchedule
from bindai_workflow.scheduler import WorkflowScheduler

scheduler = WorkflowScheduler()

schedule = WorkflowSchedule(
    workflow_id="daily-report",
    next_run=datetime(...),
    interval_seconds=86400,
)

scheduler.add(schedule)
```

The scheduler stores the schedule in its internal list.

The current `add()` method does not return the schedule.

Multiple schedules can be added to the same scheduler.

---

# In-Memory Scheduler

The current scheduler stores schedules in:

```python
self._schedules: list[WorkflowSchedule]
```

This means schedules are process-local and in-memory.

The current implementation does not provide:

- Database persistence
- File persistence
- Distributed scheduling
- Scheduler recovery after process restart
- A persistent schedule store
- A background scheduler thread
- A built-in scheduler service

If the process stops, the scheduler's in-memory schedules are lost unless application code persists and reconstructs them separately.

---

# Checking Due Schedules

The scheduler provides:

```python
scheduler.due()
```

to identify schedules that are currently due.

Conceptually:

```text
Current UTC Time
       |
       v
Compare next_run
       |
       +---- next_run <= now ----> Due
       |
       +---- next_run > now -----> Not Due
```

A schedule is returned when both conditions are true:

1. `schedule.enabled` is `True`
2. `schedule.next_run <= datetime.utcnow()`

The scheduler evaluates every registered schedule.

---

# Due Schedule Example

Suppose the scheduler contains:

```text
Report     09:00
Backup     10:00
Sync       11:00
```

If the current UTC time is `10:30`:

```text
Report     ✓ Due
Backup     ✓ Due
Sync       ✗ Not Due
```

Calling:

```python
due_schedules = scheduler.due()
```

returns the schedules whose `next_run` is at or before the current UTC time and whose `enabled` flag is `True`.

---

# Enabled Schedules

Schedules are enabled by default:

```python
schedule = WorkflowSchedule(
    workflow_id="report",
    next_run=scheduled_time,
)
```

Because:

```python
enabled = True
```

the schedule can be returned by:

```python
scheduler.due()
```

once its `next_run` has arrived.

You can also explicitly enable a schedule:

```python
schedule.enabled = True
```

---

# Disabled Schedules

A schedule can be disabled:

```python
schedule = WorkflowSchedule(
    workflow_id="report",
    next_run=scheduled_time,
    enabled=False,
)
```

Disabled schedules remain in the scheduler's internal collection but are ignored by `due()`.

Even if:

```python
schedule.next_run <= datetime.utcnow()
```

the schedule will not be returned while:

```python
schedule.enabled is False
```

This allows application code to temporarily disable a schedule without removing it.

---

# One-Time Schedules

A schedule with no recurring interval can represent a one-time execution:

```python
schedule = WorkflowSchedule(
    workflow_id="monthly-report",
    next_run=scheduled_time,
    interval_seconds=None,
)
```

When this schedule becomes due, `due()` returns it.

Calling:

```python
scheduler.reschedule(schedule)
```

does not change `next_run` because no interval is configured.

The scheduler therefore does not automatically disable or remove a one-time schedule.

If application code calls `due()` again after the scheduled time has passed, the same enabled one-time schedule can be returned again.

For a true one-time application behavior, application code should disable or otherwise manage the schedule after processing it.

For example:

```python
schedule.enabled = False
```

---

# Recurring Schedules

A recurring schedule specifies an interval:

```python
schedule = WorkflowSchedule(
    workflow_id="hourly-sync",
    next_run=scheduled_time,
    interval_seconds=3600,
)
```

The interval is expressed in seconds.

For example:

```text
60       -> 1 minute
3600     -> 1 hour
86400    -> 1 day
604800   -> 1 week
```

The scheduler does not interpret calendar recurrence rules such as:

- every Monday
- first day of every month
- weekdays at 09:00

It only adds the configured number of seconds to `next_run`.

---

# Rescheduling

The scheduler provides:

```python
scheduler.reschedule(schedule)
```

to advance a recurring schedule.

Conceptually:

```text
Current next_run
       |
       + interval_seconds
       |
       v
New next_run
```

For example:

```python
schedule.next_run = 09:00
schedule.interval_seconds = 3600
```

After:

```python
scheduler.reschedule(schedule)
```

the schedule becomes approximately:

```text
next_run = 10:00
```

The implementation performs:

```python
schedule.next_run += timedelta(
    seconds=schedule.interval_seconds,
)
```

---

# Rescheduling Without an Interval

If:

```python
schedule.interval_seconds is None
```

the scheduler does not change `next_run`.

For example:

```python
schedule = WorkflowSchedule(
    workflow_id="one-time-report",
    next_run=scheduled_time,
    interval_seconds=None,
)

scheduler.reschedule(schedule)
```

leaves the scheduled time unchanged.

---

# Zero Interval

The current implementation checks the interval using truthiness:

```python
if schedule.interval_seconds:
```

Therefore:

```python
interval_seconds=0
```

does not advance the schedule.

A positive interval should be used for recurring schedules.

The scheduler does not validate the interval value when a schedule is created.

---

# Missed Recurring Schedules

`reschedule()` advances `next_run` by **one interval only**.

For example:

```text
next_run = 09:00
interval = 1 hour
current time = 13:30
```

Calling:

```python
scheduler.reschedule(schedule)
```

changes:

```text
09:00 -> 10:00
```

It does not automatically advance the schedule to `14:00` or repeatedly catch up missed intervals.

Because `10:00` is still in the past, another call to `due()` can return the schedule again.

Application code is responsible for deciding how missed executions should be handled.

---

# Scheduler Lifecycle

A typical application-level scheduling loop looks like:

```text
Register Schedules
       |
       v
Check Due Schedules
       |
       v
Start Due Workflows
       |
       v
Reschedule Recurring Schedules
       |
       v
Check Again
```

The current `WorkflowScheduler` provides the core operations:

```text
add()
  |
  v
due()
  |
  v
reschedule()
```

The surrounding application must determine:

- when to call `due()`
- how to execute due workflows
- when to call `reschedule()`
- how to handle failures
- how to handle missed schedules
- how frequently to poll

There is no built-in scheduler loop.

---

# Scheduler Does Not Execute Workflows

`WorkflowScheduler` does not invoke `WorkflowExecutor`.

Its responsibility is to identify schedules that are due.

The separation is:

```text
WorkflowScheduler
       |
       v
due()
       |
       v
WorkflowSchedule
       |
       v
Application Code
       |
       v
Workflow
       |
       v
WorkflowExecutor
```

This keeps scheduling state separate from workflow execution.

---

# Scheduler vs Workflow Executor

The two components have different responsibilities.

| Scheduler | Workflow Executor |
| --- | --- |
| Stores workflow schedules | Executes workflow instances |
| Determines which schedules are due | Runs workflow nodes |
| Tracks `next_run` | Manages execution state |
| Advances recurring intervals | Handles workflow completion and failure |
| Does not execute nodes | Executes nodes |

The scheduler answers:

> When is this workflow due?

The executor answers:

> How does this workflow execute?

---

# Scheduler vs Workflow Loop

Scheduling and workflow loops both support repeated behavior, but at different levels.

| Scheduler | Workflow Loop |
| --- | --- |
| Repeats opportunities to start workflows | Repeats work inside a workflow |
| Uses timestamps | Uses a predicate |
| Operates outside workflow execution | Operates during workflow execution |
| Can produce multiple workflow executions | Continues the current workflow instance |

A scheduler controls **when a workflow may start**.

A loop controls **how a running workflow repeats**.

---

# Example: Hourly Workflow

An application can register an hourly workflow:

```python
from datetime import datetime

schedule = WorkflowSchedule(
    workflow_id="hourly-report",
    next_run=datetime(...),
    interval_seconds=3600,
)

scheduler.add(schedule)
```

The application can then poll for due schedules:

```python
for schedule in scheduler.due():
    # Application code starts the corresponding workflow.

    scheduler.reschedule(schedule)
```

The scheduler maintains the timing state.

It does not resolve `workflow_id` to a workflow or execute it automatically.

Application code must perform that mapping and execution.

---

# Multiple Schedules

A single scheduler can contain multiple schedules:

```text
WorkflowScheduler
├── Daily Report
├── Hourly Sync
├── Data Backup
└── Knowledge Refresh
```

Calling:

```python
scheduler.due()
```

evaluates all schedules currently stored in the scheduler.

Every enabled schedule whose `next_run` is at or before the current UTC time is included in the returned list.

---

# Current Time Handling

The current implementation uses:

```python
datetime.utcnow()
```

inside `WorkflowScheduler.due()`.

Therefore, `due()` compares each schedule's `next_run` against a naive UTC-based `datetime`.

Applications should supply compatible `next_run` values.

The scheduler does not currently provide:

- Timezone conversion
- Local-time scheduling
- Daylight-saving-time handling
- Calendar-based recurrence
- User timezone configuration

These concerns belong to application-level scheduling logic.

---

# Timezone Considerations

Because the scheduler uses:

```python
datetime.utcnow()
```

applications should avoid mixing incompatible datetime representations.

For example, if application code supplies timezone-aware timestamps while the scheduler uses a naive UTC timestamp, Python datetime comparisons may fail.

A simple approach compatible with the current implementation is to use naive UTC datetimes for `next_run`.

More advanced timezone behavior should be handled before schedules are passed to `WorkflowScheduler`.

---

# Recurring Execution

Recurring schedules use a fixed interval.

For example:

```python
interval_seconds=86400
```

represents a 24-hour interval.

The scheduler calculates the next execution time by adding that number of seconds:

```text
09:00
  |
  + 24 hours
  v
09:00 next day
```

This is duration-based recurrence rather than calendar-based recurrence.

---

# Schedule State

A schedule contains four pieces of state:

```text
workflow_id
     +
next_run
     +
interval_seconds
     +
enabled
```

For example:

```python
WorkflowSchedule(
    workflow_id="knowledge-refresh",
    next_run=scheduled_time,
    interval_seconds=86400,
    enabled=True,
)
```

The scheduler does not maintain additional execution metadata for the schedule.

There is no built-in:

- last-run timestamp
- run count
- failure count
- execution result
- retry state
- schedule history

Applications that need these features must manage them separately.

---

# No Duplicate Detection

The scheduler does not check whether a workflow is already registered.

For example, application code can add multiple schedules with the same `workflow_id`:

```python
scheduler.add(schedule_a)
scheduler.add(schedule_b)
```

Both schedules remain in the internal list.

`due()` evaluates them independently.

Applications should avoid registering duplicate schedules unintentionally.

---

# No Automatic Execution

The scheduler does not start a background thread or process.

This means an application must actively call:

```python
scheduler.due()
```

for due schedules to be detected.

A typical application might use its own timer, worker, service loop, or deployment infrastructure to call the scheduler periodically.

# Typical Use Cases

The scheduling mechanism can support workflows such as:

- Periodic reports
- Recurring data synchronization
- Scheduled document processing
- Knowledge refreshes
- Recurring maintenance
- Automated backups
- Monitoring workflows
- Periodic AI processing

The scheduler only manages the timing state. Workflow execution remains the responsibility of the surrounding application.

---

# Scheduling and Workflow Execution

A complete application-level flow can look like:

```text
WorkflowSchedule
       |
       v
WorkflowScheduler.due()
       |
       v
Due Workflow ID
       |
       v
Application Resolves Workflow
       |
       v
Workflow Execution
       |
       v
WorkflowScheduler.reschedule()
```

The scheduler intentionally does not contain workflow registry or execution logic.

This allows applications to choose how workflows are resolved and executed.

---

# Error Handling

The current scheduler does not execute workflows, so it does not manage workflow execution errors.

If application code starts a workflow and that workflow fails, the application is responsible for deciding whether and when to reschedule the associated schedule.

Similarly, the scheduler does not implement:

- Retry policies
- Backoff
- Failure handling
- Dead-letter behavior
- Execution cancellation

Those concerns belong to the workflow execution or application infrastructure.

---

# Persistence and Recovery

Schedules are stored only in memory:

```python
self._schedules: list[WorkflowSchedule]
```

There is no persistent scheduler store in the current implementation.

Consequently:

```text
Application Process
       |
       v
WorkflowScheduler
       |
       v
In-Memory Schedules
```

If the process exits, the schedules disappear.

Applications requiring durable scheduling should persist schedule definitions externally and reconstruct the scheduler after startup.

---

# Best Practices

- Use a consistent UTC-based time representation for `next_run`.
- Prefer positive `interval_seconds` values for recurring schedules.
- Explicitly disable one-time schedules after processing if they should never run again.
- Reschedule recurring schedules after processing them.
- Decide how your application should handle missed intervals.
- Keep scheduling separate from workflow execution.
- Avoid registering duplicate schedules unintentionally.
- Do not assume the scheduler persists schedules.
- Do not assume the scheduler executes workflows automatically.
- Handle workflow failures separately from schedule management.
- Use application-level infrastructure for polling or background scheduling.
- Design recurring workflows so repeated execution is safe.

# Summary

The **Workflow Schedule** template demonstrates how BindAI represents and checks time-based workflow schedules.

`WorkflowSchedule` stores:

```text
workflow_id
next_run
interval_seconds
enabled
```

`WorkflowScheduler` provides three core operations:

```text
add()
  |
  v
due()
  |
  v
reschedule()
```

`add()` stores schedules in memory.

`due()` returns enabled schedules whose `next_run` is at or before the current UTC time.

`reschedule()` advances a schedule by one configured interval when `interval_seconds` is truthy.

The scheduler does not execute workflows, persist schedules, run a background polling loop, or provide timezone-aware recurrence.

It is therefore best understood as a lightweight scheduling state and due-checking component that application code can combine with BindAI workflow execution.

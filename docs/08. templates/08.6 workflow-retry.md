# Workflow Retry Template

The **Workflow Retry** template demonstrates how BindAI can retry failed workflow-node execution before ultimately failing the workflow.

Retry behavior is implemented by the workflow executor. When a node raises an exception and a retry policy is configured, the executor re-executes that same node until it succeeds or the configured maximum number of attempts is reached.

This template introduces executor-level failure recovery.

---

# Purpose

This template demonstrates how to:

- Configure a retry policy
- Retry failed node execution
- Limit the total number of attempts
- Continue workflow execution after successful recovery
- Handle final workflow failure

---

# Workflow Structure

Retry is handled by the executor rather than by a separate workflow branch.

Conceptually:

```text
Workflow
   |
   v
Operation
   |
   +---- Success ----> Continue
   |
   +---- Exception
            |
            v
        Retry Policy
            |
            v
         Try Again
```

The retry mechanism operates around the execution of the current node.

---

# RetryPolicy

The retry configuration is represented by `RetryPolicy`:

```python
from bindai_workflow.retry import RetryPolicy

policy = RetryPolicy(
    max_attempts=3,
    delay_seconds=5,
    exponential_backoff=True,
)
```

The policy contains three fields:

| Field | Default | Current role |
| --- | ---: | --- |
| `max_attempts` | `3` | Controls the total number of execution attempts |
| `delay_seconds` | `5` | Configuration value; not currently applied by the executor |
| `exponential_backoff` | `True` | Configuration value; not currently applied by the executor |

The current executor uses `max_attempts` for retry decisions.

---

# Retry Policy Defaults

`RetryPolicy` is a dataclass with these defaults:

```python
RetryPolicy(
    max_attempts=3,
    delay_seconds=5,
    exponential_backoff=True,
)
```

The policy itself does not currently implement validation or retry behavior.

The workflow executor is responsible for interpreting the policy during node execution.

---

# Execution Flow

When a node executes successfully:

```text
Execute Node
     |
     v
  Success
     |
     v
Continue Workflow
```

When the node raises an exception and a retry policy exists:

```text
Execute Node
     |
     v
 Exception
     |
     v
Retry Policy
     |
     v
Try Again
```

The executor repeats the same node execution until it succeeds or the retry limit is reached.

---

# Retry Lifecycle

For:

```python
max_attempts=3
```

the execution can look like:

```text
Attempt 1
   |
 Failure
   |
Attempt 2
   |
 Failure
   |
Attempt 3
   |
 Success
   |
Continue Workflow
```

If the final attempt also fails:

```text
Attempt 3
   |
 Failure
   |
Workflow Failure
```

`max_attempts` represents the total number of attempts, including the initial execution.

It does **not** represent the number of retries after the first attempt.

---

# Retry Counter

The workflow context tracks the current retry attempt using:

```python
context.retry_attempt
```

Before executing each workflow node, the executor resets the counter:

```python
context.retry_attempt = 0
```

When the node raises an exception, the executor increments it:

```python
context.retry_attempt += 1
```

The executor then compares the value against:

```python
context.retry_policy.max_attempts
```

If the retry attempt reaches the configured maximum, the workflow fails.

---

# Successful Recovery

A retry can recover from a temporary node failure.

For example:

```text
Attempt 1
   |
Exception
   |
Retry
   |
Attempt 2
   |
Success
   |
Next Workflow Node
```

After the node succeeds, the executor resets:

```python
context.retry_attempt = 0
```

The workflow then continues normally.

---

# Retry Without a Policy

If a node raises an exception and no retry policy is configured:

```text
Execute
   |
Exception
   |
No Retry Policy
   |
Workflow Failure
```

The executor immediately invokes its normal failure handling.

There is no automatic retry when `context.retry_policy` is `None`.

---

# Retry Limit

The `max_attempts` field controls the total number of attempts.

For example:

```python
RetryPolicy(
    max_attempts=3,
)
```

allows up to three executions of the failing node:

```text
Attempt 1
Attempt 2
Attempt 3
```

If all three fail, normal workflow failure handling occurs.

---

# Retry Behavior in the Executor

The executor effectively follows this pattern:

```python
while True:
    try:
        node.execute(context)
        context.retry_attempt = 0
        return
    except Exception as ex:
        policy = context.retry_policy

        if policy is None:
            fail()

        context.retry_attempt += 1

        if context.retry_attempt >= policy.max_attempts:
            fail()

        # Retry immediately
```

The retry is therefore implemented inside the node execution loop.

No additional workflow node is required to represent the retry.

---

# Delay Configuration

The retry policy contains:

```python
delay_seconds=5
```

However, the current executor does **not** sleep for this duration.

The current implementation retries immediately.

Therefore:

```python
RetryPolicy(
    delay_seconds=5,
)
```

does not currently produce a five-second delay between attempts.

The field exists as part of the retry configuration and can support future delay behavior.

---

# Exponential Backoff

The policy also contains:

```python
exponential_backoff=True
```

However, the current executor does not calculate or apply exponential backoff.

The current behavior remains:

```text
Failure
   |
Immediate Retry
   |
Failure
   |
Immediate Retry
```

`exponential_backoff` is therefore configuration for future retry behavior rather than an active feature in the current executor.

---

# Exception Handling

The current retry mechanism catches exceptions raised by:

```python
node.execute(context)
```

There is no exception-type filter in the current `RetryPolicy`.

Therefore, when a retry policy is configured, node exceptions are handled by the same retry mechanism regardless of exception class.

There is no current configuration such as:

```python
retry_on=[TimeoutError, ConnectionError]
```

in `RetryPolicy`.

---

# Retry vs Loop

Retry and Loop solve different problems.

| Retry | Loop |
| --- | --- |
| Responds to node exceptions | Responds to a workflow predicate |
| Re-executes failed node work | Intentionally repeats workflow routing |
| Implemented by the executor | Implemented by `LoopNode` |
| Uses `RetryPolicy` | Uses a loop predicate |
| Stops on success or attempt limit | Stops when the predicate becomes false |

Use Retry for failure recovery.

Use Loop for intentional iteration.

---

# Retry and Parallel Workflows

Retry can apply to nodes inside a parallel-style workflow.

Conceptually:

```text
             Parallel
             /      \
            v        v
       Branch A    Branch B
          |           |
          v           v
        Retry       Retry
          \           /
           \         /
             Join
```

The retry behavior still belongs to the workflow executor.

The `ParallelNode` does not implement retry logic itself.

---

# Retry and Timeout

Retry can be combined with workflow timeout behavior.

Conceptually:

```text
Workflow
   |
   +---- Timeout Policy
   |
   +---- Operation
             |
             +---- Retry Policy
```

The retry policy controls failed node execution.

The timeout policy is checked by the workflow executor during workflow execution.

The two mechanisms therefore serve different purposes:

- Retry handles node failures.
- Timeout limits workflow execution time.

---

# Final Failure

When the allowed attempts are exhausted, the executor invokes normal workflow failure handling.

The workflow failure path:

- Records the error in `context.errors`
- Marks the workflow context as completed
- Sets the workflow finish time
- Emits a `workflow.failed` event
- Persists the workflow instance
- Stores failed workflow history
- Returns an unsuccessful `WorkflowResult`

The failure handler also executes registered compensation callbacks, if any.

Compensation errors are ignored during this failure-handling phase.

---

# Failure Without Retries

A node failure without a retry policy follows the same final failure path:

```text
Node Execution
      |
      v
Exception
      |
      v
No Retry Policy
      |
      v
Workflow Failure
```

The workflow does not attempt the node again.


The retry behavior is provided by the executor rather than by additional workflow nodes.

# Safe Retry Considerations

Retrying a node means executing its operation again.

This is important for operations that have side effects.

For example:

```text
Send Email
Create Payment
Create Database Record
```

may not always be safe to repeat unless the underlying operation is designed to be idempotent.

A retry policy should therefore be used deliberately.

For external operations, consider whether repeated execution could produce duplicate side effects.

---

# Best Practices

- Set `max_attempts` deliberately.
- Remember that `max_attempts` includes the initial attempt.
- Retry operations only when repeating them is safe.
- Consider idempotency for external side effects.
- Do not assume `delay_seconds` currently causes a delay.
- Do not assume `exponential_backoff` is currently active.
- Remember that the current policy does not filter exception types.
- Combine retry with timeout behavior when appropriate.
- Monitor repeated failures in production.
- Test both successful recovery and exhausted retries.

# Summary

The **Workflow Retry** template demonstrates executor-level recovery from failed workflow-node execution.

When a node raises an exception and a `RetryPolicy` is configured, BindAI retries that node until it succeeds or the configured `max_attempts` limit is reached.

The current `RetryPolicy` contains:

```python
max_attempts
delay_seconds
exponential_backoff
```

Only `max_attempts` currently affects execution.

The current executor retries immediately. `delay_seconds` and `exponential_backoff` are not yet applied, and there is no exception-type filtering.

This makes the current retry implementation a simple attempt-limit mechanism that can be extended later with delays, backoff, and more selective retry behavior.

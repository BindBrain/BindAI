# Workflow Retry Template

The **Workflow Retry** template demonstrates how BindAI can retry failed workflow-node execution before ultimately failing the workflow.

Retry behavior is implemented by the workflow executor. When a node raises an exception and a retry policy is configured, the executor re-executes that node until it succeeds or the configured attempt limit is reached.

The current implementation provides basic executor-level retry handling. Retry delays and exponential backoff are not yet applied.

---

# Purpose

This template demonstrates how to:

* Configure a retry policy
* Retry failed node execution
* Limit repeated attempts
* Continue workflow execution after successful recovery
* Handle final workflow failure
* Understand the limitations of the current retry implementation

---

# Workflow Structure

Retry is handled by the executor rather than by a separate workflow branch.

Conceptually:

```text
Workflow
   |
   v
Operation
   |
   +---- Success ----> Continue
   |
   +---- Exception
            |
            v
        Retry Policy
            |
            v
         Try Again
```

The retry mechanism operates around the execution of the current node. It does not require an additional workflow node to represent each retry.

---

# RetryPolicy

The retry configuration is represented by `RetryPolicy`:

```python
from bindai_workflow.retry import RetryPolicy

policy = RetryPolicy(
    max_attempts=3,
    delay_seconds=5,
    exponential_backoff=True,
)
```

The policy contains three fields:

| Field                 | Default | Current behavior                                             |
| --------------------- | ------: | ------------------------------------------------------------ |
| `max_attempts`        |     `3` | Used by the executor to determine when retries are exhausted |
| `delay_seconds`       |     `5` | Defined but not applied by the executor                      |
| `exponential_backoff` |  `True` | Defined but not applied by the executor                      |

The executor uses `max_attempts` when deciding whether to retry a failed node.

The existence of a policy field does not mean that the corresponding behavior is implemented.

---

# Retry Policy Defaults

`RetryPolicy` is a dataclass with these defaults:

```python
RetryPolicy(
    max_attempts=3,
    delay_seconds=5,
    exponential_backoff=True,
)
```

The policy object stores configuration values. The workflow executor interprets the policy during node execution.

Currently, only `max_attempts` affects retry decisions. The policy does not itself execute nodes, wait between attempts, or calculate backoff intervals.

---

# Execution Flow

When a node executes successfully:

```text
Execute Node
     |
     v
  Success
     |
     v
Continue Workflow
```

When the node raises an exception and a retry policy exists:

```text
Execute Node
     |
     v
  Exception
     |
     v
Increment Failure Counter
     |
     v
Attempt Limit Reached?
     |
     +---- No ----> Retry Immediately
     |
     +---- Yes ---> Workflow Failure
```

The executor repeats the same node execution until it succeeds or the attempt limit is reached.

Retries occur immediately; the configured delay and exponential-backoff settings are not currently applied.

---

# Retry Lifecycle

For:

```python
max_attempts=3
```

the execution can look like this:

```text
Attempt 1
   |
 Failure
   |
Attempt 2
   |
 Failure
   |
Attempt 3
   |
 Success
   |
Continue Workflow
```

If all three attempts fail:

```text
Attempt 3
   |
 Failure
   |
Workflow Failure
```

Here, `max_attempts` represents the maximum number of failed attempts handled by this retry mechanism before failure, assuming the exception reaches the retry handler each time. It is not three additional retries after an initial attempt.

For example, with `max_attempts=3`, the executor can attempt the node up to three times. If the first attempt fails and the second succeeds, execution continues after the second attempt.

---

# Retry Counter

The workflow context tracks the current retry attempt using:

```python
context.retry_attempt
```

Before executing a workflow node, the executor resets the counter:

```python
context.retry_attempt = 0
```

When the node raises an exception and a retry policy exists, the executor increments it:

```python
context.retry_attempt += 1
```

The executor then compares the counter with:

```python
context.retry_policy.max_attempts
```

If the counter reaches the configured maximum, the executor returns a workflow failure. Otherwise, it continues the execution loop and retries the node.

After a successful node execution, the counter is reset.

---

# Successful Recovery

A retry can recover from a temporary node failure.

For example:

```text
Attempt 1
   |
Exception
   |
Retry Immediately
   |
Attempt 2
   |
Success
   |
Next Workflow Node
```

After the node succeeds, the executor resets:

```python
context.retry_attempt = 0
```

The workflow can then continue normally.

Successful recovery depends on the node succeeding on a subsequent attempt. The retry mechanism does not guarantee that a transient failure will resolve.

---

# Retry Without a Policy

If a node raises an exception and no retry policy is configured:

```text
Execute
   |
Exception
   |
No Retry Policy
   |
Workflow Failure
```

The executor invokes its normal failure handling.

There is no automatic retry when `context.retry_policy` is `None`.

---

# Retry Limit

The `max_attempts` field controls the limit used by the executor.

For example:

```python
RetryPolicy(
    max_attempts=3,
)
```

allows up to three attempts of the node execution handled by the retry loop:

```text
Attempt 1
Attempt 2
Attempt 3
```

If all three attempts fail, the executor invokes normal workflow failure handling.

Choose this limit deliberately, particularly when a node calls an external service or performs an operation with side effects.

---

# Retry Behavior in the Executor

The executor follows this simplified pattern:

```python
while True:
    try:
        node.execute(context)
        context.retry_attempt = 0
        return

    except Exception as ex:
        policy = context.retry_policy

        if policy is None:
            fail()

        context.retry_attempt += 1

        if context.retry_attempt >= policy.max_attempts:
            fail()

        # Retry immediately; no delay or backoff is applied.
```

This is a simplified illustration of the retry logic, not a complete copy of the executor implementation. The real executor also performs workflow bookkeeping and failure handling.

The retry is implemented within the node execution loop. No additional workflow node is required to represent the retry.

---

# Delay Configuration

The retry policy contains:

```python
delay_seconds=5
```

However, the current executor does **not** sleep for this duration.

For example:

```python
RetryPolicy(
    max_attempts=3,
    delay_seconds=5,
)
```

does not currently produce a five-second delay between attempts.

The field is defined in the policy, but it is not applied by the executor. Retries therefore occur immediately.

---

# Exponential Backoff

The policy also contains:

```python
exponential_backoff=True
```

However, the current executor does not calculate or apply exponential backoff.

The current behavior remains:

```text
Failure
   |
Immediate Retry
   |
Failure
   |
Immediate Retry
```

The `exponential_backoff` field is not currently active. Do not rely on it to increase the interval between retry attempts.

---

# Exception Handling

The current retry mechanism catches exceptions raised during node execution.

There is no exception-type filter in the current `RetryPolicy`. When a policy is configured, exceptions caught by this handler are subject to the same retry-attempt logic regardless of exception class.

There is no current configuration such as:

```python
retry_on=[TimeoutError, ConnectionError]
```

in `RetryPolicy`.

Applications should not assume that only transient or explicitly selected exception types will be retried.

---

# Retry vs Loop

Retry and Loop solve different problems.

| Retry                                          | Loop                                                      |
| ---------------------------------------------- | --------------------------------------------------------- |
| Responds to caught node execution exceptions   | Repeats workflow logic according to a loop predicate      |
| Re-executes failed node work                   | Intentionally repeats workflow routing                    |
| Implemented by the executor                    | Implemented by workflow loop functionality                |
| Uses `RetryPolicy`                             | Uses a loop predicate                                     |
| Stops on success or an exhausted attempt limit | Stops when its loop condition no longer permits iteration |

Use Retry for failure recovery. Use Loop for intentional iteration.

# Retry and Parallel Workflows

Retry behavior is implemented by the workflow executor rather than by `ParallelNode` itself.

Conceptually, a workflow might contain parallel branches:

```text
             Parallel
             /      \
            v        v
       Branch A    Branch B
           |          |
           v          v
         Node       Node
           |          |
           v          v
       Execution   Execution
        failure     failure
```

Whether retry behaves as expected within a particular parallel workflow depends on how that workflow is executed and how its node failures propagate.

Do not assume that retry configuration changes parallel-join semantics or guarantees recovery of an entire parallel branch. Verify those interactions for the workflow structure being used.

---

# Retry and Timeout

Retry and timeout policies serve different purposes:

* **Retry** handles exceptions raised during node execution.
* **Timeout** checks elapsed workflow time during execution.

The current timeout implementation checks elapsed time between node executions. It does not interrupt a node that is already running.

Consequently, retry and timeout should not be treated as independent guarantees that bound the total execution time. Immediate retries may continue within the node execution loop before the executor reaches its next timeout check.

Also note that the timeout policy's `fail_workflow` field is not currently used by the executor.

---

# Final Failure

When the retry limit is reached, the executor invokes its normal workflow failure handling.

That failure path is responsible for recording the failure and producing an unsuccessful workflow result. The exact persistence, event, and compensation behavior depends on the executor's failure-handling implementation.

Retry itself does not provide durable job recovery, distributed execution, or a guarantee that external side effects can be undone.

If your application depends on specific failure events, persistence behavior, or compensation callbacks, verify those behaviors against the relevant runtime implementation.

---

# Failure Without Retries

A node failure without a retry policy follows the normal failure path:

```text
Node Execution
      |
      v
Exception
      |
      v
No Retry Policy
      |
      v
Workflow Failure
```

The executor does not attempt the node again when no retry policy is configured.

# Safe Retry Considerations

Retrying a node means executing its operation again. This is important for operations that have side effects.

For example, these operations may not always be safe to repeat:

* Sending an email
* Creating a payment
* Creating a database record
* Submitting an order
* Calling an external API that changes state

An operation might succeed remotely even if the local workflow receives an exception before obtaining the result. Retrying it could then repeat the side effect.

A retry policy should therefore be used deliberately. For external operations, consider idempotency controls and application- or tool-level error handling.

---

# Best Practices

* Set `max_attempts` deliberately.
* Understand that the limit controls the number of attempts handled by the retry loop.
* Retry operations only when repeating them is safe.
* Consider idempotency for external side effects.
* Do not assume `delay_seconds` causes a delay.
* Do not assume `exponential_backoff` is active.
* Remember that the current policy does not filter exception types.
* Do not treat workflow timeout as a hard interruption of a running node.
* Test both successful recovery and exhausted retries.
* Verify failure and compensation behavior for workflows that depend on it.

# Summary

The **Workflow Retry** template demonstrates executor-level retry handling for failed workflow-node execution.

When a node raises an exception and a `RetryPolicy` is configured, BindAI retries the node until it succeeds or the configured attempt limit is reached.

The current `RetryPolicy` contains:

```python
max_attempts
delay_seconds
exponential_backoff
```

Only `max_attempts` currently affects retry execution. Retries happen immediately, and delay, exponential backoff, and exception-type filtering are not implemented.

The current implementation provides basic attempt-limit handling, which can be extended later with delayed retries, backoff, and more selective retry behavior.

# Workflow Timeout Template

The **Workflow Timeout** template demonstrates how BindAI can detect when a workflow has exceeded its configured execution-time limit.

Timeout checking is implemented by the workflow executor. Before processing each node, the executor compares the elapsed time since the workflow started with the configured `TimeoutPolicy`.

If the elapsed time exceeds the configured limit, the executor fails the workflow with:

```text
Workflow timeout.
```

The current timeout implementation is a workflow-level elapsed-time check. It does not forcibly interrupt a node that is already executing.

---

# Purpose

This template demonstrates how to:

- Configure a workflow timeout
- Limit total workflow execution time
- Detect workflows that exceed their configured duration
- Fail timed-out workflows through normal workflow failure handling
- Protect workflows from unexpectedly long execution

Timeouts are particularly useful for workflows that depend on external services or contain loops and other operations that may run longer than expected.

---

# Workflow Structure

A timeout does not introduce additional workflow nodes.

The normal workflow structure remains:

```text
Node A
  |
  v
Node B
  |
  v
Node C
  |
  v
Completed
```

The executor checks the elapsed workflow time while progressing through the workflow.

---

# TimeoutPolicy

Timeout configuration is represented by `TimeoutPolicy`:

```python
from bindai_workflow.timeout import TimeoutPolicy

policy = TimeoutPolicy(
    seconds=30,
)
```

The policy contains two fields:

| Field | Default | Current role |
| --- | --- | --- |
| `seconds` | Required | Maximum elapsed time used by the executor |
| `fail_workflow` | `True` | Configuration field; not currently consulted by the executor |

A policy can be assigned to the workflow execution context:

```python
context.timeout_policy = TimeoutPolicy(
    seconds=30,
)
```

---

# Timeout Policy Defaults

`TimeoutPolicy` is a dataclass.

For example:

```python
TimeoutPolicy(
    seconds=30,
)
```

creates a policy with:

```python
seconds=30
fail_workflow=True
```

The `fail_workflow` field currently does not change executor behavior.

When the timeout limit is exceeded, the current executor directly enters workflow failure handling.

---

# How Timeout Detection Works

The workflow executor checks the timeout during its main execution loop.

Conceptually:

```text
Workflow Started
      |
      v
Check Elapsed Time
      |
      +---- Within Limit ----> Execute Node
      |                            |
      |                            v
      |                       Next Node
      |                            |
      +----------------------------+
      |
      +---- Limit Exceeded ----> Fail Workflow
```

The elapsed time is calculated from:

```python
context.started_at
```

The executor effectively performs:

```python
elapsed = datetime.now(UTC) - context.started_at
```

and compares the result against:

```python
timedelta(seconds=policy.seconds)
```

---

# Timeout Trigger

If the elapsed time is greater than the configured duration, the executor enters its normal failure path:

```text
Workflow Execution
       |
       v
Timeout Check
       |
       v
Limit Exceeded
       |
       v
Workflow Failure
```

The timeout failure is generated by the executor as:

```python
self._failure(
    instance,
    "Workflow timeout.",
)
```

The resulting workflow is unsuccessful.

---

# Timeout Failure Behavior

A timeout is handled as a normal workflow failure.

The workflow failure handler:

1. Executes registered compensation callbacks
2. Records the timeout error
3. Marks the workflow context as completed
4. Records the finish time
5. Emits a `workflow.failed` event
6. Persists the workflow instance
7. Stores failed workflow history
8. Returns an unsuccessful `WorkflowResult`

The recorded error is:

```text
Workflow timeout.
```

---

# Timeout Checking and Node Execution

Timeout detection occurs during the executor's workflow loop, before the next node is processed.

For example:

```text
Node A
  |
  v
Timeout Check
  |
  v
Node B
  |
  v
Timeout Check
  |
  v
Node C
```

The timeout mechanism does **not** continuously interrupt a node that is already running.

For example:

```text
Workflow Started
      |
      v
Long-running Node
      |
      |  <-- node continues executing
      |
      v
Node Returns
      |
      v
Next Timeout Check
      |
      v
Timeout Detected
```

If a node blocks for a long time, the executor cannot perform its next timeout check until control returns from that node.

---

# Total Workflow Duration

The timeout is measured from the workflow context's `started_at` timestamp.

The executor does not reset the timeout after each node.

For example:

```python
TimeoutPolicy(
    seconds=30,
)
```

represents approximately 30 seconds of total elapsed workflow time from the recorded start time.

It does **not** provide a new 30-second allowance for every node.

---

# Successful Execution

If the workflow completes before the timeout limit, execution proceeds normally.

```text
Workflow Started
      |
      v
Node A
      |
      v
Node B
      |
      v
Node C
      |
      v
Workflow Completed
```

The executor records successful completion and returns:

```python
WorkflowResult(
    success=True,
    output=context.variables,
)
```

---

# Timed-Out Execution

If the workflow has exceeded its timeout when the executor performs its next timeout check:

```text
Workflow Started
      |
      v
Node A
      |
      v
Node B
      |
      v
Timeout Check
      |
      v
Timeout Exceeded
      |
      v
Workflow Failed
```

The resulting `WorkflowResult` is unsuccessful and contains:

```text
Workflow timeout.
```

---

# Workflow Events

A successful workflow eventually emits:

```text
workflow.completed
```

A timed-out workflow follows the failure path and emits:

```text
workflow.failed
```

The failure event contains the workflow and execution identifiers together with the failure timestamp.

There is no separate timeout-specific event in the current workflow executor.

---

# Execution History

A timed-out workflow is stored as a failed execution in workflow history.

The history contains:

```text
success = False
error = "Workflow timeout."
```

This allows timeout failures to remain available for monitoring and troubleshooting through the workflow history mechanism.

---

# Persistence

When the timeout failure occurs, the executor persists the workflow instance before returning the failure result.

This preserves the failed execution state for the workflow infrastructure.

---

# `fail_workflow` Configuration

`TimeoutPolicy` contains:

```python
fail_workflow: bool = True
```

For example:

```python
TimeoutPolicy(
    seconds=30,
    fail_workflow=True,
)
```

However, the current `WorkflowExecutor` does not inspect `fail_workflow`.

When the timeout condition is exceeded, the executor directly invokes:

```python
self._failure(
    instance,
    "Workflow timeout.",
)
```

Therefore, changing:

```python
fail_workflow=False
```

does not currently prevent workflow failure.

The field exists in the timeout configuration but is not yet an active execution control.

---

# Timeout and Retry

Timeouts and retries solve different problems.

| Timeout | Retry |
| --- | --- |
| Limits elapsed workflow execution time | Re-executes failed node work |
| Based on elapsed time | Based on node exceptions |
| Applies to the workflow execution | Applies to the current node execution |
| Produces workflow failure when exceeded | Continues until success or attempt limit |

For example:

```text
Workflow
   |
   +---- Timeout Policy
   |
   +---- Operation
             |
             +---- Retry Policy
```

Retry does not reset the workflow's timeout start time.

The timeout remains based on the same:

```python
context.started_at
```

---

# Timeout and Loops

Timeouts are particularly useful for workflows containing loops.

For example:

```text
Loop
  |
  v
Process Item
  |
  v
Update State
  |
  v
Loop
```

The timeout provides an overall execution limit:

```text
Loop
  |
  v
Process
  |
  v
Loop
  |
  v
Timeout Check
  |
  v
Workflow Failed
```

This can protect against unexpectedly long-running or incorrectly terminating workflows.

The timeout does not replace the loop's termination predicate.

---

# Timeout and Parallel Workflows

Timeouts also apply to workflows containing parallel-style fan-out.

For example:

```text
             Parallel
             /      \
            v        v
        Branch A  Branch B
            \        /
             \      /
               Join
                 |
                 v
              Continue
```

The workflow uses its existing `context.started_at` value when checking the timeout.

There is therefore one workflow-level elapsed-time check rather than an independently managed timeout for each branch.

The `ParallelNode` itself does not implement timeout behavior.

---

# Long-Running Operations

Timeouts are useful for workflows involving:

- AI providers
- External APIs
- Databases
- Document processing
- Cloud services
- Network operations
- External integrations

However, timeout detection is executor-driven.

If an individual node blocks for a long time, the executor cannot perform another timeout check until that node returns.

For operations that require forcibly cancelling or interrupting long-running work, additional infrastructure is required beyond the current workflow timeout mechanism.

---

# Choosing a Timeout

Timeout values should reflect the expected total workflow duration.

Example operational ranges might be:

| Workflow Type | Example Timeout |
| --- | ---: |
| Simple workflow | 10–30 seconds |
| AI workflow | 30–120 seconds |
| Document processing | Several minutes |
| Large batch workflow | Based on expected workload |

These are examples only. BindAI does not enforce these values as defaults.

Choose a timeout based on the actual workload and operational requirements.

---

# Important Implementation Boundaries

The current timeout implementation:

- Measures elapsed time from `context.started_at`
- Checks the timeout during the executor's workflow loop
- Compares elapsed time with `TimeoutPolicy.seconds`
- Fails with `"Workflow timeout."` when the limit is exceeded
- Uses normal workflow failure handling
- Records failed workflow history
- Emits `workflow.failed`
- Persists the workflow instance

The current implementation does **not**:

- Interrupt a node that is already executing
- Create a separate timeout for each node
- Create separate timeouts for parallel branches
- Reset the timeout after retries
- Use `fail_workflow` to control timeout behavior
- Emit a dedicated timeout event
- Cancel external operations automatically

---

# Best Practices

- Set a realistic timeout for the entire workflow.
- Remember that the timeout is measured from `started_at`.
- Do not assume the timeout interrupts an already-running node.
- Do not assume each node receives its own timeout duration.
- Do not assume `fail_workflow=False` currently disables failure.
- Use timeouts as protection against unexpectedly long workflows.
- Combine timeouts with retry policies when appropriate.
- Monitor `workflow.failed` events for timeout failures.
- Inspect execution history for repeated timeout errors.
- Make loop termination conditions explicit.
- Design long-running operations with executor-level timeout checking in mind.

# Summary

The **Workflow Timeout** template demonstrates how BindAI limits the elapsed execution time of a workflow.

A `TimeoutPolicy` specifies the maximum duration in seconds:

```python
TimeoutPolicy(
    seconds=30,
)
```

During execution, the `WorkflowExecutor` checks the elapsed time from `context.started_at` before processing the next node.

If the configured limit has been exceeded, the executor fails the workflow with:

```text
Workflow timeout.
```

The normal failure lifecycle then records the error, executes compensation callbacks, emits a `workflow.failed` event, persists the workflow state, stores failed history, and returns an unsuccessful `WorkflowResult`.

The policy also contains `fail_workflow`, but the current executor does not use that field.

Timeouts therefore provide a predictable workflow-level elapsed-time safety mechanism while remaining compatible with loops, retries, parallel fan-out, and other workflow features.

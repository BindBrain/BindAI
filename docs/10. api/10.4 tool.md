# Tool API Reference

Tools allow BindAI agents to perform operations beyond language-model generation.

A tool is a callable operation that can execute application logic, access external services, process data, or perform other deterministic work.

This page documents the current public Tool API and its relationship with agents and workflows.

---

# Overview

A typical tool execution flow is:

```text
Agent
  |
  v
Tool
  |
  v
ToolResult
```

Tools can be used for operations such as:

* Calling APIs
* Querying databases
* Searching data
* Processing files
* Performing calculations
* Sending notifications
* Executing application-specific logic

Tools provide a controlled interface between AI reasoning and application operations.

---

# Creating a Tool

A tool can be represented by a normal Python callable.

For example:

```python id="r7x3mc"
def search(query: str) -> str:
    return f"Search results for: {query}"
```

The function's parameters and type annotations provide useful information about the expected tool inputs.

Docstrings can also describe the tool's purpose and behavior.

---

# Registering a Tool

Tools are registered with a `ToolRegistry` when they need to be resolved and executed by the BindAI tool system.

Tools can also be supplied directly to an agent during construction.

For example:

```python id="k4m8vp"
from bindai_core import Agent

agent = (
    Agent.builder()
    .provider("openai:gpt-4.1-mini")
    .tool(search)
    .build()
)
```

This keeps tool registration associated with the agent that actually requires the tool.

---

# Multiple Tools

An agent can use multiple tools.

Conceptually:

```python id="v6q2nc"
agent = (
    Agent.builder()
    .provider("openai:gpt-4.1-mini")
    .tools(
        search,
        calculate,
    )
    .build()
)
```

Each tool should have a clear responsibility.

Exposing unnecessary tools can make agent behavior less predictable and increase the available action surface.

---

# Tool Registry

`ToolRegistry` manages registered tools.

Conceptually:

```text id="x8m4qc"
ToolRegistry
     |
     +---- Tool A
     +---- Tool B
     +---- Tool C
```

The registry is responsible for tool registration and lookup.

It can be used independently of the broader Project architecture.

---

# Tool Execution

The tool execution layer can execute a registered tool by name.

For example:

```python id="n5v9xb"
from bindai_core import ToolExecutor

executor = ToolExecutor(registry)

result = executor.execute(
    "search",
    "BindAI",
)
```

The executor returns a `ToolResult`.

---

# ToolResult

`ToolResult` is the result abstraction used by tool execution.

It contains:

| Property  | Description                             |
| --------- | --------------------------------------- |
| `success` | Whether the tool execution succeeded.   |
| `value`   | The value returned by the tool.         |
| `error`   | Error information when execution fails. |

Conceptually:

```python id="q3m7vc"
result = executor.execute("search", "BindAI")

if result.success:
    print(result.value)
else:
    print(result.error)
```

The successful tool value is available through `result.value`.

---

# Successful Tool Execution

When a tool executes successfully, its normal Python return value is wrapped in a successful `ToolResult`.

For example:

```python id="t8n4mc"
def add(a: int, b: int) -> int:
    return a + b
```

Executing the tool produces a result whose value is:

```text
3
```

when called with `1` and `2`.

Applications should use `ToolResult.value` to access the returned value.

---

# Failed Tool Execution

If a tool raises an exception during execution, the tool system represents the failure through a failed `ToolResult`.

Conceptually:

```python id="p6v3xb"
result = executor.execute("some_tool")

if not result.success:
    print(result.error)
```

This allows callers to handle tool failures without treating every expected tool failure as an application crash.

---

# Unknown Tools

Attempting to execute a tool that is not registered produces a failed `ToolResult`.

For example:

```python id="m4q8vc"
result = executor.execute("missing_tool")
```

The result indicates failure and includes an error describing the unknown tool.

Applications should validate tool registration when constructing larger execution systems.

---

# Tool Inputs

Tools receive normal Python arguments.

Typical inputs include:

* Strings
* Integers
* Floating-point values
* Booleans
* Lists
* Dictionaries
* Structured Python objects

For example:

```python id="b7n3xc"
def create_ticket(
    title: str,
    priority: str,
) -> str:
    ...
```

The function signature communicates the expected arguments.

Tool implementations should still validate values where application or security requirements demand it.

---

# Tool Outputs

Tools can return normal Python values.

Examples include:

* Strings
* Numbers
* Dictionaries
* Lists
* Structured records
* API responses
* Search results

The tool execution layer wraps the returned value in `ToolResult`.

For successful execution:

```python id="c9m4vp"
result.value
```

contains the tool's returned value.

---

# Tool Context

The current standard tool API does not require every tool to receive an implicit workflow or execution context.

A normal tool can simply declare the parameters it needs:

```python id="f8q2mc"
def lookup_customer(customer_id: str) -> dict:
    ...
```

This keeps tools explicit and easy to test.

Applications that require additional state should pass the required information explicitly or use an appropriate application subsystem such as Memory.

Do not assume that a standard tool automatically receives a `context` object or exposes arbitrary workflow variables.

---

# Agent Tool Calling

Agents can use registered tools during model execution.

Conceptually:

```text id="y5n8vc"
User Request
     |
     v
Agent
     |
     v
Model
     |
     +---- Tool Call
              |
              v
            Tool
              |
              v
          ToolResult
              |
              v
        Continue Execution
```

The model can determine that a tool is appropriate when tool calling is supported by the configured provider.

The exact number and sequence of tool calls depends on the agent, model, provider, and execution configuration.

---

# Tools and External Services

Tools are a useful boundary for external operations.

For example:

```text id="u7m3xc"
Agent
  |
  v
Tool
  |
  v
Connection
  |
  v
External Service
```

A tool can use a BindAI Connection to communicate with an external service.

This keeps service-specific communication outside the agent's reasoning logic.

---

# Tools and Workflows

Tools can also participate in workflows.

Conceptually:

```text id="r6q9mc"
Workflow
    |
    v
Tool
    |
    v
ToolResult
```

A workflow can use tools for deterministic operations, external API calls, data processing, or other application logic.

The exact workflow integration depends on the workflow implementation.

---

# Shared Tools

The same tool implementation can be supplied to multiple agents.

For example:

```text id="p8m4xc"
             Search Tool
             /    |    \
            /     |     \
           v      v      v
        Agent A Agent B Agent C
```

This is a sharing pattern rather than a special `SharedTool` class.

Shared tools are useful when several agents require the same operation.

---

# Local Tools

Some tools should remain specific to one agent or application.

Examples include:

* Internal business operations
* Application-specific transformations
* Specialized domain logic
* Privileged operations

Keeping such tools local reduces unnecessary coupling and limits their exposure.

---

# Tool Discovery

Agents should only receive the tools they are intended to use.

Explicit tool assignment improves:

* Predictability
* Security
* Maintainability
* Prompt clarity
* Execution control

A tool should not be exposed broadly merely because multiple agents could technically use it.

---

# Tool Security

Tools can have significant privileges.

A tool might be able to:

* Read private data
* Modify databases
* Send messages
* Create external resources
* Trigger deployments
* Delete information

Therefore:

* Validate inputs.
* Limit permissions.
* Protect credentials.
* Restrict state-changing operations.
* Avoid exposing secrets to models.
* Audit sensitive operations where appropriate.
* Use separate tools for clearly different privilege levels.

The agent should not be treated as a security boundary.

---

# Read vs Write Tools

It is useful to distinguish between read-only and state-changing operations.

### Read operations

Examples:

* Search
* Retrieve records
* Read documents
* Inspect configuration

### Write operations

Examples:

* Create records
* Update data
* Send messages
* Trigger deployments
* Delete resources

Write operations generally require stricter validation and authorization.

---

# Idempotency

Tools that perform external side effects should consider idempotency.

For example:

```text id="d5v8mc"
Tool Call
   |
   v
External Operation
   |
   +---- Success
   |
   +---- Unknown Outcome
             |
             v
           Retry?
```

A retry can accidentally duplicate an operation if the first request actually succeeded.

Where supported, use idempotency keys or other mechanisms provided by the external service.

---

# Error Handling

Tool implementations should handle expected failures explicitly.

Potential failures include:

* Invalid input
* Authentication errors
* Permission errors
* Network failures
* Rate limits
* External-service errors
* Unexpected exceptions

The tool system converts execution exceptions into failed `ToolResult` values.

Applications should inspect:

```python id="e7m3vx"
result.success
result.error
```

when appropriate.

---

# Tool Performance

Tools should avoid unnecessary work.

Useful practices include:

* Minimize external requests.
* Reuse appropriate connections.
* Avoid unnecessary computation.
* Use caching when appropriate.
* Keep payloads reasonably small.
* Set appropriate external-service timeouts.
* Avoid long-running operations when a workflow mechanism is more appropriate.

Tool performance directly affects the responsiveness of agents and workflows that depend on those tools.

---

# Tool Documentation

Tools should have clear interfaces.

A good tool should communicate:

* What it does
* What arguments it accepts
* What it returns
* What failures can occur
* What external side effects it performs

For example:

```python id="w3m8vc"
def search(query: str) -> list[str]:
    """Search the configured knowledge source."""
    ...
```

Clear descriptions improve maintainability and help models understand when a tool should be used.

---

# Tool Testing

Tools should be tested independently from agents.

Useful tests include:

* Valid arguments
* Invalid arguments
* Return values
* Exceptions
* External-service failures
* Authentication failures
* Permission failures
* Side effects
* Idempotency
* Boundary conditions

A simple unit test can exercise the underlying Python function without involving a language model.

Integration tests can separately verify real external-service behavior.

---

# Tool Reuse

Reusable tools should have stable interfaces.

A shared tool should avoid depending unnecessarily on:

* Global mutable state
* A particular agent
* A particular prompt
* A specific workflow
* An unrelated application's internal state

Keeping tools self-contained makes them easier to reuse across agents and workflows.

---

# Tool and Memory

Tools can interact with Memory when an application requires persistent information.

Conceptually:

```text id="n4q8mc"
Agent
  |
  v
Tool
  |
  v
Memory
```

The tool should use the Memory API explicitly rather than assuming that tool execution automatically provides memory access.

---

# Tool and Knowledge

Tools can also interact with Knowledge.

For example:

```text id="x6m3vc"
Agent
  |
  v
Tool
  |
  v
Knowledge / Retrieval
```

However, when the agent itself already has Knowledge and retrieval configured, a separate retrieval tool may not be necessary.

Choose the simplest architecture that provides the required behavior.

---

# Tool Lifecycle

A typical tool lifecycle is:

```text id="q8v4mc"
Define
  |
  v
Register
  |
  v
Expose to Agent / Workflow
  |
  v
Execute
  |
  v
ToolResult
```

The underlying Python callable can remain independent from the lifecycle of an agent.

---

# API Accuracy

The current Tool API should not be confused with a project-level tool-management API.

This documentation intentionally does not assume methods such as:

```python id="m5q9xc"
project.add_tool(...)
project.tools(...)
project.tool(...)
shared_tool(...)
tool.execute(...)
tool.success()
tool.failure()
```

unless they are explicitly implemented by the installed BindAI version.

The verified execution pattern is based on the tool registry and executor:

```python id="v8m3qp"
executor = ToolExecutor(registry)
result = executor.execute(
    "tool_name",
    *args,
    **kwargs,
)
```

The result is a `ToolResult` with `success`, `value`, and `error`.

---

# Best Practices

* Give each tool a focused responsibility.
* Use explicit function parameters.
* Provide clear type annotations.
* Document tool behavior.
* Validate important inputs.
* Return predictable values.
* Handle expected failures.
* Limit tool permissions.
* Keep credentials outside prompts and source code.
* Expose only required tools to each agent.
* Test tools independently.
* Treat state-changing tools with additional caution.
* Keep reusable tools independent from application-specific state.

---

# Related APIs

The Tool API works closely with:

* Agent
* `ToolRegistry`
* `ToolExecutor`
* `ToolResult`
* Workflow
* Memory
* Knowledge
* Connections

Together these components allow BindAI agents and workflows to perform controlled application operations.

---

# Summary

Tools extend BindAI beyond language-model generation.

The core execution flow is:

```text id="b4m7xc"
Python Callable
      |
      v
Tool Registry
      |
      v
Tool Executor
      |
      v
ToolResult
```

Agents can use tools during model execution, while workflows can use tools as deterministic operations.

The current Tool API emphasizes simple Python callables, explicit registration, predictable `ToolResult` values, and controlled integration with external systems.
